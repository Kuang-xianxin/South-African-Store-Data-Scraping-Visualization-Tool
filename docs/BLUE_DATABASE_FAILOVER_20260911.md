## 已确认需求

用户要求主机失联后笔记本接管完整BLUE ERP，明确包括人工编辑、配置和权限修改。用户接受两库短暂分叉并在恢复后去重合并，核心限制是Seller API不能由两台同时调用；正常API出口优先主机。此要求覆盖此前固定101、必须先证明数据库硬隔离或迁移三节点才能继续的方案前提；保留全部变更和明确处理冲突仍属交付要求。

用户已确认没有腾讯可独立控制的远程电源隔离设备。本次已授权方向包含完整ERP接管和恢复合并，但没有授权复制完整业务库到腾讯或购买/扩容云资源。三节点组复制仅保留为另一种一致性方案，不再作为本方向的前置条件。

## 当前方向：可分叉的数据，与不可分叉的API执行权

- 正常主机承担ERP主角色和Seller API执行；笔记本维持可接管的数据副本。主机失联达到判定条件后，腾讯可指定笔记本为当前ERP接管节点，笔记本的数据库连接、实际写权限、后台任务与公共入口须一并切换。
- API执行权单独管理，不从“数据库可写”“本机看起来是主节点”推导。真实发送出口必须拒绝旧代次或无权限的调用，覆盖手动刷新、定时、翻页、重试及子进程；仅在开始前检查锁或网页分流不足。还要清点GREEN是否使用同一账号，不能只锁BLUE就宣称所有环境无重复调用。
- 腾讯失联时不得各自发放Seller API执行权。已发出的请求状态不明时暂停新出口派发；ERP本地编辑与API暂时等待应分开显示。旧主恢复不自动抢回执行权，笔记本原刷新完成后再让下一次正常刷新优先主机。
- 应优先评估由腾讯统一派发、受控请求出口实际执行的方案；普通可过期租约存在进程暂停、迟到请求及在途未完成窗口，不能仅靠延时就宣称严格互斥。若不能消除窗口，须明确披露并保持保守等待。[请求侧隔离分析](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)
- 数据库可以按用户取舍存在短暂分支；每次故障切换保存代次、共同基线和双方后续变更。两个可写MySQL实例恢复后不能直接开启相互复制，也不能清库覆盖旧主。先保存分支证据，再运行受控合并与校验。

## 完整ERP恢复合并的规则

以下是完整交付要求。当前仅实现只读分支快照和三方冲突计划，尚未实现完整事务变更日志、人工冲突界面与MySQL合并回写。MySQL多源复制自身不负责冲突检测/解决，业务层必须处理。[MySQL说明](https://dev.mysql.com/doc/refman/8.0/en/replication-multi-source.html)

| 数据类别 | 去重与合并要求 |
| --- | --- |
| Seller订单 | 保留店铺作用域与order_item_id业务身份。相同投递ID/相同内容幂等；同一订单不同状态或费用属于修订，不能当重复丢掉，也不能仅按到达时间取最后一条 |
| 库存与采集历史 | 保留店铺、Offer/变体、实际采集时间、任务/观察ID和来源；不同时间的库存分别保留，旧补交不得覆盖更新观察；历史数据不能把不同商品共享SKU直接合并 |
| 人工编辑与业务配置 | 保存稳定对象ID、原基线/版本、修改者和字段变更；一边未改时可合并另一边变更。双方同字段不同值进入冲突，保留两份证据；关联事务、外键、唯一约束和删除标记一起处理 |
| 账号、密码、权限 | 不能取权限并集或按最新机器时间覆盖。撤权/停用不得被旧记录复活；密码冲突不得静默择一，必要时撤销会话并由有权人员处理。网络分区期间另一端无法即时获知新撤权，这属于此可用性取舍的真实限制 |
| 队列、预约、额度与后台任务 | 已结束/取消的任务不能被迟到分支重开；刷新及外部调用不因恢复合并重放。模型额度、冷却和单次预约也不能因切库重置，关联回执与业务结果需同事务核验 |
| 派生指标、缓存与导出 | 优先由合并后的基础数据重建，保留历史报告时间和审计记录；不拼接两份缓存后冒充一致数据 |

原竞品交付日志已使用attempt_id/内容校验与事务回执，但只覆盖其采集结果，不是Seller API或全部ERP的跨库合并实现。Seller API客户端的翻页和重试最终经过TakealotClient._send_get，当前已提供请求执行权钩子并完成测试，但启用标记仍关闭，未宣称所有运行进程已装载。仓储层仍按现有业务主键更新，尚没有完整的跨库合并回写。

## 本方向的交付门槛

1. 在隔离环境实现并验证API请求出口限制：双方抢执行权、旧代次、暂停后恢复、在途请求、腾讯重启、网络分区和所有调用入口。请求不明不等于可自动重试。
2. 为完整ERP保存可重放/可审计的事务或变更日志，验证新增ID冲突、更新/删除冲突、外键、撤权、密码、队列和额度；无冲突自动合并，冲突保持双方证据并提供处理入口。
3. 连接与身份保护支持实际接管节点；把定时任务、文件导出、权限会话、集成和公共入口逐项纳入。复制正常或健康200不能代表完整ERP已接管。
4. 在持久化安全边界备份并发布双节点，验证真实受控故障、恢复合并及原采集连续性，再启用自动接管。不能先允许无日志双写、等发生冲突后再补实现。

## 前次一致性风险核验（风险仍存在，用户已调整取舍）

腾讯联系不上主机时，主机可能断电，也可能只是断开到腾讯的链路，而本机ERP和数据库仍能运行。现有协议故意不会在超时后释放旧owner；直接绕过会丢掉单写保护。独立进程心跳和最近一次只读/GTID快照不等于当前硬隔离证明。

异步复制还存在主机已提交、笔记本尚未收到的事务窗口。MySQL官方明确说明该故障情形可能导致提升缺失事务的副本；单独开启有超时回退的半同步，也不能被描述为完整故障接管方案。[MySQL 8.0 半同步说明](https://dev.mysql.com/doc/mysql-replication-excerpt/8.0/en/replication-semisync.html)

## 保留的替代方案：三节点单主组复制（非当前前提）

这是前次候选架构。用户已选择允许数据库短暂分叉、但要求API独占；本方案不再阻塞当前方向，也未获准迁移。

1. 主机、笔记本、腾讯各运行一个专用BLUE MySQL成员；腾讯必须保存第三份业务数据，不能只运行现有无数据仲裁脚本。三成员可容忍一成员故障，失去多数的一侧无法继续提交。[多数派条件](https://dev.mysql.com/doc/refman/8.0/en/group-replication-fault-tolerance.html)
2. 正常以主机为PRIMARY；同版本成员选举偏好主机、笔记本、腾讯依次降低。主机失效且笔记本与腾讯健康时，目标为笔记本PRIMARY。腾讯协调器读取数据库实际成员角色再发布主库状态，不覆盖组内共识结果、不靠陈旧心跳强制新建组。
3. 所有成员启动先只读；退出组时采用阻止业务连接/写入的策略。旧主恢复后先以SECONDARY加入并追平，禁止自动强制bootstrap或删除不一致事务以迎合组状态。数据库是否切回主机通过受控切换处理，不能靠主机上线就抢主。[故障和网络分区](https://dev.mysql.com/doc/refman/8.0/en/group-replication-responses-failure.html)、[启动及退出保护](https://dev.mysql.com/doc/refman/8.0/en/group-replication-responses-failure-exit.html)
4. BLUE应用、worker、模型额度存储和子进程都通过经过核验的动态写主入口连接；保留环境标记、CA、节点UUID和3307隔离，连接池换主时失效。不自动重试结果未知的业务事务，也不重放未确认结束的Seller API整次刷新。
5. Seller API出口偏好独立于数据库主权。主机故障时在笔记本开始新的合法刷新；主机恢复后等待笔记本既有刷新结束，下一次可回主机执行并连接届时实际写主。正在执行的刷新迁移/续跑不自动包含在数据库切换中。

Windows与Linux节点需统一MySQL兼容版本、lower_case_table_names（现主机为1）、事务/日志与加密配置，建立三向受限网络和TLS。网络延迟影响提交性能，当前未完成三向延迟和稳定性验收，不承诺秒级无感。[组复制要求](https://dev.mysql.com/doc/refman/8.0/en/group-replication-requirements.html)

## 三节点替代方案的迁移门槛（仅选择此方案时适用）

- 先确认用户接受腾讯保存BLUE第三副本，并解决内存容量；不自动购买/扩容资源，不因本提案移动GREEN数据库。
- 用独立空库与合成数据验证单主、主机进程故障、网络分区、仲裁重启、旧主恢复和结果未知的事务；不借生产断电来替代隔离试验。
- 对BLUE做可恢复备份，验证全实例表结构、权限、SQL和应用连接兼容性；保留原数据、账号隔离、采集队列、交付日志和刷新归属。
- 等原刷新空闲、采集结果可靠落盘后安排切换边界，获取最终GTID并核对完整迁移；迁移失败时不得擅自回滚已在新主提交的数据。
- 最后才进行受控真实切换及恢复验收，同时验证唯一PRIMARY、旧主拒写、复制一致、应用实际连接与授权业务读写、公共入口和原批次连续性；达到这些证据后才宣布自动接管已启用。
