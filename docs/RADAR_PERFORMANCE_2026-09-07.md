# 绿版雷达读取性能优化（2026-09-07）

## 诊断与实现

公网 nginx 的慢请求样本中，自有商品接口总耗时与回源耗时均约 22.7～22.9 秒，回源使用本机反向 SSH 通道 18503。这个阶段的主要瓶颈在本机读库和计算；不能把全部慢请求归因于公司出口 IP。

六店、1039 个自有商品的本机基线：历史投影 16.097 秒、官方销量 8.010 秒、完整调用 24.297 秒。性能剖析发现大量历史行由纯 Python 驱动解码，以及每个商品重复计算相同店铺、相同日期的销量完整性。

本次实现：

- 新增可选 `fast-reads` 依赖组，安装 Windows CPython 3.11 的 `mysqlclient==2.2.8`，绿版 `.env` 设置 `TAKEALOT_ERP_READ_DRIVER=mysqlclient`。只转换 ERP 只读引擎的 `mysql+pymysql` URL；采集与写入连接保持原驱动。只读事务限制继续由公共引擎实现。
- 官方销量按店铺、日期预计算完整性和修订证据；纯日期转换使用有上限的缓存。缺失、零销量、时区、截止日及全部历史累计口径保持原样。
- 复用 Seller 历史与官方销量元数据，组件缓存最多 4 项、最长 600 秒；按数据修订版本、店铺、PLID 和截止日期区分。并发同键请求沿用已有合并机制。
- 官方销量元数据与卡片字段分开缓存，返回值深拷贝；权限改变或相关店铺更新使对应缓存失效。竞品采集不再无条件使未改变的 Seller 历史重算。
- 真正竞品完整响应与自有商品完整响应采用各自实际依赖的数据主题；保留原完整响应缓存上限和 180 秒 TTL。

没有增加 Redis：已有进程内缓存与请求合并机制，本次证据指向首次读库和重复计算，单独替换缓存存储无法消除这些成本。

## 验证记录

- 同一个真实 MySQL 只读事务内，新旧官方销量结果对六店、1039 个 PLID 完整比较一致；该次销量函数由 11.562 秒降至 2.736 秒。
- 单独组件计时：首次 14.214 秒 / 58 条 SQL；复用组件为 5.633 秒、10.032 秒 / 13 条 SQL。采集和主机负载影响明显，不能把最短样本当作稳定承诺。
- 相关测试初始两组共 145 项通过；补充混合空 PLID 与缓存可变对象隔离检查后，相关 15 项重跑通过，合计覆盖 146 个不同测试。

## 发布与回滚边界

只发布当前绿版后端。公司网卡、DHCP、路由器、网关、DNS、代理配置及 MySQL 服务均不调整；蓝版独立环境未部署本次依赖或配置。

正式启动使用 `scripts/restart_erp.ps1`，前后保留原批次、检查点、已有成功记录与队列。驱动回滚可将 `.env` 的 `TAKEALOT_ERP_READ_DRIVER` 改回 `pymysql` 后通过相同正式脚本重启。源码回滚应只撤销本任务差异，不能整体覆盖并行任务的改动。新驱动无数据库迁移。

冷缓存、相关店铺刷新、应用重启、权限或数据版本变化仍可能触发重算；本次不保证任何情况下都瞬间打开。
