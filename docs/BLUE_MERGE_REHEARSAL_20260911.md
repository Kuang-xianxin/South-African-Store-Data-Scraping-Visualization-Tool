## 本轮新增行为

- 主机以实际 `S-1-5-18` 身份生成 Seller 专用密钥，公钥在腾讯登记为固定 `main --seller-only` 受限命令；实际 SSH 认证成功，查询返回 `seller-coverage-not-enabled`，Seller HTTP 调用为 0。临时 SYSTEM 任务已结束并删除。此前的提升进程失败保留为历史记录，本轮原生提升成功。
- `blue_branch_apply.open_review` 持有三份快照和计划的只读事务，从完整来源重新计算每一条候选、冲突及摘要。仅重新计算被删减计划的摘要，也不能把遗漏的行变成已通过的计划。
- `blue_branch_review.py resolution-template` 产生绑定计划摘要的 JSON 冲突选择文件，默认没有答案，不导出密码、会话或业务行正文；选择须填写 `old` 或 `current` 和理由。`validate` 重新核对全部来源与选择，输出计划、选择和结果摘要，MySQL 写入为 0。这个文件不是 ERP 人工处理页面，也不代表已获业务裁决。
- 普通业务冲突可以显式选取版本；账号、权限、会话、额度、队列和不可改写历史不能通过通用工具选取旧记录。保留当前撤权状态通过测试；恢复旧权限仍需专门的业务处理流程。
- 合并 SQL 使用参数绑定，不执行快照中的 DDL，不关闭外键或唯一约束。按依赖先删子后删父、先写父后写子；循环关联、额外表、表结构漂移、触发器和事件拒绝进入通用执行路径。
- 在实际写入前和提交前比较所有业务行，检测未参与计划的并发变化，以及意外 CASCADE/SET NULL 副作用。一条约束失败或最终状态不符，会回滚整笔行变更及回执。
- 计划摘要、冲突选择摘要和最终行摘要形成与业务变更同事务的回执。提交回复丢失后先查询回执；已经提交的计划不会重放，也不会把后续人工修改覆盖回旧结果。更换已提交计划的冲突选择会被拒绝。

事务执行先关闭自动提交再取得显式表锁，事务提交或回滚后才解锁；没有在锁后调用会释放表锁的 `START TRANSACTION`。实现依据及限制见 [MySQL 表锁与事务说明](https://dev.mysql.com/doc/refman/8.0/en/lock-tables.html)。

## 真正执行和未执行的范围

真实回写只在测试启动的独立 MySQL 8.0 实例中执行：随机 loopback 端口、独立临时数据目录、server_id=987654、64MiB buffer pool、合成业务行，未注册服务，测试结束关闭所拥有的进程。没有读取或复制任何真实业务分支。

`rehearse` 在 DML 前核对专用数据库名称、随机标记、UUID、端口、server_id 和数据目录，拒绝 `takealot_ops`、已知蓝库 UUID、3306/3307/13317 和101/102。调用要求独占的专用连接，不用于应用连接池。该入口不能被当作已就绪的生产合并执行器。

回滚演练确实执行过 SQL，只是行变更和事务回执最终回滚；它不是对任意生产库“无副作用试跑”的承诺。自增计数器可能在回滚后前移，因此本工具仅允许合成演练实例。[MySQL 自增分配与回滚说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-auto-increment-handling.html)

原计划字段 `mysql_apply_available=false` 继续表示生产回写尚不可用。真实约束通过不等于跨分支业务事务语义已验证：原始事务日志、权限/配置的专门合并、真实数据副本演练和动态角色保护仍待完成。
