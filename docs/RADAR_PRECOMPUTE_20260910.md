# 雷达持续预计算与分析层试点

2026-09-10 17:31。第一阶段已发布 GREEN、BLUE 主机与 BLUE 笔记本；云端分析试点仅完成准备包，未部署。

## 本轮修改

- 延续 MySQL 事实库和本地 SQLite 压缩卡片索引，单个计算线程、每批最多 64 个 PLID；索引与卡片仍在完整事务提交后一起可见。
- 新增本地预热登记，最多保存四个最近查询意图。启动时恢复，之后每分钟重新核对账号启用状态、实时权限和授权店铺，再调用同一只读查询路径。首次没有登记时，为最近登录且有权限的最多两个账号准备两个分区；不会保存会话或权限副本。五分钟无人访问不再导致常用登记范围停止更新。
- 完整日期范围跟随实际数据边界推进；用户明确缩窄的历史范围保留。任意新增范围仍可能需要首次完整构建，不能把后台预热等同于冷计算本身加速。
- 旧物化结果只在同一源码版本、账号权限、店铺归属和查询范围内作为带生成时间的预览；取消十五分钟后必须等重算的限制。严格刷新请求仍等待完整结果，失败不发布半份数据。
- 自有官方销量跨日改变数据版本和商品指纹，保留权限正确的旧预览。每次构建固定日期与读取闭包，避免一次事务混用前后两天的计算。
- 物化源码指纹跟踪雷达处理函数、本地辅助函数及其项目内导入依赖；依赖模块保守地整份纳入。无关页面函数体修改不会再全部失效。旧版未分页接口缓存维持原策略。

## 分析层部署决定

腾讯主机 119.91.117.232 本次只读实测：2 个逻辑核、1963MiB 物理内存、276MiB available、2047MiB swap 已全部占用，根分区剩余 28GiB；未发现 Docker 可执行文件。该时刻容量不足以承载新分析服务，本轮不向该代理/仲裁机器安装容器或分析组件。

后续采用独立云资源上的一套共享 Cube Core（[仓库](https://github.com/cube-js/cube)，⭐20,797，2026-09-10核对；[官方记载](https://cube.dev/blog/cube-dev-raises-62m-to-accelerate-cubejs-development)2019年3月开源），通过受限内网通道连接只读数据源；两台 Windows ERP 继续保留各自读取与爬虫职责。先用独立 BLUE 数据和官方销量口径做影子验证，通过后再评估 GREEN 接入。GREEN 与 BLUE 数据、凭证和预聚合命名空间必须隔离，不能因为共享云资源而合并数据库。

已准备 [Compose与试点说明](../deploy/cube-pilot/README.md)。配置只开放回环API、分配独立持久卷并限制并发/内存；镜像摘要和数据源必须显式提供，业务模型与权限验证前拒绝查询。YAML及JavaScript语法检查通过，未运行Docker或创建数据通道。第二次主机采样available约305MiB，swap仍全部占用；两次采样都不满足这套试点的容量预算。

Cube 的 API、刷新进程和 Cube Store 都需要内存；预聚合数据还需要持久磁盘。参考[官方部署文档](https://docs.cube.dev/admin/deployment/core)、[MySQL 数据源文档](https://docs.cube.dev/admin/connect-to-data/data-sources/mysql)。试点初始并发设为 1；容量上限根据实测峰值确定，不用交换空间充当可用预算。

试点的验收口径：固定相同数据版本，比较当前服务与分析结果的店铺/PLID/Offer/日期/覆盖缺失、7/15/30/60/90 天及累计销量；缺失不补零，历史修订可回补。然后测完整入口的首次、重复、增量及重启读取、内存峰值、磁盘增长和断网表现。只有实际降低端到端延迟、无权限泄漏且成本可接受，才将 ERP 请求切入；原读取路径作为回退。
