# 2026-09-05 查询与渲染性能复核

## 实测结论

本轮针对正式 ERP 的本机 MySQL 只读投影。计时不包含用户电脑渲染、图片下载和公网网络延迟，也不代表永久 SLA。采集仍在自然运行，没有为测试停止采集、修改业务数据或触发新的平台请求。

| 范围 | 优化前 | 优化后 | 核对 |
|---|---:|---:|---|
| 1366 张真正竞品卡，完整历史冷投影 | 8.431 秒 | 5.903 秒 | 同一 MySQL 只读事务，完整 JSON 相同，约快 30% |
| 1039 张自有卡，六店历史冷投影 | 9.962 秒 | 9.364 秒 | 同一事务，完整 JSON 相同；不含随后官方销量汇总 |
| 真正竞品完整接口投影 | 8.415 秒 | 5.996 秒 | 包含列表序列化前的数据装配；普通计时 |
| 10000 次相同 ZAR 金额格式化 | 327.06 毫秒 | 12.60 毫秒 | 每个格式化字符串相同；这是函数基准，不是页面整体提速倍数 |

最初带 cProfile 的真正竞品/自有历史投影分别为 22.6/27.5 秒，其中包含剖析器开销，不能与上表普通计时混用。真正竞品查询实际读取约 2.7 万商品快照与 3.6 万变体记录。

## 已落地

- 历史商品与变体使用完整字段的轻量只读行，省去数万条 ORM 实例的状态追踪和属性访问开销；列名显式绑定，历史点、字段和排序不删减。
- 库存五窗口仅计算所需件数；只含一个卖家/报价的相同范围复用结果；日期和报价身份不重复解析。不改变精确库存、范围分轨、跨缺失净变化、补货独立及数据不足规则。
- 卖家发现历史只投影身份；同一快照报价索引复用；过期库存参考仅在同 PLID 历史中查找。
- 自有历史查询提前按实际可见当前 PLID 收窄，结果与原先读全量再过滤一致。
- 链接复核仅读取每个异常 PLID 最新一条快照，保留同 PLID 的真实图片/标题。
- 真正竞品独立分区的短缓存按日期共享；含自有数据的缓存仍严格按授权店铺隔离。
- 页面刷新优先完成当前查看分区，再加载另一分区。自有分区优先且尚未确定日期时，先用轻量日期接口得到与原首屏一致的真正竞品观察边界。刷新时保留已有卡片，旧请求不得覆盖当前店铺或更新后的目标缓存。
- 11 个 Vue 页面/组件共用最多 32 个数字格式化对象，保留各自币种、小数位、紧凑金额和空值规则。

曾实测同时启动两个历史投影：两块都完成由 23.207 秒缩短至 17.760 秒，但真正竞品首屏从 8.415 秒退化到 9.148 秒。最终采用当前分区优先，未采用无条件并行。自然采集会更新列表排序，跨不同事务的接口结果不能直接按数组位置作一致性结论；一致性证据以上表同事务核对为准。
