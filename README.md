# Takealot 店铺运营数据工具

这是一个在 Windows 本机运行的小型运营 ERP：通过只读 Seller API 采集自有店铺 Offer 与 Sales 数据，并通过公开商品接口和隔离匿名购物车观察竞品。统一的 Vue 3 + TypeScript 前端包含经营总览、商品中心、经营四象限、风险与质量、竞品雷达、报表与 NFT102 工作台；自有店铺和竞品历史统一保存在本机 MySQL 8.0。

## 1. 安装

在 PowerShell 中进入项目目录：

```powershell
Set-Location -LiteralPath 'D:\南非店铺数据抓取'
uv venv --python 3.11 .venv
uv pip install --python .\.venv\Scripts\python.exe -e ".[dev]"
.\.venv\Scripts\python.exe -m playwright install chromium
```

检查命令是否已安装：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli --help
```

## 2. 配置 API Key 与 MySQL

复制模板，生成项目根目录下的 `.env` 文件：

```powershell
Copy-Item .env.example .env
notepad .env
```

填写 API Key，并把 MySQL 密码替换为本机应用账号密码：

```env
TAKEALOT_API_KEY=在这里粘贴真实Key
TAKEALOT_DATABASE_URL=mysql+pymysql://takealot_app:密码@127.0.0.1:3306/takealot_ops?charset=utf8mb4
```

密码中的 `+`、`@`、`:` 等特殊字符必须使用 URL 百分号编码。程序会自动读取 `D:\南非店铺数据抓取\.env`，已经存在的系统环境变量优先于 `.env`。不要把真实 Key 或数据库密码写进 `.env.example`，也不要把 `.env` 发给他人或提交到 GitHub。

旧 SQLite 数据只作为迁移源和回退留档，不再被 ERP、采集或日报读取。首次切换时，MySQL 目标库必须为空，然后执行：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli migrate-to-mysql
```

迁移器会复制全部业务表并逐表核对行数；目标库已有数据时会拒绝执行，避免覆盖或重复导入。

## 3. 首次采集与检查

采集当前 Offer 和最近七个南非标准时间（SAST）自然日的 Sales：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli collect
```

也可以指定销售日期范围：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli collect --start 2026-07-01 --end 2026-07-21
```

检查数据库完整性和当天数据质量：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli verify
```

如果出现未知销售状态，命令会返回非零状态。先在 `config/sale_status_rules.yaml` 中确认该状态应计入还是排除，再重新计算。

## 4. 本地看板

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli dashboard
```

首次启动后，管理员必须先在服务器电脑上打开 `http://127.0.0.1:8501`，创建首个管理员账号；这个初始化入口会拒绝其他局域网电脑，避免同事抢先注册管理员。密码至少8个字符，只以带随机盐的 scrypt 哈希保存到本机 MySQL。

初始化完成后，同事可打开 `http://服务器局域网IP:8501` 登录。服务器 IP 可在 PowerShell 执行 `ipconfig` 查看 IPv4 地址。正式 ERP 监听 `0.0.0.0:8501`，但 MySQL 仍只连接本机 `127.0.0.1`，数据库端口不会提供给局域网。当前方案适用于同一受信任局域网，不应把 `8501` 直接映射到公网；如需跨网络或公网访问，应增加 HTTPS 反向代理和网络访问控制。

权限分为三级：

- 查看员（`viewer`）：查看页面和下载已有文件，不能刷新、采集、上传或生成；
- 运营员（`operator`）：拥有查看权限，并可刷新店铺数据、采集竞品、生成报表和 NFT102；
- 管理员（`admin`）：拥有运营权限，并可在“用户权限”页面创建、停用账号、调整角色和重置密码。

权限由后端接口强制执行，不只是隐藏前端按钮。会话保存在可撤销的 HttpOnly Cookie 中，12小时过期，写操作需要 CSRF 校验；连续登录失败会被短时限流。浏览、筛选和切换页面时使用 MySQL 只读事务，不调用平台 API，因此查看已有历史数据不需要 API Key。

侧边栏会显示“最近采集”和“最新指标”，用于判断当前看到的数据是否已经更新。“最近采集”以及竞品历史快照的时间固定按北京时间（Asia/Shanghai）显示，不跟随浏览器或南非平台时区；“最新指标”仍是既定的 SAST 业务日期。需要立即更新时，可点击“刷新全部数据”；该按钮会调用项目根目录 `.env` 中的 API Key，完成带分层重试的只读采集、指标重建、日报导出、完整性检查和备份，并把这次结果冻结为当前 10:00 核对周期的独立“手动刷新”版本。普通运营账号共享全局1小时冷却：任何账号成功刷新后，所有非管理员页面都会同步显示刷新人和剩余倒计时，冷却结束前不能再次刷新；管理员可以越过冷却，但不能和一场正在执行的刷新并发。冷却记录保存在 MySQL，服务重启后仍有效；失败刷新不开始冷却。失败时可查看 `logs\takealot-ops.log`，失败原因也会进入日报运行记录，页面不会显示或记录 API Key。

“经营四象限”使用商品最新的近30天浏览量和截至最新指标日的近7个自然日下单件数。图上横纵坐标显示商品在店铺内的相对位置，避免少数极端商品把其余点挤在一起；切换宽松、标准或严格分组时，十字分界线和中心交点会使用接口返回的实际分位排名同步移动。横轴固定为“近30天浏览量相对排名”，纵轴固定为直立竖排的“近7日下单件数相对排名”，两个方向都显示0、25、50、75、100关键排名刻度；竖向分界线明确标注“浏览量分界 + 真实值”，横向分界线明确标注“下单分界 + 真实值”。四类散点使用固定高对比色，其中“待优化”散点与对应文字统一为棕色。鼠标移到商品点上会立即出现 ERP 样式的信息卡，显示商品名称、平台 SKU、库存、近30天浏览量、近7日下单、首次上架/最早记录、最近补货时间和数据截止日期；信息卡会按点位自动向上或向下展开，不会被图框裁切，字段标题使用高对比样式。点击小点会直接复制平台 SKU 并显示结果反馈。销量为0始终放在低销量侧，缺失数据保持未分类。单品分析和店铺总览的每日下单件数图只显示真实整数件数，不再绘制可能产生小数的移动平均线。

Offers 接口提供 `created_at` 时，“首次上架”使用该平台时间；旧历史没有该字段时明确标为“本库最早记录”，不会伪装成平台真实上架时间。系统逐条比较同一商品的有效平台库存快照：后一条库存高于前一条时，后一条快照的实际采集时间就是“最近补货时间”，同时显示较前次增加数量；该时间按北京时间展示，不属于估算。没有观察到库存增加时显示暂无记录。Offers 接口只明确返回近30天滚动浏览量，没有独立的近7日流量字段，因此四象限接口和悬浮卡不再推算或展示近7日流量，只展示平台原值“近30天浏览量”。

“报表工作台”提供“生成全部报表”按钮，按顶部选择的截止日期从现有本地数据生成离线网页、电子表格和图片。生成过程不重新采集、不调用平台接口；完成后可在页面分别下载三个文件。若所选日期已经存在日报，页面会直接显示现有文件的下载按钮，再次导出会按当前本地指标重新生成同名日报。

异常口径默认以“最新指标日”为准：看板总览、Excel 总览和 HTML 总览都统计该日出现异常的去重商品数；异常明细保留同一商品在当天触发的每一种异常，因此明细记录条数可能大于异常商品数。看板“异常商品”页默认仅显示最新指标日，可切换“全部历史”追溯旧记录；Excel、HTML 和 PNG 日报默认只输出最新指标日异常，不混入历史日期。

### 4.1 竞品观察

“竞品雷达”是统一 Vue ERP 的一个正式模块，与经营总览等页面共用 `8501` 地址和同一份 MySQL，不再通过 Streamlit 嵌入或单独启动第二个端口。

平台当前会拒绝原来的普通 HTTP 公开接口请求，因此竞品商品、变体和评论改由 Playwright 启动本机 Chrome/Edge 导航公开 JSON 地址；库存仍在另一个隔离匿名购物车会话中探测。命令行批量采集会复用同一个公开数据浏览器会话；ERP 页面逐条请求时，每条链接使用独立且必须完整关闭的浏览器生命周期，避免一个商品的页面状态污染下一商品。

竞品中心支持一次粘贴多条 Takealot 商品链接，每行一条，按 PLID 自动去重。当前最小闭环会：

- 读取公开商品标题、评分和全部公开评论，并枚举尺寸、颜色、左右款等全部变体；
- 按 4–5 星、3 星、1–2 星固定口径汇总好评、中评和差评；
- 可选在同一个隔离浏览器会话中逐个变体加入购物车，记录每个变体的 SKU、卖家、价格和可售上限，并在结束后清空测试购物车；
- 保存商品历史快照、变体库存明细和按 PLID 去重的共享评论；
- 从第二次可比快照开始，展示库存净流出、新增评论和观察期销量信号。

库存不是 Takealot 全平台物理总库存，而是采集时每个变体在当前匿名会话、当前卖家和当前 SKU 下的平台仓购物车可售上限。尺寸、颜色等选择器会被组合枚举，页面“各变体库存”逐行展示；当前不可加入购物车的变体直接显示“没货”。无论提示出现在快捷数量还是自定义数量校验中，只要页面出现 `current stock = N` 明确警告，程序就立即把 `N` 保存为精确平台仓库存并停止该变体的所有后续数量尝试。确认 9 件可加入后会先验证 10 件；平台提示 `We currently do not have 10 in stock.` 或明确拒绝 10 件时记录为精确 9 件，程序也会在输入框未出现时继续读取页面弹窗。若只是 `10+` 输入框打不开/无法完成输入，且没有明确缺少 10 件的提示，则仍保守显示“至少 9 件”。只有 10 件明确被接受才继续超量测试和二分校验。首次打开数量菜单时会等待动画并最多重开3次；仍读不到数字选项就刷新购物车一次、重新核对同一 PLID 后再试，避免页面慢加载造成偶发“未探测”。数量控件显示更新成功后会留出短暂提示结算窗口，避免平台警告稍晚出现时被误判为已接受。只有999件仍被接受或后续页面拒绝继续验证时才显示保守下限。探测会等待异步加购落库、重试数量菜单动画和临时购物车更新错误，并只把 `aria-hidden` 未启用的数量输入框视为可编辑控件；Braze 营销遮罩只在阻挡目标控件时被清理。本次最终仍未探测成功时，当前库存继续为空；页面只在 SKU、卖家和变体集合一致时显示“上次成功库存 + 时间”的过期参考，该值不会回填当前库存，也不参与库存净流出和销量计算。公开接口标记为 `is_leadtime` 的供应商调货/长时效到货变体不计入有效平台仓库存，统一显示“没货”，也不参与库存净流出销量推断。评论属于 PLID 商品维度，所有变体共用同一份评论，不重复抓取或计数。竞品页面不展示基于评论率反推的累计销量估算；库存变化和观察期评论信号也不是官方销量，补货、购物车占用、取消和评论延迟都可能影响判断。

竞品详情的“公开评论”支持把好评/中评/差评与起止日期组合筛选，并可按最新评论、最早评论、评分从高到低或评分从低到高排序；页面会显示筛选后的评论数和该商品评论总数。没有评论日期的记录在未设置时间范围时保留，设置时间范围后不纳入结果。

库存探测严格以输入链接中的 PLID 为目标：程序只点击该商品页右侧主购买区的 `Add to Cart`，不会点击“You Might Also Like”“What’s Hot”等推荐商品。跳转购物车后还会再次核对目标 PLID；找不到目标商品就让本条库存探测失败并清空购物车，不会拿其他商品的库存冒充竞品库存。

大量链接首次建档时，可在页面关闭库存探测，先快速采集公开商品与评论；后续再分时补充库存。单个链接失败不会中断整批。

竞品最新状态表顶部提供组合筛选器：关键词可匹配商品名称、PLID或当前卖家，并可叠加“有货 / 没货 / 未探测”库存状态和动态经营信号。页面实时显示筛选结果数与商品总数，支持一键清除；本次库存未探测、仅显示上次成功过期参考的商品归入“未探测”。这些筛选只处理当前已经读取的列表，不会重新采集平台或写入数据库。

竞品最新状态表支持直接点击商品打开完整详情弹窗，无需滚动到页面底部。弹窗集中展示价格、当前库存与上次成功参考、经营信号、评论结构、各变体的 SKU/卖家/价格/库存与探测说明、库存及评论历史快照，并完整提供评论分类、起止日期组合筛选、日期或评分排序和评论全文。商品详情不再重复铺在最新状态表下方；长内容只在弹窗内部滚动，顶部商品标题和底部“打开 Takealot 商品页 / 关闭”操作保持可见。

梯子或代理短时不稳定时，公开数据浏览器启动会自动重试；无论预热失败、请求取消还是页面超时，程序都会强制关闭页面上下文、Chrome 和 Playwright 驱动，不允许遗留后台浏览器进程。只有真实导航失败、429 或 Takealot 5xx 才归入连接类错误；页面内容暂时无法判定会单独保留重试，不会累计断网次数。批量页面连续两条出现真实连接或 Takealot 临时服务错误时会暂停剩余链接，保留此前已成功写入的数据和当前进度，避免断网期间继续空跑全部链接。恢复网络后可重新提交失败链接。

商品公开数据单次返回 404 时不会删除链接，也不会直接当成永久失效。系统会在同一个 Playwright 浏览器中同时检查目标商品页和最近成功采集的已知正常商品：Takealot 的 `404, Page Not found` 标题或正文会被明确识别为不存在页面，不能因为404页自身也有标题就误认成商品；正常商品则使用商品标题和页面商品内容识别，不依赖单个可见标题在固定8秒内出现。如果对照或目标内容暂时无法稳定判定，本次单独标记“页面复核结果不确定”并保留重试，不计入连接失败；只有目标明确为404页且正常对照可打开，才记录一次有效的“疑似失效”。至少间隔10分钟累计3次有效复核后才转为“确认失效”，任意一次后续采集成功都会把状态重置为正常。竞品雷达的“链接复核状态”会展示疑似/确认状态、复核次数、对照 PLID 和最近检查时间，方便运营审计。

每次点击“开始采集”都会建立一个独立批次，并把原始链接顺序、已检查位置、失败位置、已确认失效位置、成功 PLID、运行状态和当前链接请求编号保存到当前浏览器的本地断点。采集中整页刷新或前端重新加载时，ERP 会自动回到竞品雷达并从当前链接恢复，不需要再次点击“继续”；服务进程仍在时，恢复请求会复用同一请求编号和同一后台探测任务，不会把正在执行的商品重复爬取。人工点击停止、连续连接失败暂停和已经正常结束的批次不会自动启动。切换模块或 ERP 服务重启后，只要链接列表及 PLID 顺序没有改变，“继续失败/未完成”仍可从本批最早失败项往后恢复：此前成功的商品即使穿插在失败项后面也会直接跳过，只重试疑似失效、其他失败项和尚未执行项；已确认失效链接在本批后续续爬中自动跳过。这里的跳过仅依据当前批次成功/确认失效记录，不会因为数据库中存在昨天的快照而跳过今天的新采集；需要人工重新检查全部链接时点击“开始采集”建立新批次，确认失效链接也会再次进入检查。

服务端把每个批次的开始、手动/自动恢复、暂停、人工停止、完成，以及每条链接的开始、结果、请求复用和异常写入 `logs\competitor-collection.log`。日志按大小轮转，方便以后区分是页面刷新、人工操作、网络暂停还是具体 PLID 异常；日志不记录账号密码和会话密钥。

点击“开始采集”后，页面会先逐行检查链接格式、Takealot 域名和 PLID，不会把其他平台链接送入采集流程。发现错误时会自动回到并选中第一个问题链接，输入框红色闪烁，下方按“第几行 / 具体原因 / 完整链接”显示编译器式诊断；修改输入后提示自动清除，再次点击即可重新校验。

竞品采集开始后可以切换到其他 ERP 页面；竞品雷达页面会保持采集实例，返回后继续显示原输入、完成数量、进度条、成功结果和失败说明，不会因为导航切换而清空。

竞品批量采集同一时间只允许一个账号、一个浏览器标签页运行。当前操作者、已检查/总数、成功、失败、待续爬以及正在处理的 PLID 会由服务器同步到所有用户的竞品雷达页面；其他用户的输入和开始按钮在占用期间不可用，直接绕过前端请求也会被后端拒绝。同一账号打开其他标签页也不会启动第二批。人工停止时，系统会先等待当前商品的 Playwright 浏览器探测完成清理，再释放给下一位运营。

当前交付是最小模块。原独立工具中的关键词/类目排名、卖家上新、Buy Box 历史占有率和六工作表 Excel 尚未迁入；这些信号不会在当前页面中伪装成已支持。

## 6. 每日完整运行

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli daily-run
```

执行顺序为：完整分页采集 → 七个 SAST 自然日指标重建 → 数据质量检查 → 报表导出 → MySQL 表完整性检查 → `mysqldump` 一致性备份。任何分页失败都不会发布不完整快照或报表。日志写入 `logs\takealot-ops.log`，不会记录 API Key 或数据库密码。

### 运营日报的周期版本

运营日报不会让后一次采集覆盖前一次值。核对周期固定为北京时间当日 10:00（含）至次日 10:00（不含），周期内全部定时采集和右上角手动刷新都归入同一个日报业务日并逐次保存。例如 7 月 25 日 10:00 至 7 月 26 日 09:59 的所有版本都归入 7 月 24 日日报。三个计划阶段分别运行：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli daily-report-run --slot morning
.\.venv\Scripts\python.exe -m takealot_ops.cli daily-report-run --slot evening
.\.venv\Scripts\python.exe -m takealot_ops.cli daily-report-deadline
```

- 每个自然日 10:05 首次成功采集的平台仓可售库存会按实际北京时间日期冻结到独立的 `daily_inventory_snapshots`，作为该日唯一的系统库存值。次日核对该业务日时，只读取这份 10:05 快照；次日 10:05、18:00 和手动刷新取得的实时库存仅按各自实际日期留存，绝不回写成前一日库存。
- 早间、晚间和周期内全部手动版本继续分别保存前一业务日订单与近30天浏览量，但版本核对只比较当天订单数（销量）。任意两个成功版本的非空销量不同就进入待办；销量一致时不推送版本待办，库存变化和浏览量变化都不参与版本冲突。
- 每次成功点击右上角“刷新全部数据”都会在完成完整采集后增加一个不可覆盖的手动刷新版本；同一周期允许存在多个手动版本，但普通运营账号受全局1小时冷却限制，管理员可按需越过冷却。
- 普通 HTML、Excel、PNG 日报也使用该前一业务日作为文件日期和数据截止日期；采集仍会重拉截至执行日的最近7个 SAST 自然日，以补回平台延迟订单。
- 每次早间/晚间任务都有分层保护：单个 HTTP 请求会重试网络超时、429和5xx；整批采集失败后依次使用新会话重试和忽略异常系统代理的直连备用；Windows任务仍失败时每5分钟重启，最多3次。只有 Offers 与 Sales 都完整返回才允许冻结日报，禁止把旧缓存伪装成当次成功数据。
- 每次整批尝试的序号、策略、开始/结束时间、阶段状态、脱敏失败分类和最终根因会同时写入 `logs/takealot-ops.log` 与日报运行记录；页面“采集保护与重试记录”可直接查看。所有路径耗尽后才标记漏爬，并明确区分鉴权拒绝、限流、网络/DNS/TLS/代理、接口异常响应和本地流程异常。
- 商品只有在本周期最终采用值的当天订单数或平台库存为空时才标记“漏爬”；近30天浏览量为空不算漏爬，某次采集失败或商品缺席但订单与库存已由其他成功版本补齐时也不打商品漏爬标识。漏爬不算冲突、不要求人工确认，也不阻止导出。所有定时/手动采集失败、商品缺席和字段空值的脱敏原因仍持久化到运行日志，并进入 Excel“漏爬说明”供追查。
- 近30天浏览量保留全部采集版本、底层存储和页面/Excel 展示，但不参与冲突判断。同一 10:00 核对周期内，只比较各成功版本的当天订单数；任意非空销量不同就进入“同周期销量版本差异”待办，即使最后一次又恢复为较早数值，中间差异也不会被覆盖。销量一致的商品不推送版本待办，自动采用最新非空销量；库存始终采用业务日当天10:05固定快照。运营员和管理员可选择本周期最新拉取值、早间值、晚间值或人工候选值确认有差异的销量版本，确认及人工修改必须填写备注。人工候选值可以反复修改，第二次打开会回填上次候选值、原因和备注；每次保存都追加修改前后值的审计，不覆盖历史。
- 库存连续性只在相邻两个日报日都已经取得稳定正确值后计算：某一方仍有未确认的同周期版本差异时，只保留该日期的版本差异待办，跨日公式暂缓。版本确认后系统立即用确认值重算；仍不相符才继续推送独立的“前后日报日库存连续性”待办。若库存待办存在期间又出现新版本差异，则先切回版本差异待办；已经有人工确认基线时，只对比“上次人工确认值”和确认后的新拉取/人工候选，旧的已处理版本只保留审计、不再混入本次证据。重新确认后再用新的确认值计算库存连续性。
- 库存连续性待办只展示前一日报日正确库存、当前日报日正确订单/库存和跨日公式；同周期版本待办只展示本次待确认的版本值。运营可填写原因把库存异常确认为“差异属实”，该动作只关闭待办，日报矩阵、库存异常筛选、顶部异常统计和 Excel 库存单元格仍保留红标；“确认合并”只处理版本选择，不能顺带关闭库存连续性问题。
- 待办卡不会再统一显示“数据有差异”：同周期销量不一致显示“销量版本有差异”，跨日报日公式不平显示“前后日报库存不平”。如果问题由既有人工确认之后的新销量版本或连续性传播触发，标识会明确增加“确认后”或“人工确认后”，版本问题和库存问题使用不同颜色。
- “单独加备注”不会确认、关闭或改变待办。运营员和管理员都可以新增、修改、删除备注，并按通用备注、同周期版本差异或库存连续性关联展示；新增、修改、删除都会追加审计，保留创建人、修改人、中国时间和修改前后内容。删除只从当前有效备注中移除，不会删除审计历史。确认合并时填写的确认备注会自动显示为“（确认：备注内容）”；如果确认合并后库存公式仍不平并继续确认差异，差异备注同时显示为“（库存差异已确认：备注内容）”。两条备注并列写入页面与 Excel 的同一备注单元格。撤销相应确认后只移除对应的当前有效备注，历史仍保留在审计中。
- 人工确认合并后会立即重新计算下一日报日的库存连续性。如果确认前公式成立、确认后的前一日库存却让下一日报日出现新冲突，下一日报日会自动重新进入待办；运营继续确认该待办时，系统再向后一日报日检查，形成可连续传播的核对链。待办卡明确标注“由前一日人工确认合并触发”，并展示触发日期、确认来源、操作人、北京时间、备注、确认前后公式、当前实际库存以及所有相关采集版本的订单和库存。
- 已确认商品可从日期备注行的“备注与确认记录”撤销本次确认。撤销必须填写原因，系统不会删除原确认，而是追加“撤销确认”审计、清空当前最终值并恢复为“已撤销确认待重核”；同日需要重新选择正确版本。若撤销影响下一日报日的库存连续性，下一日报日同时保留“撤销确认后库存待重算”待办，展示原确认值、撤销人/时间/原因、当前订单、实际库存和撤销前公式；前一日重新确认后立即按新正确值重算，仍不平则转成真实库存连续性待办，恢复正确则自动解除。
- 18:30 仍未合并的数据会形成持久待办快照。次日仍正常采集；库存连续性使用各业务日当天10:05固定库存，不使用次日实时库存回填，历史待办会在 ERP 全局持续提醒。
- 页面不再提供“日报业务日期”选择器，固定按北京时间 10:00 边界自动读取当前核对周期对应的日报日。页面和 Excel 主表保留原工作表的商品横向布局；页面加载最近30个有数据业务日，每个日期固定显示“近30天浏览量、当天订单数、平台库存数量（当日10:05）、备注”四行，表格内部可上下滚动且一次最多完整显示5日，打开时自动定位最新日期。备注行按“（通用/版本/库存：备注内容）”显示在对应商品列，可点击管理该商品当天的全部备注。“当天访客数”字段已完全移除，不能用30天滚动窗口差值伪造。
- 日报下方的“待办处理留痕”集中列出已经执行的确认合并和库存差异确认，展示商品、平台SKU、日报日、采用来源或库存公式、处理人、北京时间、备注以及后续撤销结果。可按北京时间“处理日期”和日报“数据日期”独立或组合筛选，并随时清除筛选恢复全部记录。当前仍有效的记录可从这里直接撤销：撤销库存差异确认后，若公式仍不平，原库存待办会自动恢复；原处理和撤销记录都只追加、不删除，便于误操作后查找和还原。即使商品后来不在当前商品表中，留痕也会从当时的采集快照恢复商品名和平台SKU。
- 只要截止日期及之前存在未处理的销量版本差异或库存连续性异常，运营日报 Excel 就拒绝导出并返回具体日期和 SKU；漏爬不会阻断。最后一项待办确认完成时会自动导出到 `exports\operations-daily\YYYY-MM-DD\`。

如果只需用当前数据库做演练、不访问平台，可运行：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli daily-report-capture --slot morning --date 2026-07-24
```

## 7. 安装 Windows 每日计划任务

安装脚本本身不会自动运行；只有运营人员明确执行后才会创建计划任务。默认按中国时间建立三个互不覆盖的任务：`10:05` 早间采集前一业务日、`18:00` 晚间复核同一业务日、`18:30` 未合并快照/自动导出。错过触发时间后会尽快补跑，并忽略并发重复实例：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\install_scheduled_task.ps1 `
  -ProjectPath 'D:\南非店铺数据抓取' `
  -MorningAt '10:05' `
  -EveningAt '18:00' `
  -DeadlineAt '18:30'
```

计划任务使用项目自己的 `.venv`，工作目录固定为项目根目录；不会改变 ERP 的局域网监听地址。

当前不增加 09:50 正式采集：Takealot Sales 接口支持按 SAST 日期范围重复查询，项目每次会重拉最近7个业务日并按订单行更新，因此10点后仍能补回前一日数据；09:50 反而更容易取得尚未完全入账的早期版本。若后续连续日志证明平台会删除历史订单，再增加“仅存原始响应、不参与最终值”的09:50保险快照，而不是把它混入早晚确认口径。

## 8. 备份与恢复

每次 `daily-run` 会通过 `mysqldump --single-transaction` 在 `backups\` 中生成一致性 `.sql` 备份，只保留最新 8 份。

恢复步骤：

1. 停止正在运行的看板和每日任务。
2. 在 MySQL Workbench 中备份或清空目标 `takealot_ops` 数据库。
3. 使用 Workbench 的 Data Import 导入选定的 `backups\takealot-*.sql`。
4. 运行 `.\.venv\Scripts\python.exe -m takealot_ops.cli verify`。
5. 验证通过后再启动看板和每日任务。

## 9. 流量指标口径

`page_views_30_days` 只能称为“近30天浏览量”；不得将其或每日快照差值标注为精确日流量或访客数。

“近30天日均浏览量”只是滚动窗口值除以 30；“30天浏览量窗口净变化”只是相邻快照的窗口差值。缺失值保持为空，不补零。

## 10. MySQL 运行边界

- 正式运行只使用本机 MySQL 8.0、`mysql+pymysql` 同步驱动和 `utf8mb4` 字符集。
- ERP 查询连接执行数据库级只读事务；采集、指标重建和竞品刷新使用单独的可写连接。
- 应用账号只授予 `takealot_ops` 数据库所需权限，不使用 root 启动 ERP。
- 每日运行执行 MySQL `CHECK TABLE` 并生成 `mysqldump` 备份。
- `data\takealot.db` 仅保留为迁移完成前的数据留档，不再是运行数据源，也不会自动回退。

## 11. 一键更新 NFT102 访客表

推荐从统一 ERP 的“`报表工作台` → `NFT102 续写`”页面操作：

1. 运营同事完成当天备注并保存 Excel；
2. 在页面上传这份最终版 `.xlsx`；
3. 页面自动识别表内最新日报日期，并默认选择连续下一天；
4. 点击“保存基准并生成下一日表格”；
5. 生成完成后直接下载新表格和运营核对说明。

上传文件会按内容哈希原样存档到 `data\nft102-baselines\`，不会被覆盖。新 Excel 和核对报告仍输出到 `outputs\nft102-daily\YYYY-MM-DD\`。程序只在点击生成按钮后调用只读 Takealot API；运营填写的内容、批注、图片和其他工作表继续沿用上传版本。

连续上传前一天生成的文件时，输出文件名会替换旧的 `_NFT102_日期` 后缀，不会每天叠加日期导致文件名越来越长。

中国时间每天 10:00 左右是平台销量切日窗口，建议 10:05 后执行。若需要保留原命令行方式，仍可双击项目根目录的 `更新NFT102日报.bat`；该方式会自动寻找本机最新模板，而网页方式始终以本次明确上传的运营最终版为准。

看板固定使用中文界面：导航、按钮、上传提示、字段名、商品状态、异常说明以及图表和表格工具控件均不显示英文。平台返回的商品原始名称、店铺代码、商品编码和南非货币符号属于真实业务数据，保持平台原值，不做猜测性翻译。网页上传上限为100兆字节。

填写口径：

- 表格日期使用当天日期；“当天订单数”使用前一天完整的 Sales quantity。
- “访客总数”填写 `page_views_30_days`，含义是近30天滚动浏览量。
- 接口不提供精确“当天访客数”，因此续写旧模板时该行留空；运营日报页面和导出表不再展示该字段。
- “平台库存数量”填写 Takealot 各地区 `quantity_available` 合计；收货中和在途库存不计入可售库存。
- 仅按表头中的完整 13 位 SKU 自动匹配；无法识别、无法匹配和重复旧列会留空并写入核对报告。

每次会同时生成 `.核对报告.txt`（供运营查看）和 `.核对报告.json`（供程序审计）。
