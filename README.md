# Takealot 店铺运营数据工具

这是一个在 Windows 本机运行的小型运营 ERP：通过只读 Seller API 采集自有店铺 Offer、Sales、Returns 与 Shipment 数据，通过长睿 W8 客户接口读取仓配数据，并通过公开商品接口和隔离匿名购物车观察竞品。统一的 Vue 3 + TypeScript 前端包含经营总览、商品中心、关键词流量、搜索定位、经营坐标、异常商品、退货管理、物流管理、竞品雷达和用户权限，共10个模块；自有店铺和竞品历史统一保存在本机 MySQL 8.0。约平台仓、NFT102、旧风险/质量与运营日报的后台能力仍保留，但不再作为前端模块展示。

## 1. 安装

在 PowerShell 中进入项目目录：

```powershell
Set-Location -LiteralPath 'D:\南非店铺数据抓取'
uv venv --python 3.11 .venv
uv pip install --python .\.venv\Scripts\python.exe -e ".[dev]"
.\.venv\Scripts\python.exe -m playwright install chromium
```

检查命令是否已安装：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli --help
```

## 2. 配置 API Key 与 MySQL

复制模板，生成项目根目录下的 `.env` 文件：

```powershell
Copy-Item .env.example .env
notepad .env
```

单店可继续只填写 `TAKEALOT_API_KEY`。多店铺使用非敏感注册表把店铺代码、显示名称和密钥环境变量对应起来；真实密钥仍各自单独保存，并把 MySQL 密码替换为本机应用账号密码：

```env
TAKEALOT_API_KEY=在这里粘贴真实Key
TAKEALOT_STORE_02_API_KEY=在这里粘贴第2家店真实Key
TAKEALOT_STORES=current|官方店铺显示名A|TAKEALOT_API_KEY;store-02|官方店铺显示名B|TAKEALOT_STORE_02_API_KEY
TAKEALOT_DATABASE_URL=mysql+pymysql://takealot_app:密码@127.0.0.1:3306/takealot_ops?charset=utf8mb4
```

密码中的 `+`、`@`、`:` 等特殊字符必须使用 URL 百分号编码。程序会自动读取 `D:\南非店铺数据抓取\.env`，已经存在的系统环境变量优先于 `.env`。不要把真实 Key 或数据库密码写进 `.env.example`，也不要把 `.env` 发给他人或提交到 GitHub。

物流管理还需要在同一个被 Git 忽略的 `.env` 中配置长睿提供的 W8 授权码。当前正式服务商域名是 `crgyl.w8soft.net`，测试域名与正式域名不是同一租户；不要把正式授权码写进测试地址。

```env
W8_API_TOKEN=在这里粘贴长睿提供的授权码
W8_BASE_URL=https://crgyl.w8soft.net/prod-api/w8
```

“搜索定位”默认使用火山方舟豆包Seed 2.0 Lite，阿里云百炼千问作为跨厂商备用。真实 Key 可放在被 Git 忽略的 `.env`，也可保存为 Windows 用户级 `DASHSCOPE_API_KEY` 和 `ARK_API_KEY`；正式重启脚本只在当前进程缺少对应变量时按这两个固定名称补载，不覆盖已经显式提供的进程变量，也不输出或写入 Key 值。普通打开页面、切店、筛选和查看历史只读 MySQL，不调用模型或 Takealot。只有拥有“调用多模态模型并采集搜索定位”权限的用户点击“识别图片并定位”才产生模型请求和受控公开搜索：

```env
DASHSCOPE_API_KEY=在这里粘贴阿里云百炼Key
TAKEALOT_SEARCH_QWEN_MODEL=qwen3.7-plus
ARK_API_KEY=在这里粘贴火山方舟Key
TAKEALOT_SEARCH_DOUBAO_MODEL=doubao-seed-2-0-lite-260215
TAKEALOT_SEARCH_MAX_PAGES=5
TAKEALOT_SEARCH_MAX_KEYWORDS=14
TAKEALOT_SEARCH_PAGE_DELAY_SECONDS=3.0
TAKEALOT_SEARCH_PAGE_DELAY_JITTER_SECONDS=2.0
TAKEALOT_SEARCH_OFFER_MAX_AGE_HOURS=36
TAKEALOT_SEARCH_IMAGE_MAX_DIMENSION=640
```

> 2026-08-18 当前精简查询口径：新图文融合结果固定生成6至10个真实买家会输入的短查询，每个只允许2至4个英文单词，其中至少4个不得超过3词；`cat litter box`、`cat storage box`这类完整商品短语优先，颜色、规格、SEO式功能串和连续`with/and`描述不得占用直接搜索位。这里历史文档中的“完整搜索词”只表示完整商品意图，不再表示长尾句。Takealot返回的相关扩展若超过4词，只保留原始顺序与相关性审计，不进入搜索页、不继续作词根；主标题直验、人工决策参数、偏差页补救和历史同词复采也统一受4词上限约束。`box`、`case`、`light`、`stand`、`device`等宽泛单词不能单独成为同品别名或搜索词；平台原始`boxes`仍可留档，但不能因同页多为本商品就冒充精准词。提示版本已升级，旧版长词缓存不会复用于新分析；历史分析仍按原证据只读展示。

每次新分析先执行彼此隔离的两个模型阶段。第一阶段只接收最长边640像素的可信主图，不接收主标题、SKU或人工事实，输出可见物理形态和图片观察；服务器随后把这份独立观察与当前官方主标题做确定性交叉验证，但差异大只显示提醒，不再切换供应商、压低置信度或阻断分析。第二阶段再把同一主图、当前主标题、独立图片观察和交叉验证摘要一并交给模型，至少生成6个图文融合第一直觉词/词组和6个完整搜索词。两个模型阶段的所有生成文本字段都必须显式回传`South Africa`、`South African English`和`South African local customer habits`三项固定地域契约；缺失或改成泛美国/英国语境会按结构化输出无效处理。该契约保证预测时采用南非本地客户习惯和南非英语语境，但不把模型预测冒充平台实测搜索量、热度或真实客户调查；视觉事实仍只能来自图片，地域语境不能补造不可见事实。模型若明确指出图片与标题都无法确认的关键商品事实，批次会把该商品记为“待人工事实”并直接跳过，不发Takealot根词扩展或搜索请求；人工确认入口对每个已分析商品都可选使用，但不强制。相同主图、相同当前主标题、实际模型链和提示版本才可复用完整双阶段结果；本次提示版本已升级，旧版未声明南非地域契约的缓存不会复用于新分析。两个阶段及失败供应商返回的所有可计量usage都会合计入本轮Token与费用，结构校验失败的响应即使有usage也不能缓存。默认单商品最多验证14个搜索词、每词5页；未发起请求的候选显示“未验证”，不会把占位0冒充实测同类率0%。按2026-08-11[火山方舟官方价目](https://www.volcengine.com/docs/84458/1585097)与[阿里云百炼官方价目](https://help.aliyun.com/zh/model-studio/model-pricing)，豆包Seed 2.0 Lite在当前小于32K输入档为每百万输入Token 0.6元、每百万输出Token 3.6元；千问`qwen3.7-plus`备用按配置中的标准价每百万输入2元、输出8元估算，供应商限时折扣或账号地域以控制台账单为准。页面批次预览会按当前授权店铺、标题相关缓存、同批同图同标题复用和历史Token重新计算基准、常见区间及保守上界，实际账单仍以供应商返回Token及当时价格为准。Key不会进入页面、数据库、日志或错误响应。

单商品日常操作仍是选择一个自有在售商品并点击一次；另提供当前账号全部可访问、已启用且已接入店铺的批次预览，运营确认商品数、Token、人民币和时长估算后才冻结队列并一键启动。批次不会把店铺数量写死为六家，服务端始终按登录账号授权动态取范围；全局最大并发固定为1，运行期间单商品分析不能插队。页面约每2.5秒同步进度，并提供暂停、恢复、停止和“从第一个商品重新开始”；重新开始会生成新批次ID并重新计费，不覆盖旧审计。资格轮到时失效或模型明确要求关键人工事实会跳过，后者不发平台请求；模型、网络或平台异常在当前项后暂停，失败商品不自动重试。检查点、逐项结果、实际Token和费用写入Git忽略的`logs/search-ranking-batch.json`，ERP重启后必须人工恢复。

一次商品分析最多使用14个查询位：6个由图文融合模型直接生成的南非完整搜索词、6个词根相关核心位、1个真实扩展的相邻需求探针，以及在核心平台词根不足时才启用的1个补救位。6个词根相关核心位通常由不同第一直觉入口的Takealot真实根词扩展占用；若主标题中的完整商品词组没有补全词，或平台返回项全部未通过同品相关性筛选，最多拿出其中1位直接搜索该完整标题词组，不额外扩容。该来源明确标记为“主标题完整词组直验”，不能冒充平台补全、平台热词或搜索量。第一直觉词/词根可以是单词，也可以是2至5词的完整商品词组；模型可直接生成`lazy sofa`、`floor chair`等词组，主标题拆词也优先保留已出现的商品词组，再保留少量单词作为发现入口，不会把`compressed sofa`强行截成`compressed`。服务器先观察最多14个核心根词和1个相邻需求根词，再在总计最多20个根词观察内，把最多4个已通过相关性闸门的平台多词扩展继续作为词组词根观察一层。模型直生成词不会冒充平台扩展或搜索量，平台扩展也不由模型猜造；同一文案同时命中两种来源时保留双证据。标题连续版优先完整首页验证通过的图文融合长尾，类目覆盖版只使用通过商品相关性筛选的真实平台扩展并优先不同词根，蓝海版继续使用严格机会门槛。

根词扩展、搜索第一页和游标翻页都通过同一个ERP实例级闸门串行排队：相邻公开请求默认至少3秒，并追加0至2秒随机抖动，即每次起始间隔为3至5秒；搜索扩展和游标端点遇到403、429或5xx时不自动重试，避免一次点击放大为连续请求。搜索第一页使用一次匿名浏览器页面导航，根词扩展和后续游标由同一空白浏览器上下文导航公开HTTPS接口；不会带Seller Portal登录态、ERP登录Cookie或用户浏览器Cookie，但平台仍可看到ERP服务器出口IP、TLS/浏览器特征及该匿名上下文自行产生的普通站点Cookie，因此风险只能降低，不能宣称为零。每次分析保存并展示实际经过节流闸门的扩展/搜索数据访问次数；该数字不包含浏览器首屏自行加载的静态资源和平台内部请求，不能冒充网络数据包总数。平台原始扩展按完整根词全店共享：首次实际命中才采集，24小时内直接复用；严格超过24小时后也不定时刷新，只有下一次真实分析再次命中该根词时才刷新一次。刷新失败时保留旧快照供审计，但不会用过期顺序生成当前标题。升级时会把既有成功分析已经保存的原始顺序和原采集时间幂等回填到共享库，不会为回填访问上游或把旧数据重新计时。页面“平台原始词根/词组扩展库”只读本机MySQL，查看不会访问Takealot；它如实展示平台原始第1至5项，因此可能仍看到`corduroy jacket`、`lazy susan`等跨商品意图，但这不代表为当前商品入选。逐商品分析会另行保存“相关/不相关、理由、是否继续作词组词根”的筛选审计；只有保留同品身份，或命中已结构化相邻需求替代商品族的扩展，才会进入搜索、评分和蓝海判断。`box`等宽泛商品尾词必须带与已识别商品族一致的上下文才算身份锚点：例如猫用品标题应优先保留`cat storage box`，不能让更宽的`storage box`或`storage boxes`仅凭`box`通过同品闸门。平台明确返回空列表时页面必须显示“本次未返回补全词”，不能留白，更不能把空结果写成热词。旧分析可能只保存`seed`、`input_state`或`shopper_root`而没有新版`root`，页面按该顺序兼容回退并在全部缺失时显示安全占位，不会因历史字段缺失使整个模块加载失败。平台第几项可作为搜索意图参考，但不是Takealot公开搜索量，系统缓存命中次数也不是买家搜索次数。

平台扩展的排除项必须按完整商品形态与正向同品身份共同判断，不能把一个多词排除项的最后一个商品名词无限扩大。例如模型排除`rigid frame sofa`时仍须拦截该完整形态，但如果模型其他商品类型或直接别名明确支持`sofa`，就不能因此把`sofas`、`sofa chair`、`lazy sofa`或`sofa bed`全部清零；`sofa cover`等配件改指向及完整排除形态继续不入选。相关性闸门判为同品的扩展也不得再被二次适配评分以相反的宽泛尾词规则静默删除。

旧 SQLite 数据只作为迁移源和回退留档，不再被 ERP、采集或日报读取。首次切换时，MySQL 目标库必须为空，然后执行：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli migrate-to-mysql
```

迁移器会复制全部业务表并逐表核对行数；目标库已有数据时会拒绝执行，避免覆盖或重复导入。

> 2026-08-12 当前口径：搜索定位的新分析已停止逐字补全路径，以上仍出现的“补全路径”“输入状态”只描述历史记录和底层Takealot接口。完整词根既可以是一个词，也可以是2至5词的有意义商品词组，并按六级来源处理：1人工确认商品事实、2图文融合模型预测、3主标题确定性拆词、4搜索结果页反向学习、5相邻需求模型词根、6图题交叉验证词；相同根词保留全部来源与原始短语，并按最高优先来源确定主归属。初始核心根词按第1、2、3、6类的相对顺序进入最多14个核心根词预算；服务器仍为当前主标题按原顺序确定性提取的最多8个有效根词保留最低覆盖，并优先保留`lazy sofa`、`sofa chair`等商品词组，再保留少量`lazy`、`sofa`等发现入口。第4类有运行依赖：必须先取得一条真实Takealot搜索结果页，才能从偏差页标题中反向学习；一旦存在合格学习种子，条件式补救会先用第4类，再以既有次优根词扩展兜底。第5类使用1个相邻需求机会根词，第6类作为最低优先交叉词参与初始核心池。模型多词种子保持为完整词组，不会再截成首词，也不会请求`lazy s`、`rgb l`等逐字里程碑。初始根词与最多4个相关多词后续根词合计最多观察20个；后续根词只扩展一层，防止无限发散。每个根词下Takealot返回的第1至5项按该入口原序保存和展示，不跨根词合并“最佳顺序”，也不直接视为入选；逐商品相关性闸门只允许同品名称/直接别名，或结构化相邻需求明确列出的替代商品族进入候选，材质、功能或空间修饰词的单点重合不够。页面“平台原始词根/词组扩展库”只读本地MySQL并隐藏历史残缺输入；`corduroy jacket`、`lazy susan`、`foldable table`、`modular psu`、`floor lamp`和`sofa cover`等原始返回会保留审计但不进入搜索。根词来源优先级或扩展顺序都不是公开搜索量、销量或蓝海结论；入选扩展仍须通过完整搜索页相关性、目标自然位、低同类竞争及事实安全门槛。`lazy sofa`可以由模型、标题词组或相关平台扩展进入验证，但不能替代尚未人工确认的`compressed sofa`商品事实。

> 同日起，词根来源可信度与搜索词语义等级完全拆开。S级表示当前商品的同品名称或直接别名，例如获得图文融合支持的`floor chair`、`lazy sofa`；如果当前官方标题连续出现`Lazy Sofa`且该短语与已验证商品主体一致，即使融合模型遗漏该别名，系统也会确定性补为S证据；`compressed sofa`这类不可从外观确认的隐藏结构词还必须已出现在当前官方标题或由运营人工确认。A级表示不同商品族解决同一买家任务，模型必须同时给出买家任务、替代商品族和排除项，并由实际第一页自然结果标题达到相邻商品至少50%、S+A合计至少70%、相邻结果至少3个才成立；配件、耗材、保护套及语义碎片统一归为C/I级不采用。来源排在第5级不会自动得到A级，第1级也不会自动得到S级，等级只由商品关系和实际结果页证据决定。蓝海是独立的第二道闸门：只有S或A、确实来自Takealot完整根词扩展、事实安全、目标自然位不晚于72且首页扣除本商品后直接同品不超过2个才成立。因此`lazy sofa`可以是“S级蓝海”，不必硬判成A级；`compressed sofa`在当前标题未声明且尚未人工确认时仍不能凭词面猜成同品。旧分析没有新等级证据时保守隐藏蓝海结论，需重新分析。

## 3. 首次采集与检查

采集当前 Offer，以及最近七个南非标准时间（SAST）自然日的 Sales 与 Returns：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli collect
```

普通 `collect` 的 Returns 使用同一个显式日期区间；日报、计划任务和右上角完整刷新则固定重拉截止日向前365个SAST自然日的 `/returns`，并展开 `outcomes` 与 `transactions`。每次运行会保存实际请求起止日，页面只有在成功批次完整覆盖当前查看区间时才显示“明细已采集”；部分覆盖、失败和从未采集都不会被解释为零退货。Returns 暂时失败不会阻断已经成功的 Sales 指标和日报，但正式状态会保留失败及最近成功明细。

```powershell

```

### 3.1 导入平台 SKU、公司 SKU 与 RMB 成本主档

下载后的产品主档通过独立 CLI 进入 MySQL。默认只预检，不写产品、映射或成本业务行；生效日期必须显式提供，财务可分别使用每月 1 日、15 日，运营临时补平台 SKU 时使用实际确认日期：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli import-product-master `
  'C:\路径\产品主档.xlsx' `
  --effective-date 2026-08-15
```

预检会输出文件 SHA-256、工作表、源行数、拆分后的平台 SKU 数、公司产品数、RMB 成本数、当前 `offer_current.sku` 命中情况、已有映射改绑和全部警告。确认无误后在同一命令追加 `--apply`；相同文件内容、工作表和生效日期再次执行会复用原批次，不重复写入。已有平台 SKU 改绑公司 SKU 默认拒绝，只有人工核对后追加 `--allow-reassignments` 才会执行，并在逐行审计中保存改绑前后值。

表头必须能明确识别“平台 SKU”“公司 SKU/自编 sku”“产品/中文品名”；RMB 单件成本列可使用“成本（RMB）”“单件成本（RMB）”“采购成本（RMB）”等明确名称。普通“采购费用”可能是月度合计，系统故意不把它猜成单件成本。一个单元格中的多个平台 SKU 可用换行、逗号或分号分隔；同一批次出现平台 SKU 改指不同公司 SKU、公司 SKU 对应不同产品名或多个成本时，整批回滚并给出源行号。成本为空时仍可导入 SKU 映射，但成本保持缺失。

当前表结构分为 `company_products` 跨店公司产品主档、`platform_sku_mappings` 当前平台 SKU 映射、`company_product_costs` 按生效日期追加的 RMB 单件成本历史，以及 `product_master_import_batches` / `product_master_import_rows` 两级导入审计。成本变化不会覆盖旧值；经营数据按平台 SKU 查公司产品时，可按数据日期取得当时最后一个已生效成本。Vue ERP 不提供上传或编辑入口，但所有现有自有平台 SKU 商品卡与详情会从本地 MySQL 只读带出公司 SKU，未命中统一显示“未关联”；商品中心、关键词流量、搜索定位、经营坐标、异常商品、退货管理和竞品雷达的现有搜索框均可直接搜索公司 SKU 或公司产品名。

商品中心详情的小指标卡会把该RMB单件成本按服务端最新取得的CNY/ZAR机构参考汇率换算为兰特，同时显示原人民币成本、换算率、汇率日期、北京时间获取时刻和来源。汇率固定从Frankfurter只读接口获取，ERP进程内成功缓存1小时；更新失败但已有成功缓存时明确标注旧值，没有可用汇率时兰特金额保持“—”，不影响人民币成本和其他详情。该值仅用于运营成本估算，不是支付或结算汇率，也不会写回产品主档。

竞品雷达的自有链接商品详情会按当前选中的精确Seller API Offer显示“成本与利润（人民币）”。详情卡展示人民币单件成本、兰特参考值、当前售价毛利润和“平台直接费用后利润（估算）”，两种利润都同时展示销售利润率与成本加价率。后者使用同店同Offer近30个已完成南非自然日中已验证Seller Sales行的`sum(total_fees) / sum(selling_price)`综合费率，并披露覆盖天数、销售天数、行数、件数、总费用及销售额；`selling_price`不重复乘数量，`total_fees`已包含成功费、履约费、揽收费和库存调拨费，不再重复相加。没有已验证日、没有销售、销售行费用不完整，或缺成本/汇率/售价时，该项保持“—”并说明原因，不把缺失费用当成0。仓储费、广告费、月租、头程、税费和退货损失尚未按该SKU完整核实，因此不在估算中；该数值只是比毛利更接近实际的单件经营利润估算，不是净利润、历史结算或未来结算保证。“原价毛利润”仍不在页面展示。页面继续披露汇率日期、北京时间获取时刻和来源；前端详情缓存按小时换桶，与服务端1小时汇率缓存一致。

截至2026-08-18对6个已连接店铺的正式MySQL只读核对：1,645个当前Offer/SKU均返回平台SKU，其中1,456个已映射并有当日有效人民币成本，189个仍缺成本，当前覆盖率为88.51%。因此不能表述为“所有SKU已有成本”；缺失项会在详情中明确显示“未关联/暂不能计算”，必须通过新的受审计产品主档导入补齐，不能在页面或公式中猜测。

凡搜索框允许输入商品名称，现统一支持模糊搜索：忽略大小写、重音符号、标点和多余空格，名称片段可以匹配，拆分后的单词也可以任意换顺序；例如`Wireless Speaker`可由`speaker wireless`找到。这里的“乱序”只改变单词位置，不会把单词按字母集合或任意字母重组来匹配。单词内仍允许少量输入错误：查询词5至8个字符最多1处，9个字符及以上最多2处，漏字、错字或一次相邻字母误换均计入，4字符及以下不容错；因此`speaker wirless`可以命中，但`rekaeps sseleriw`或严重错拼不会命中。SKU、公司SKU、PLID、Offer ID、TSIN、条码、订单号、RRN、完整链接和卖家等身份字段仍只按原文字的完整或部分内容匹配，不对编号做错字猜测。该规则覆盖商品中心、关键词流量、搜索定位、经营坐标、异常商品、退货管理、竞品雷达各商品搜索入口和保留的Streamlit单品分析；退货由后端在分页前匹配，其他Vue列表只过滤已读取的数据，普通搜索不会访问任何上游或写业务数据。

竞品雷达以及异常商品复用的自有链接详情会按公司 SKU 展示全部本地库存证据：海外仓只读取最新一份六店共享长睿 W8 成功快照，并按规范化后的公司 SKU 精确匹配，现存、可用、锁定、已分配、在途和不良分阶段显示；平台仓只汇总当前账号已授权店铺中该公司 SKU 的全部当前 Offer，分别展示可售、在途和收货中，并保留店铺、平台 SKU 与 Offer 明细。详情普通打开只读本机 MySQL，不现场调用长睿或 Takealot；不同库存阶段可能相互包含，因此页面不生成海外仓与平台仓的跨阶段总和，字段未覆盖时显示缺失而不补零。

首次启动后，管理员必须先在服务器电脑上打开 `http://127.0.0.1:8501`，创建首个管理员账号；这个初始化入口会拒绝其他局域网电脑，避免同事抢先注册管理员。密码至少8个字符，只以带随机盐的 scrypt 哈希保存到本机 MySQL。

Windows计划任务`Takealot ERP 登录后自动启动`会在当前Windows账号登录后延迟30秒运行`ensure_erp_started.ps1`。它先等待自动启动的`MySQL80`并检查`/api/health`：ERP已经健康时直接退出，不重启、不打断活动任务；ERP未运行时才调用上述正式`restart_erp.ps1`启动链。任务使用当前交互式用户而不是SYSTEM，确保用户级模型Key、Windows凭据管理器和需要可见浏览器的人工操作仍属于同一账号；因此电脑开机后仍需正常登录Windows，但进入桌面后无需再手动启动ERP。启动检查使用跨进程互斥避免重复拉起，结果写入`logs\erp-startup.log`，失败时每分钟最多重试12次，并允许使用电池时启动。

“物流管理”把长睿正式环境的仓库、渠道、产品数、库存、入库、出库、退货与状态分布，同 Takealot Shipment、PO、目的仓、发货/卸货状态和 SKU 收货数量放在一页。打开或切回物流页面只读取当前店铺在 MySQL 中的最近成功快照，不会因为页面访问、切店或等待缓存过期自动调用长睿或 Takealot。两边上游只在人工点击“手动同步两边接口”，或既有10:05早间、18:00晚间、次日09:00周期末及右上角手动店铺采集完整成功后同步；人工重复同步仍保留最短间隔保护。Takealot读取和最近成功快照按当前店铺隔离，并发工作线程显式继承所选店铺上下文，不会复用其他店铺的Key或PO。W8是六店共用服务商，同一轮全店定时采集只读取一次长睿结果，再在每个店铺上下文分别保存快照。每次成功读取的完整脱敏物流数据会覆盖保存到本机 MySQL，任一上游接口暂时失败时自动展示该服务商最近一次成功快照，并标明本地同步时间。页面不创建、取消、打印或修改任何上游物流单据，也不展示长睿收件人地址。

两边只有在头程号、箱唛或长睿单号明确出现在 Takealot Reference、Tracking Info 或 PO 字段时才列为“明确编号直连”。候选关系分为三级：完整卖家 SKU 与各 SKU 发送数量完全一致、双方唯一且建单日期相差不超过30天为高置信；完整 SKU 集合一致但数量不同、日期相差不超过60天为中置信；至少一半 SKU 精确重合但整单 SKU 范围不同、日期相差不超过60天为低置信。页面逐条展示双方数量、差额、日期差和一对多歧义；只有2至3个 Takealot Shipment 的逐SKU数量合计精确等于一个长睿入库单时才额外提示可能拆批组合。所有档位都不会自动当成已确认关系；拥有“确认物流关联”权限的运营或管理员人工核对后才写入永久关联与审计记录，撤销时必须填写原因。仅日期接近、数量相同或文本相似均不会单独形成候选。W8 当前查询结果没有逐站扫描轨迹；退货接口返回条数与 `total` 不一致时会明确告警，并按实际返回条目展示。

独立“退货管理”读取 Takealot Seller API `GET /v1/returns`，按顶栏日期与店铺范围汇总每条 Seller Return 的退货日期、Seller Return ID、订单号、RRN、Offer/TSIN/平台SKU、数量、地区、官方退货原因、客户备注、处理结果及交易展开，并关联本地商品名称、图片和公司SKU。页面可按商品名称/公司产品名模糊搜索，也可按SKU、单号、RRN和备注原文搜索，并按原因、处理结果和分页筛选；跨店数据始终保留真实店铺身份。自有链接的完整详情页也显示该PLID在所选观察区间内最近20条明细，并可进入完整模块。Offers 中的 `quantity_returned_30_days` 只作为独立滚动30天计数展示，不能反推出原因、客户备注、处理结果或交易，也不能替代 `/returns` 明细。普通查看只读本机MySQL，不会现场调用Takealot。

统一 Vue ERP 当前已移除“约平台仓”的侧边栏入口、页面组件、前端请求与专用类型，用户权限页也不再展示平台仓草稿能力。后端 Seller Portal 适配器、兼容接口、MySQL 草稿/Shipment/审计记录、Windows 凭据与安全开关仍原样保留，供以后重新评估前端时复用；这项保留不代表当前 Vue 页面能够查看或执行约仓。真实写适配器继续固定直连`https://seller-api.takealot.com`，不经过星凯、不使用星凯JWT或签名，也不改动原本严格GET-only的公开Marketplace API客户端。由于这是Takealot未公开的Portal内部契约，后端继续受默认关闭的`TAKEALOT_PORTAL_BFF_ENABLED`总开关和默认空的`TAKEALOT_PORTAL_ENABLED_STORES`店铺代码允许列表约束；只有两个条件同时满足的明确单店请求才可能登录、验证OTP、预审、创建或执行后续平台动作，端点升级时必须重新核验。

每店铺邮箱和密码必须由服务器管理员从本机控制台写入运行ERP的Windows账号所拥有的凭据管理器；交互式方式为运行`.\.venv\Scripts\python.exe -m takealot_ops.cli portal-credential-set --store 店铺代码 --email 邮箱`，再在隐藏输入提示中填写密码。本机用户级环境变量可以作为管理员一次性导入来源，但ERP运行时不直接依赖这些变量，且不得把密码复制到项目`.env`。保留的兼容API没有接收密码的入口，密码不进入MySQL、日志、审计或HTTP响应。可用`portal-credential-status --store 店铺代码`查看脱敏状态，或用`portal-credential-delete --store 店铺代码 --confirm-store 店铺代码`删除。OTP和Bearer只在当前Python进程内存按店铺隔离，OTP固定`remember_device=false`，重启或退出即清空。2FA由Takealot的`/v1/login`响应触发，不是ERP定时强制。

保留的单次直接创建兼容请求内部固定执行“校验会话 → 必要时登录/2FA → Takealot服务端`shipments_review`分仓 → 逐Offer/区域数量完全一致校验 → 单次提交Task 22”。本地记录仅用于幂等和审计；浏览器端没有约仓入口。`UNALLOCATED`、未知仓库、数量变化或部分分配都拒绝建单。POST/PUT从不自动重试；网络超时会标记“结果未知”，必须先去Seller Portal人工核对，避免重复Shipment。确认PO使用平台预览和Task 21后再输入Shipment ID；归档使用平台当前归档端点。当前Portal构建产物中的“确认已发货”路径存在`vi/`疑似拼写异常，因此实现采用推定的`/v1/`路径但继续由`TAKEALOT_PORTAL_SHIPPED_WRITE_ENABLED=false`独立关闭，必须在授权人工抓包确认后才能开放。所有后端兼容流程都服从Takealot服务端分仓和补货限制，绝不实现“不可约”绕过。

权限页面提供四个快速模板：

- 查看（`viewer`）：查看店铺、竞品和已有报表，不执行采集、刷新或人工处理；
- 运营（`operator`）：承担日常运营工作，可调用搜索定位、管理物流关联，并可采集、刷新及生成报表；
- 选品（`selection`）：可查看和采集竞品雷达，但不执行店铺刷新或管理操作；
- 管理员（`admin`）：默认拥有全部业务能力，并可管理账号和权限。

四个模板都只是新建账号或快速套用的起点，不是固定角色边界。管理员可在“用户权限”页面对每个现有账号逐项开启或关闭店铺查看、搜索定位运行、物流关联确认、竞品采集、刷新和用户管理等现有前端权限；套用模板会替换该账号当前的自定义权限，逐项调整后账号需重新登录生效。运营日报相关权限键仍保留给后端兼容流程，但不在统一 Vue 前端中展示或编辑。系统始终保留至少一个启用的用户权限管理账号，避免管理员把自己锁在系统外。

“用户权限”页面同时提供无数量上限的店铺权限目录和账号—店铺多对多分配。每个账号都可多选“运营店铺”，当前常见的一人两店只是运营规则，不是程序上限；这组勾选决定顶栏“我的运营店铺”合并范围和逐店负责运营名单。管理员、老板等跨店账号可同时开启“全部店铺（含未来新增）”，以后增加第7、第8个店铺时会自动进入其可见范围，但不会自动变成该账号负责运营的店铺；未勾选店铺仍可单店查看。关闭全部店铺后，运营店铺勾选同时也是该账号可查看的范围。该开关独立于查看、运营、选品、管理员四个权限模板，因此“老板”不需要新增一套写死的角色。

升级时，既有账号会无损保留为“全部店铺”，避免上线后突然失去数据；管理员再按实际分工把普通运营改为限定店铺。正式业务表现已使用`store_code`区分店铺，原有历史自动归入`current`，新采集按所选店铺写入。2026-08-04 已接入`current`至`store-06`六家店；以后仍可先预留新店，只有凭据进入`TAKEALOT_STORES`并完成首次采集后才标记为已接入。

登录后，页面顶栏的“当前查看店铺”会列出该账号可访问的店铺，并在所有模块统一提供“我的运营店铺”和“全部店铺”范围；“全部店铺”只包含当前账号可访问、已启用且已接入的数据店铺，不接受前端任意店铺ID列表。经营总览、商品中心、关键词流量、搜索定位、经营坐标、异常商品、退货管理、物流管理和竞品雷达都读取同一个全局选择，切换模块后范围保持不变；用户权限本身不按店铺过滤，但不会重置该选择。选择具体店铺时，请求携带真实店铺代码；选择合并范围时，后端按账号权限逐店读取并给每条商品、退货、货件和候选保留店铺身份，详情或人工操作再以该行真实店铺代码路由，不能把`all`伪装成店铺代码。待接入店铺仍只显示安全说明，不会复用其他店铺数据。不同运营人员通过各自账号登录取得店铺和功能范围，管理员页面不提供无留痕的账号冒充切换。

跨店读取继续遵守模块边界：物流管理把公司共享W8仓数据展示一次，只合并各店Takealot货件快照，且跨店视图不允许手工强制同步。搜索定位、商品详情和物流人工关联等按行操作会携带该行店铺代码，后端仍执行账号授权、功能权限和CSRF校验。普通切换范围只读本机MySQL，不触发Takealot、W8、模型或Seller Portal请求；较慢的旧范围响应还会被请求序号与当前范围校验丢弃，避免快速切换后回写过期店铺数据。被移出前端的约平台仓兼容接口仍要求明确单店，并继续执行账号授权、功能权限、CSRF、本机边界和双开关校验。

原顶栏“数据截止日期”已统一改为“数据范围”。默认视口是当前自然月月初至今天；查看历史时，“上一个月/下一个月”按完整自然月切换，回到本月时截止日期自动收在今天，不产生未来日期。运营也可直接修改开始日期和截止日期形成任意历史视口。经营总览的店铺下单、周期末流量和多店总销售额折线读取整个所选区间；商品、关键词和经营坐标等既有单日页面继续使用区间截止日期。异常商品不显示开始—截止区间，只显示独立的一个“数据日期”，选择该日不会改写其他模块保留的全局区间。竞品雷达已有自己的北京时间观察区间和“按区间重算”，因此该页不再重复显示顶栏自然月范围控件；其他页面不受影响。保留的运营日报后端流程继续使用独立的10:00业务周期日期，不受这个前端全局范围控件影响。

店铺范围与公共模块权限彼此独立。竞品雷达只要账号已开启对应功能权限，即使没有分配任何店铺也可以进入和操作；登录时会自动落到第一个可用公共模块。竞品雷达会只读复用当前单店 Seller API Offer 的PLID和完整刷新历史来识别自有链接，但这不改变它的公共模块权限边界。经营总览、商品中心、关键词流量、搜索定位、经营坐标、异常商品、退货管理和既有店铺报表仍属于店铺数据范围，必须同时具备对应功能权限和已接入店铺授权；保留的风险与运营日报后台接口继续执行同一店铺授权校验。“刷新全部数据”另按固定账号控制，只允许`kxx`执行，不随普通账号的店铺或模板权限开放。共用商品缩略图接口接受店铺、竞品或后端日报任一查看权限，但仍要求登录并执行官方图片来源安全校验。

侧边栏的10个模块入口都是带 `#module=<模块键>` 地址的真实链接。普通左键仍在当前单页内切换并保留竞品雷达正在运行的页面实例；右键可直接使用浏览器原生“在新标签页中打开”，Ctrl/Cmd/中键同样遵循浏览器默认行为。当前模块会同步到地址栏，因此刷新、复制链接或在新标签中粘贴都能恢复对应模块。退货管理使用 `#module=returns`；旧 `#module=daily-report` 和 `#module=platform-warehouse` 都不再是有效前端模块地址。模块链接不放宽权限：无权模块仍显示“未开放”，直接打开其地址也会在登录态校验后回退到当前账号可用模块，接口继续由后端强制鉴权。

“经营总览”的顶栏店铺下拉框只要当前账号至少有一家已接入运营店铺，就提供“我的运营店铺 · N 店”（多店时显示“店合并”）；账号有两个以上已接入可见店铺时始终同时提供明确的“全部店铺 · N 店合并”，即使运营范围恰好等于全部范围，也保留用户要求的“全部店铺”选项。运营范围只汇总明确勾选的店铺，全部范围只汇总账号可访问店铺。登录后默认选择覆盖账号全部可访问已接入店铺的最宽范围，用户仍可切回具体店铺；只有一个已接入店铺时继续保持单店。切回具体店铺时只读取该店的完整趋势、健康度和商品明细；合并范围由后端解析成授权店铺集合，不作为虚构店铺代码。后端会再次按账号、启用状态和接入状态收窄范围，不会泄露其他店铺或把数量写死。每张卡片显示该店自身最新可用指标日的下单件数/金额、近7日下单、在售商品、转化率、缺货、最近周期末商品近30天浏览量，以及平台可售、平台在途和平台收货中库存；点击“进入该店明细”会切回真实店铺上下文。

老板盘面的健康状态不使用黑箱分数，而是按“需关注、数据待补、当前口径正常”排列，并直接列出缺货商品、流量和库存字段缺口。数据异常仍不在经营总览展示，也不参与店铺健康判断或排序；运营在独立“异常商品”模块按当前店铺查看。各店“负责运营”只取明确勾选该运营店铺、账号启用且拥有店铺查看权限的账号；管理员若被明确勾选也会进入名单，单纯全店可见不会自动产生运营责任。姓名只随当前账号所选合并范围返回。顶部库存物流区从本地最近成功快照把共享 W8 海外仓只计一次，同时按合并范围最新 Offer 汇总平台可售、平台在途与平台收货中，并显示商品字段覆盖。海外仓锁定、已分配出库、海外仓在途和平台不同阶段分开展示，不相加成可能重复的“总库存”。跨店销售合计继续标注实际返回家数，不把缺失店铺补0，也不假设各店指标日完全相同；转化率中位数不跨店平均。打开页面、切换多店范围或进入某店明细只读本地 MySQL，不触发 W8 或 Takealot 上游同步。

选择“全部 N 个店铺”后，老板盘面同时按顶栏完整日期视口显示已结束且有指标南非业务日的“可见店铺总销售额趋势”，不再在单店与六店汇总层各截一次最近30日。每个点汇总 Seller Sales 已进入正式指标的订单行金额 `ordered_revenue`；该金额已是接口返回的整条订单行金额，不会再乘一次数量。只要至少一家当前账号可见、启用且已接入店铺存在该业务日金额，就返回并绘制已有店铺合计；缺失店铺不补0，点位、顶部摘要和悬浮详情都会明确显示覆盖家数与缺失家数，不能把部分合计冒充完整六店总额。只有所有店铺都没有该日金额时才返回空值并保留折线断点。当前仍在进行的 SAST 日即使已经取得日内部分值也不进入折线；日内 Sales 拉取可以更新暂存累计值但不计历史修订，该 SAST 日结束后的第一次成功 Sales 拉取只建立正式日终基线。每次 Sales 完整成功都会重拉并重建截至执行日的最近30个 SAST 自然日；即使同批 Offers 失败，Sales 仍会独立尝试核验历史销售额，但该次运营日报/周期末完整采集仍保持失败。只有已经建立日终后 Sales 正式基线，且时间更晚的成功 Sales 批次再次改变该业务日金额或件数时，才立即更新正式指标并在不可覆盖的修订记录中保存修改前后值、差额、前后数据源、Sales 运行 ID、请求范围和发现时间；日内累计、第一次日终基线、同批次或本地重建都不计纠偏，数值未变化的成功重拉仍会刷新来源验证时间。既有原始审计行继续保留，读取时按同一严格口径排除旧日内累计记录，不做破坏性删除。此前的一次全历史回补已把Seller Sales可返回的旧记录写入正式指标，因此人工选择更早视口时直接读取这些本地历史；定期最近30日修订与全历史回补是两条不同范围。折线用绿色表示后续 Sales 已验证、橙色表示周期末失败后仍待完整验证、蓝色表示日终基线后已由更晚 Sales 修订；下方“销售额日终后历史修订记录”默认跟随当前视口，也可继续手工调整日期回查所有前后来源。该页面及审计查询继续只读本地 MySQL，不会因查看而访问上游。

Vue ERP 的折线图使用统一的高对比视觉和清晰详情交互：六店总销售额、店铺流量、关键词滚动流量，以及竞品价格/精确库存/评论三联图都加粗主线、强化坐标和网格，并用十字指示线定位当前数据点；竞品自有链接选中精确Seller API自有报价时再追加“近30天浏览量”第四张图。经营总览和关键词流量的既有悬浮详情继续跟随鼠标指针，靠近视口边缘时自动换向或收住位置，鼠标离开折线图后立即隐藏；竞品报价历史三/四联图改为在图表上方固定显示共用详情框，默认展示最新报价时间点，鼠标横向移动或左右方向键只切换详情内容，详情框本身不移动也不因移出图表而消失。四个指标共用同一北京时间横轴范围和左右绘图区边界，各自纵轴使用一致版式但保留自身量纲；每个指标面板左侧固定拆分为指标说明、纵轴刻度和绘图区三个独立栏位，并以竖线分隔说明栏，长指标名及说明不会再压住刻度或折线。自有Seller API价格、库存和近30天浏览量现在写入同一次不可变Offer观察；流量图只接纳与当前Seller报价观察`captured_at`完全相同的逐次记录，不再把每日快照吸附到最近节点，因此同次价格、库存、评论断点和流量节点位于同一垂直线。历史兼容迁移只从明确关联同一Offer采集运行的日报版本或完全相同时间戳的旧快照回填，无法证实的旧日内值保持缺口，不用18:00或最近值代替。出现第四张图时卖家导航改为上方紧凑排列，四联图独占整行宽度，不再被左右双栏压窄。近30天浏览量的商品名称变更节点使用加粗边框，变更但流量缺失时显示空心节点，详情披露同次Seller刷新时间及变更前后名称。竞品报价历史图不使用曲线光晕、面积阴影或图框内阴影；其上方另并列显示随当前卖家/报价切换的“区间内售出件数”和“区间内补货件数”。计算先按卖家、SKU、变体和条件范围分组，再过滤缺失与非精确库存点；每个范围至少两个精确点才分别累计下降段和上升段，单点范围直接忽略，不同范围之间不相减。过滤后只要仍有一组可比点就显示汇总结果，整个区间没有任何同范围精确点对时才显示“数据不足”，且明确只是库存观察而非平台实际订单或入库单。没有详情浮层的其他折线图不因这项交互统一而新增弹框。全部图表随容器宽度自适应，不创建横向滚动条。缺失日期/时间点仍保持无值并以“×”标识；当缺口前后都有真实值时可用虚线桥接两端，图例明确虚线不是插值、补0或期间真实走势。六店销售额中的“某店缺失”属于跨店覆盖不完整而不是整个日期无值，因此按已有店铺合计绘点并醒目标注覆盖和缺失家数；其他图表的真实缺失点不受影响。详情继续披露店铺/商品覆盖、同日参考、库存证据或PLID共用评论等真实状态，不会为了视觉连续而改写业务口径。

全部现有前端模块会保留在侧边导航中，账号没有对应查看权限时以“未开放”标识展示；点击锁定模块或页面内未授权的竞品采集、日报处理/导出等操作时，统一显示“当前账号该功能权限未开放”，不得静默无响应。“刷新全部数据”属于固定账号例外，非`kxx`账号不显示按钮且后端直接拒绝。后端仍会再次校验每个接口，前端提示不能替代真实授权。

前端发布新权限模型而正式后端尚未重启时，页面会按旧账号的查看、运营或管理员模板临时补齐权限，避免登录后空白；后端重启后自动改用账号级真实权限。登录信息无法识别、接口连接失败或页面脚本异常时，页面必须显示明确错误说明和重新连接/重新加载入口，不允许只留下空白页。

权限由后端接口强制执行，不只是隐藏前端按钮。会话保存在可撤销的 HttpOnly Cookie 和 MySQL 会话记录中：登录后有效7天，只要在到期前继续使用，系统就把到期时间自动顺延到最近一次有效使用后的7天；为避免页面高频轮询反复写库，同一会话每1天最多续期一次，并同步刷新浏览器 Cookie。连续7天没有任何有效使用才需要重新登录；主动退出，或管理员修改该账号的权限、模板、密码、启用状态时，旧会话仍会立即失效。写操作需要 CSRF 校验，连续登录失败会被短时限流。浏览、筛选和切换页面时使用 MySQL 只读事务，不调用平台 API，因此查看已有历史数据不需要 API Key。

侧边栏会显示“最近采集”和“最新指标”，用于判断当前看到的数据是否已经更新。登录页面保持打开时，可见页每15秒自动读取一次本机只读状态；页面从后台恢复可见时会立即重读，因此不需要手工刷新浏览器。隐藏页暂停这项定时请求，短暂本机服务异常会保留最后一次成功状态；这条链路不会触发Takealot、采集任务或数据库业务写入。“最近采集”以及竞品历史快照的时间固定按北京时间（Asia/Shanghai）显示，不跟随浏览器或南非平台时区；“最新指标”仍是既定的 SAST 业务日期。右上角“刷新全部数据”只向`kxx`账号显示；后端也会按用户名硬校验，其他账号即使拥有管理员模板、`refresh.run`或直接调用接口仍返回403。点击后固定调用项目根目录`.env`中的全部已配置店铺，正式环境当前依次刷新6店，不受顶栏当前所选单店或合并范围影响；各店均执行带分层重试的只读采集、指标重建、日报版本冻结和物流快照同步，每家成功结果都进入当前10:00核对周期的独立“手动刷新”版本。全店任务最多同时运行一场，成功状态保存在MySQL并在切店和服务重启后保持一致；当前`kxx`管理员可越过成功后的1小时冷却，但不能与仍在运行的刷新并发，失败刷新不开始冷却。失败时可查看`logs\takealot-ops.log`，失败原因也会进入日报运行记录，页面不会显示或记录 API Key。

“商品中心”直接在每条商品栏中展示平台商品缩略图；图片缺失或加载失败时显示“暂无图片”，不会保留破图图标。点击商品栏或用键盘回车/空格激活后，商品身份、当前售价、最新日/近7日下单、库存、近30天浏览量、转化率以及每日销售件数快照会集中显示在当前视口的详情弹窗中；历史区不再展示流量快照，销售柱图纵轴按整数件数显示数字刻度。详情不再重复铺在商品列表下方，避免在窄屏中滚动到页面底部查找。弹窗支持遮罩、顶部和底部关闭入口及 Escape 关闭，打开时锁定背景滚动，关闭后焦点回到原商品栏。

“关键词流量”完全复用每天完整 Offers 快照：`page_views_30_days`形成按日近30天浏览量趋势，官方 `title` 形成“商品标题关键词”档案。选中商品顶部固定显示两项时间信息：首次上架优先读取平台 Offers 的 `created_at` 并按南非时间展示，旧记录缺少该字段时明确标为“本库最早记录”；最近补货只在后一条有效平台库存快照高于前一条有效快照时记录，显示该快照实际采集的北京时间和增加数量，没有观察到库存增加时显示“暂无记录”。Seller Offers 当前没有独立 `keyword`、`search_term` 或 `tags` 字段，因此系统不会伪造平台搜索词；`product_label`是数字商品标签，也不作为关键词。每个商品的首个有效标题快照就是基线；以后标题词新增、移除、词序或写法发生变化时，系统生成南非业务日变化节点和对应标签，并以高对比竖线固定在流量图上。页面可选择前后3、7、14或30天，所选节点继续驱动趋势图的前后窗口、竖线与节点高亮，并在下方标题关键词时间线保留完整标题和增删词；独立的“已选变化/基线节点”效果汇总卡已移除，不再重复展示观察进度、浏览量前后值/净变化/百分比或趋势斜率变化。后端比较数据与计算保留，变更日继续排除，缺失流量保持断点且不补0。页面没有人工建档、补录或修改入口，查看已有历史也不会调用平台接口或写入数据库。

“搜索定位”与上面的“关键词流量”是两套不同口径。列表先以当前店铺授权 Seller Offers 的 `OfferCurrent` 作为自有身份凭据；完整刷新会删除上游已不存在的Offer。只有状态严格等于`buyable`、平台与卖家可售库存合计为正、快照不超过36小时、数字PLID/主标题/Takealot官方`covers_images`主图齐全的链接才显示。点击运行时在任何模型调用前再次执行同一闸门；模型识别完成、平台搜索开始前再核对一次，状态或资料变化即停止。库存为正但状态被卖家或平台禁用仍不算在售，普通查看也不会为了更新状态自动访问上游。

通过自有在售闸门后，系统按“隔离图片观察 → 独立交叉验证 → 图文融合生成”执行。第一阶段只接收缩小后的商品主图，绝不接收主标题、SKU或人工事实，因此页面“隔离图片观察”不会复述标题。服务器随后把这份观察与当前官方主标题确定性交叉验证并单独保存；差异大只生成醒目提示和筛选标签，不会把标题偷偷塞回图片阶段，也不会因为差异自动切备用、降置信或阻断。第二阶段接收同一主图、当前主标题、隔离观察和差异摘要，至少输出6个第一直觉词/词组及6个完整搜索词。两个模型阶段生成的商品名、类目、别名、词根、买家任务、替代商品族、完整搜索词、标题建议和理由都强制以南非本地客户习惯为预测语境并使用南非英语；结构化响应必须显式回传固定地域标记，缺失或错误即拒绝。该约束不等于模型已经测得真实南非搜索量，后续Takealot根词扩展和搜索页才是独立平台证据。模型链签名只包含实际启用且按调用顺序排列的提供商与模型，不含Key；完整缓存还绑定当前规范化主标题和提示版本，标题或本次地域契约版本变化都必须重做图文融合。两个阶段的usage先持久化，后续搜索失败时不会丢失已产生费用；页面主结果继续保留最后一次完整成功分析，并另行提示最近失败尝试。

搜索定位页首把上述运行口径压缩为模型服务链、扫描边界、探索预算和请求节流四组常驻信息；南非英语语境与普通查看只读本地继续直接显示。平台扩展入选口径和六级词根来源收进默认折叠的“词根与平台扩展规则”，需要时再展开；这只是信息层级调整，不改变模型调用、候选筛选、请求节流、自然排名或证据边界。

每个已分析商品都显示可选的“人工确认商品事实”入口，不把人工确认设为完成分析的前置步骤。若图文融合模型明确列出图片与标题都无法确定、且会改变搜索身份的关键事实，单商品结果会说明缺口，批次则记录“待人工事实”并跳过该商品，不发补全或搜索页请求；其他商品继续串行。运营可填写例如购买类型`compressed sofa`，也可把仅代表工艺或出货状态的`vacuum compressed`选择为结构形态；确认后仍须重新读取Takealot补全和搜索页，只有相关性及位置门槛通过才会形成标题建议。确认事实按店铺和PLID隔离并记录账号、时间、分析标题、主图和证据；撤销只改变状态并保留历史，主图变化时旧档案暂停应用。外部倒搜的前端入口、HTTP路由、客户端、工具提示和费用配置保持删除。

图文融合阶段会分别给出至少6个精准完整搜索词、至少6个普通买家可能先输入的第一直觉词根、2至8个同品直接别名，以及可竞争相邻需求的结构化假设；每个相邻假设必须包含买家任务、至少一个替代商品族和可选排除商品。当前主图绑定的人工确认事实也可补充模型无法确定的商品类型，但这些都只是候选。系统读取Takealot公开`search_suggestions`，把真实扩展文案、输入词根、第几项、采集时间和共享缓存状态写入证据，再对每个最终候选检查默认`Relevance`的完整第一页（最多36个自然商品）。S级同品统计采用图文融合或人工事实支持的商品名和直接别名，做小写、标点、简单单复数及有限复合写法归一，并排除`cover`、`sleeve`、`pad`等把主体改指向配件的标题；A级再用结构化买家任务对应的替代商品族核对实际第一页是否形成一致的替代需求。投影幕布继续使用受控商品族写法：`projection/projector + screen/cloth/curtain`的双词组合互相视为同品，但单独通用词不计同品。当前公开搜索载荷没有逐结果图片和类目证据，系统不会为第一页每个商品再次调用多模态模型，因此边界案例一律降到C/I而不猜。排名只读取`sections.products.results`中的自然`product_views`并排除显式赞助标记；平台扩展顺序是意图代理而非公开搜索量，商品总数也不是访客、热度或销量证明。

每次完整分析还会对“本次分析时的现有主标题”给出可追溯的标题质量分。`evidence-title-v2`只评价当前标题文本相对冻结商品与查询证据的表达质量，五项满分固定为100分：图文身份一致性25分、商品类型表达20分、平台已验证搜索词覆盖25分、有依据的卖点与事实表达20分、标题可读性与重复10分。自然排名、首页同类占比、竞争商品数、价格、库存、广告位和平台扩展顺序全部移出总分，只在独立搜索表现证据中展示；因此在商品和验证词证据固定时，这些表现信号变化不会改变标题分，只有标题文本或它与冻结证据的匹配变化才会改分。缺失证据从分母中排除而不是记0，并单独显示证据覆盖率；覆盖率不足70%时归为“证据不足”。历史`evidence-title-v1`记录在读取时仅使用原有分项本地换算，不调用模型、Takealot或写数据库，并明确标记兼容投影。列表仍可按高分、良好、待优化、较弱、证据不足或未评分筛选，并可独立筛出图题差异大、一般、一致和待人工事实商品；该质量分不保证自然排名或销量变化。

结果卡把“第X页、第X行、第X列”作为主定位；“跨页自然排名 #N”紧随其后解释为“自然商品序列中的第N个”。第几页来自Takealot的`after`游标页，每个游标页最多纳入36个自然商品，页内按桌面端从左到右每行四项映射坐标；跨页自然排名只按实际纳入的自然商品连续累计。若平台页内有被排除的赞助或非商品记录，下一游标页不承诺机械地从`页码 × 36 + 1`开始。页面可能额外插入其他内容，因此视觉位置仍可能与接口自然序列坐标不同。“未采用”只表示该搜索词最终没有进入推荐词；若已经找到本商品，仍保留具体排名并显示“已定位，但该搜索词未进入推荐词”。只有完全没有发送搜索页请求时才显示“未进入扫描范围”；只检查过第一页相关性但没有继续定位时显示“仅完成首页筛选 未进入后续定位”，不再用含义不明的“已拦截”。为避免每张词卡重复铺陈，页面不再显示候选生成理由或完整的S/A命中词与判级边界段落；语义等级、S/A/C+I结果、S级占比、首页命中数、扫描状态、位置、来源及采集时间仍保留，后端审计证据也不删除。

标题建议固定拆成三种彼此独立的打法，并始终分成三个区域展示：第一种“完整连续词组版”只把首个通过验证的完整核心短语前置；第二种“类目热词覆盖版”只合并真实Takealot扩展且已通过核心相关性、同时得到当前标题或当前主图绑定的已确认商品事实支持的类目表达，用更积极的前部覆盖测试多个查询；第三种“S/A蓝海命名版”只使用通过独立蓝海闸门的S级同品直称或A级相邻替代需求词。蓝海闸门要求该完整搜索词确实由平台根词扩展返回、语义等级为S或A、事实安全、目标可搜到且自然位不晚于72、首页扣除本商品后直接同品不超过2个；A级还必须通过实际第一页替代商品一致性。第二种所称“热词”仍只是平台扩展支持的搜索意图词，不代表公开搜索量；第三种未达门槛时保留区域并明确显示暂无方案，不硬编标题。当前标题本身若把商品身份写错，不能再要求新身份词必须预先存在于错误标题中：只有S级查询明确命中图文融合的同品名称，并且完整第一页仍达到同品多数，系统才可把该查询中最小的同品身份词组投影到连续版；夹在同品词之间的新上下文也必须已经由当前标题支持。颜色统一视为标题参数后置，不能因模型原建议或Seller原词序把`Blue`等颜色放在商品类型前。三种标题均只使用可支持事实：未获当前标题或当前主图绑定的人工确认事实支持的数字或规格单位、材质、颜色、受众、品牌兼容、功效及模型区别属性会被阻断；App、Smart、USB、Compressed等高风险属性也不会仅凭扩展词写入建议。系统不自动修改 Seller Portal 标题，也不保证一定前移；后续完整Offer刷新检测到标题确实等于某一建议后，只把该打法的证据词作为主验证目标并强制同词复采。任何基线词本轮缺失或未找到时都只报告证据不足，不能把剩余词的前移包装成整体前移；其他查询只能作为次要观察。该前后对比仍是观察证据，排名会受时间、地区、个性化、库存、价格和平台策略影响，不能单独证明标题造成变化。

建议标题还会经过服务器端固定整理：最终只保留字母、数字和单个空格，不含任何标点；三种打法统一按“商品类型与相关证据词在前、功能卖点居中、明确规格参数默认在末尾”成稿。服务器从当前Seller Offers标题确定性提取功率、电压、电流、容量、尺寸、重量、数量或套装、分辨率及IP或IK防护等级等规格组，在商品词去重后按原相对顺序追加到标题尾部；`S24`、`iPhone 15`、`5G`等型号、代际或连接身份不会仅因含数字被误搬。搜索定位详情对每个合格自有在售商品固定显示“决策参数人工确认”，即使尚未运行图片分析也可以操作：系统只提示参数类型和保守建议，运营必须对当前标题里的每项规格选择“是 决策参数”或“不是 保持后置”，没有可识别规格时也可以确认这一事实。一次确认按店铺、PLID和当前完整标题追加不可变审计；标题变化后旧判断留档并失效，每个标题最多确认3项为决策参数。保存只写本地MySQL，不调用模型、Takealot或Seller Portal。确认为“是”的参数会在下一次重新验证中占用一个平台补全核心位；只有参数值来自当前标题、完整搜索页同类相关性通过且不存在冲突，才允许适度前置。查询预算为6个图文融合直接词、6个补全路径、1个相邻需求及条件式1个补救词，总上限14；已确认参数只等量替换补全核心位，不扩大预算。标题区固定显示“本次分析时标题”；最新Offer标题变化时旧评分与旧建议会标记过期并要求重新分析。

Vue ERP 的现有商品图片入口统一使用登录态同源缩略图：商品中心、经营坐标、竞品雷达及其弹窗、历史卡片不再直接下载和解码平台高清原图。列表、表格、卡片和小型头图使用最长边 192 像素 JPEG，商品中心详情大图使用最长边 640 像素 JPEG；后端只接受 Takealot 官方 S3 与媒体域名，并把路径严格限制为当前 `covers_images` 或公开竞品旧图仍会返回的 `covers_tsins`，同时限制原图大小、像素和可选缩略尺寸。`covers_tsins`只扩展同源缩略图兼容，搜索定位的Seller Offer模型主图仍只接受`covers_images`。结果按尺寸缓存在 `data\runtime-cache\product-thumbnails-*`，属于可删除、按需重建的运行产物。同一图片的并发首次请求仍只转换一次；进程内缓存键锁按正在使用人数计数，成功、失败或异常退出后由最后一个使用者立即移除，不会随历史图片数量长期滞留。图片声明固有尺寸并异步解码，长列表继续懒加载和跳过离屏绘制，避免页面交互时反复布局或解码大量图片。

浏览器中的原生图片标签不能附加普通 API 使用的 `X-Store-Code` 请求头，因此缩略图同源 URL 会显式携带当前选中的真实 `store_code`；后端也只对缩略图路由兼容没有店铺参数的旧页面，在账号不存在 `current` 授权时使用其任一已授权店铺完成门禁。登录、功能权限和官方图片来源校验保持不变。其他运营电脑通过局域网打开 ERP 后，请求的仍是 ERP 服务器上的同源缩略图接口，由服务器访问、转换并缓存 Takealot 原图，客户端不会直接下载平台高清原图；无痕窗口只需重新登录，加载链路不变。

“经营坐标”使用商品最新的近30天浏览量和截至最新指标日的近30个自然日下单件数，只展示一个二维坐标散点图，不再划分明星、潜力、待优化、转化问题四象限，也不再提供分位选择、分类筛选卡或十字分界。横轴固定为“近30天浏览量相对排名”，纵轴固定为直立竖排的“近30日下单件数相对排名”；两个方向的0、25、50、75、100关键排名刻度放在图框外的独立白色数字标记中，避免被散点遮挡，图内只保留轻量参考网格。散点统一使用高对比蓝色。鼠标移到商品点上会立即出现 ERP 样式的信息卡，优先展示平台商品缩略图，并显示商品名称、平台 SKU、库存、近30天浏览量、近30日下单、首次上架/最早记录、最近补货时间和数据截止日期；图片缺失或加载失败时显示“暂无图片”，不保留破图图标。信息卡会按点位自动向上或向下展开，不会被图框裁切。点击小点会直接复制平台 SKU 并显示结果反馈。只有同时具备两个真实指标的商品进入坐标图；缺失数据不会按0处理，仍完整保留在“全部商品”区域。全部商品改为自适应卡片，商品名称和全部字段完整换行展示，不需要左右滑动；每张卡片均包含商品图片、平台 SKU、浏览量、下单、平台库存、首次上架/最早记录、最近补货及数据截止日期，并可通过“排序方式”选择器按近30天浏览量、近30日下单、平台库存或商品名称排列。搜索框支持商品名称模糊搜索，以及忽略大小写的完整或部分平台/公司 SKU 即时匹配；持续显示当前结果数与商品总数，无匹配时给出明确空态，清空后恢复全部商品。浏览器复用未变化的卡片虚拟节点，避免悬停或复制 SKU 时重新构建全部商品内容。单品分析和店铺总览的每日下单件数图只显示真实整数件数，不再绘制可能产生小数的移动平均线。

Offers 接口提供 `created_at` 时，“首次上架”使用该平台时间；旧历史没有该字段时明确标为“本库最早记录”，不会伪装成平台真实上架时间。系统逐条比较同一商品的有效平台库存快照：后一条库存高于前一条时，后一条快照的实际采集时间就是“最近补货时间”，同时显示较前次增加数量；该时间按北京时间展示，不属于估算。没有观察到库存增加时显示暂无记录。Offers 接口只明确返回近30天滚动浏览量，没有独立的近7日流量字段，因此经营坐标和悬浮卡不再推算或展示近7日流量，只展示平台原值“近30天浏览量”。

Seller API 也没有独立的店铺总浏览量字段。经营总览的“店铺商品近30天浏览量汇总趋势”复用每天次日09:00周期末成功冻结的商品版本：每个点按周期末实际采集的北京日期减一天归档，例如8月6日09:00采集显示为8月5日，不直接复用运营日报的 `business_date`。同一归档日取最新成功 `pre_close` 版本，汇总接口已返回的各商品 `page_views_30_days`，并显示覆盖商品数和缺失商品数。缺失值不补0；某日整次周期末刷新失败时，正式周期末值继续保持失败和断点，同时查找该北京时间自然日最近一次非周期末成功采集作为橙色虚线参考，并明确展示实际采集时间、来源时段、覆盖数和缺失数。没有同日成功采集时仍保持完整断点；参考值不得冒充09:00正式周期末数据。同一天因Windows重试形成多个周期末版本时只取最新成功版本，不重复相加。折线的横轴日期跟随顶栏所选视口；每个点本身仍是当日观察到的滚动30天窗口汇总，不代表精确当天流量或访客数。

统一 ERP 前端已移除“报表工作台”、NFT102 上传续写页面、旧“风险与质量”和“运营日报”模块；对应旧导航、页面、前端请求/类型、权限配置入口、全局待办提醒与事件订阅均不再加载。新的“异常商品”是独立只读模块，不恢复旧风险页或改变旧风险/报表规则。既有 NFT102、风险/质量和运营日报后台接口、数据、计划任务与导出流程仍保留，供命令行及兼容流程使用。

旧异常口径仍默认以“最新指标日”为准：后台风险投影、Excel 总览和 HTML 总览都统计该日出现异常的去重商品数；异常明细保留同一商品在当天触发的每一种异常，因此明细记录条数可能大于异常商品数。历史异常继续保存在数据库并可由后台接口读取；Excel、HTML 和 PNG 日报默认只输出最新指标日异常，不混入历史日期。经营总览和新的异常商品模块都不读取或改写这项旧风险统计。

新的“异常商品”模块把五种入口完全分开：动销突然中断、不可购买有库存、平台禁售有库存、卖家禁售有库存和有库存滞销。动销突然中断要求停销前连续7个完整业务日中至少5天有单、合计至少7件且最后一天有单，随后连续3个完整业务日为0；缺失日期、未结束的今天和未被成功Sales批次核验的日期都不当作0。三种不可售状态各自成组，“有库存”只认当前可售库存；收货中与在途数量仍作为明细展示，但都明确标为“不计入”，不能凭任一非可售阶段进入异常。滞销只纳入当前状态可购买且现货大于0的商品，选择器固定显示“4/7/10/15/20/30天及以上未动销”；实际筛选和分组计数都按连续未动销天数大于或等于所选门槛计算，正好等于门槛的商品也会进入。实际滞销天数从同一Offer最近一轮连续有现货且零销量的完整业务日开始累计，补货前无库存的日期不算，库存归零后重新有货会重新起算。Sales或同日库存快照缺失时不会向前猜算，边界无法证明则显示“至少N天”。列表后端只读取当前商品、逐日销量、历史可售库存和Sales核验状态中的必要列，不再构建整套ERP数据集；结果按店铺、截止日和数据库修订保存在64项进程内LRU中，正式Offers或指标刷新后自动换键失效。全部读取只访问本地MySQL，不触发采集或上游访问。

竞品雷达自有商品分区、个人监控池或共享类型库中的自有商品，以及异常商品卡片，点击或键盘激活后统一请求一个新的浏览器窗口，并在新窗口中直接显示无ERP侧栏的独立完整页面；原页面不会切换模块，也不再承载自有详情弹窗。新窗口地址只携带PLID、调用时的`current / operating / all`店铺范围、当前单店代码和已选观察日期，登录恢复后仍由`competitors.view`与账号店铺授权校验；个人监控池和共享类型库里的自有详情固定使用当前账号全部授权店铺范围。类目、全部卖家报价、价格/库存/评论历史、自有销量、近30天浏览量、利润、退货和公司SKU库存继续复用竞品雷达同一个完整详情组件与原接口，不复制缩水页面；真正竞品仍在当前竞品雷达页使用原详情弹窗。独立页并行读取单PLID自有窄投影、完整详情和个人监控关系，不预载整批自有链接、店铺目标或竞品工作区，也不再使用异常卡悬停预取；浏览器拦截弹出窗口时原页显示明确提示。异常列表仍使用浅层响应容器、复用数字格式化器并固定每页最多30张卡，离屏卡片可跳过绘制，完整详情的评论一次最多创建20条并分页。2026-08-17记录的列表必要列和单PLID读取耗时只是当时本机快照，不是固定SLA。整个打开过程只读本机MySQL，不触发平台采集或业务写入。

销量趋势改用同一指标日截止的自然日均值比较：近3天下单件数日均值低于近15日均值时判为“销量下降”，高于时判为“销量上升”，两者相等时不产生销量趋势异常。两个窗口都包含当前指标日；只有系统已覆盖完整15日窗口时才判断，窗口内已覆盖但没有订单的自然日按0件参与平均，历史不足不补零、不判趋势。不再使用“当日销量对比此前7日均值”以及最低销量、涨跌百分比门槛。

风险后台能力继续保留完整异常证据：销量趋势保存异常发生日截止的15天逐日销量及近3日/近15日日均，流量转化保存实际浏览量、转化率、销量窗口与必要阈值，疑似断货、停止更新和未知销售状态保留各自触发上下文。历史异常证据不得用当前指标替代，不足30天的销量窗口不得伪装完整覆盖；这些数据继续供接口和报表使用，但 ERP 前端不再提供旧风险卡片、筛选或旧详情弹窗。

### 4.1 竞品观察

真正竞品列表已移除“可跟卖机会”选择器、统计说明区、商品卡标签及隐藏机会字段的搜索命中，运营页面不再展示“全部机会 / 全部报价售罄 / 暂无卖家报价”这组入口。后端仍保留原有保守判定字段用于接口和历史兼容：只有完整成功公开报价证据才会形成值，删除前端展示不会改变采集、快照或数据库历史。

打开真正竞品当前页弹窗或自有商品独立详情页时，详情接口都直接在MySQL按当前PLID限制竞品快照、评论、变体和自有店铺观察点，不再先读取全部竞品后过滤。真正竞品弹窗关闭时不会预读列表第一件商品；同一页面内重复打开同一PLID、观察区间、店铺范围和最新采集版本时继续使用最多24项缓存，新开的自有详情窗口则按其独立页面生命周期读取。正式样本`PLID101163999`原先为读取18条历史、1条评论和18条变体而组装全库5680条历史、6598条评论及7601条变体，单次约4.45秒；按PLID查询后冷启动约0.092秒，后续数据库热态约0.026–0.031秒，返回内容未裁剪。

“竞品雷达”是统一 Vue ERP 的一个正式模块，与经营总览等页面共用 `8501` 地址和同一份 MySQL，不再通过 Streamlit 嵌入或单独启动第二个端口。

竞品雷达会从六个已接入店铺 Seller API 当前 Offer 的 `productline_id` 自动汇总自有商品链接，先在每店内去重、再跨店按PLID去重，并与人工维护的“真正竞品”分区。页面使用“真正竞品”和“自有商品跟卖”两个来源标签页，默认只显示真正竞品。进入竞品雷达时沿用顶栏全局的具体店铺、“我的运营店铺”或“全部店铺”范围；前者只取明确勾选的运营店铺，后者取全部可访问店铺，共享PLID保留各真实店铺名称。范围切换会与其他业务模块保持一致，只有一个已接入店铺时继续严格显示该店。每次点击“开始采集”都会重新读取当时最新的全部真正竞品和账号可访问的全部已接入店铺自有PLID，先放真正竞品、再放全部自有链接，按PLID去重后复用同一个页面批次、断点和串行浏览器；顶栏范围只改变页面查看范围，不会缩小手动采集范围。真正竞品和任一自有PLID都可插队，插队副本在当前商品之后执行，原队列位置和断点不被改写。每天09:00自动批次会读取全部活跃真正竞品和所有已接入店铺的当前自有PLID，范围不受某个登录账号或页面店铺选择缩小。自有PLID不会写入人工监控清单，也不需要逐条新增、修改或删除；页面始终同时显示后台全量跨店去重数和店铺内合计数，便于核对是否覆盖所有店铺。

竞品页切换顶栏店铺范围时只重新读取自有商品和对应自动目标，不再重载范围不变的真正竞品、个人池、管理员链接健康与全店目标。每次切换都会取消前一次可取消请求，并以请求序号、店铺范围和当前店铺代码三重校验响应；即使旧数据库查询较慢且晚返回，也不能把旧店结果写到新选择下。页面内按“范围 + 当前店铺 + 观察区间”缓存最近结果，切回已读取范围可直接复用；竞品组件不会因普通切店被重新挂载。服务端的`/api/competitors/own-store`只构建自有分区，列表接口不再组装详情才需要的完整历史、评论和变体DataFrame；Seller API观察点在SQL层限定到所选店铺，并用`NOT EXISTS`只补充没有同一观察记录的旧基准，避免同一店铺、Offer和采集时刻重复装载。正式六店只读核对中，T C STORE仍为182个去重PLID，全部6店仍为930个去重PLID；快速连点只影响等待中的请求，不改变最终范围。

“自有商品跟卖”分区另有“自有 Offer 最新状态”选择器，固定对应Seller Offers的`not_buyable / buyable / disabled_by_takealot / disabled_by_seller`，页面显示为“不可购买 / 可购买 / 平台已停用 / 卖家已停用”。状态和库存筛选都读取当前`OfferCurrent`；两个条件同时选择时，必须在同一个店铺代码和Offer ID上同时成立，不能把一个店铺的Disabled状态与另一个店铺的Buyable有货Offer跨店拼成命中。真正竞品继续使用原有PLID公开库存口径。同一PLID有多个自有Offer或跨店状态不同时，父卡仍展示全部去重状态；打开详情后切换自有Seller API店铺或具体报价，顶部粘性标题区会显示该Offer独立的最新状态及更新时间。区间价格、库存、原始状态和趋势仍只用于历史回看。Disabled只表示我们的Offer被停用，不代表该PLID公开页或其他卖家报价失效，手动和09:00自动批次仍会把该PLID加入`followers_only`跟卖监控并排除六店自己的Offer。

2026-08-04以前由旧页面生成的混合批次可能把当前店私有链接、其他店私有链接和真正竞品一起保存在浏览器断点中，例如旧的647条“待爬取”。断点格式现已升级为版本9；新页面首次加载会删除所有旧版断点，不再恢复错误混合清单。新建手动批次会按当前规则重新读取真正竞品和自有PLID；09:00自动批次使用独立的服务端持久断点，不会混用某个浏览器的旧本地断点。新增链接时，后端先按该PLID定向查询六店当前Offers，不再为了判断一条链接组装全部自有商品页面数据；真正竞品正常写入人工清单，属于任一已接入店铺的PLID则返回真实店铺名、不重复写入真正竞品，但仍自动加入提交账号的个人监控池并继续参加每日统一采集。

自有商品的Seller API数据来自“刷新全部数据”的完整 Offers 拉取：`store_offer_baselines`继续按北京自然日、店铺和Offer ID只保留当日最早一次完整拉取，供每日基准口径使用；`store_offer_observations`把每次手动或定时完整刷新保存为不可变历史点，并在同一条观察中原样记录价格、总库存、Takealot可售库存、卖家可售库存、官方标题和`page_views_30_days`。即使上游该字段返回空值，也会用`page_views_30_days_recorded`区分“本次确实拉取但接口无值”和“旧历史无法证明”；竞品页当前值、报价历史与第四张“近30天浏览量”折线都读取这条逐次观察。四联图只接受与当前Seller报价观察`captured_at`完全相同的流量记录，不做最近节点吸附，因此同次价格、库存、评论断点和流量节点共用一条垂直时间线。兼容迁移只从明确关联成功Offers采集运行的日报版本，或店铺、Offer ID与采集时间完全相同的旧`offer_snapshots`回填；无法证明的旧日内值保持缺口，不用18:00、日末值或邻近值代替。公开竞品批次的浏览器库存探测是另一条链路，不会调用认证Seller Offers接口。标题相对前一个有效观察变化时加粗对应流量节点并显示前后名称；滚动值只称“近30天浏览量”，不相减为当天流量，也不称访客数。切换到公开跟卖报价时不混用自有流量。自有链接详情不再额外展示重复的“SELLER API REFRESH / 自有 Offer 最新完整刷新”逐Offer清单，自有报价仍保留在卖家连续对比台，后台刷新、当前值与不可变历史均不改变；Seller API时间点没有同步公开评论时，评论折线保持断点。自有PLID进入统一共享批次后读取全部公开变体及报价，以所有已接入店铺当前Seller API的Offer ID和SKU精确排除自有Offer，剩余卖家才算跟卖；因此竞争卖家即使抢到某个变体的主报价也继续保留和探测。商品变体本身不等于跟卖，公开变体只在PLID共用变体区展示，只有排除自有身份后仍属于其他卖家的具体报价才进入跟卖列表。自有分区提供独立的六店日期区间表单，从不可变公开快照回溯区间内任一天出现过的跟卖卖家并列出具体发现日期；即使该卖家在区间末已经消失也不会漏掉。“新增跟卖卖家”表示系统全历史首次观察日期落入所选区间，不代表卖家实际开始跟卖的绝对时间。PLID商品共用评论在首次检查或公开评论数变化时单独读取，评论数不变时复用已保存正文；无论是否发现跟卖，详情都展示已有评论、评分、好中差评结构和公开变体。Takealot评论仍属于整个PLID，无法归属到某个跟卖卖家。

自有链接详情中的“上架以来销量”默认以条形图显示当前所选店铺从上架日到最新日期的全部可用Seller Sales点，每个北京时间自然日对应一根独立柱；完整0件以基线细柱保留覆盖证据，截至采集使用独立状态色，缺失日不绘制柱且不补0。图表提供独立的北京时间开始/结束日期选择器，起止日均包含在内，控件只能选择该店真实可用边界，切换店铺会恢复新店的全部日期，同店数据更新时保留并夹紧原选择，也可点击“全部日期”复位。日期选择只缩放条形图、当前点位和区间摘要；平台上架日、当前可见累计销量及上架以来完整/截至采集/缺失天数继续保持全量口径。区间摘要另显示自然日数、完整/截至采集/缺失天数和“已覆盖下单”；存在部分或缺失日期时明确说明该件数不代表完整区间销量。全部操作只处理详情接口已经返回的本地数据，不重新请求Takealot或写数据库。

“六店自有链接跟卖发现记录”默认收起，只保留标题、北京时间口径和“展开记录”按钮；展开后才创建日期查询表单、说明与结果列表。再次收起不会清空已经选择的日期或已查询结果，也不会触发新的平台访问或数据库写入。

Takealot同一变体的主购买区可能同时显示多个单选报价，例如页面上方的“Fastest Delivery”和“Best Price”。采集会保存该区域全部报价，而不是只取当前勾选项：每个变体自己的选中主报价只属于该变体，不直接触发跟卖；同一变体内其他未选报价以及下方红色`other_offers`才是跟卖候选。主购买区响应名为`sku`的值当前实际对应Offer ID，因此自有链接会用它同时交叉核对六店Seller API Offer ID和SKU。平台只返回绿色报价卖家ID、不返回名称时，页面显示稳定卖家ID和“平台未返回名称”，不会猜造卖家名。自有商品、真正竞品和个人监控池都提供互斥的“现在被跟卖 / 曾经被跟卖 / 未发现跟卖”筛选，旧快照仍按红色`other_offers`保守兼容。

竞品每日采集不再依赖运营保持竞品页面打开。Windows 计划任务默认每天北京时间09:00运行 `trigger-competitor-collection`；该命令只按北京自然日幂等写入一个持久触发文件并唤醒本机ERP，实际爬取仍由正式ERP启动与手动按钮相同的共享单批次。09:00触发时或读取目标后正式取得采集权前，只要发现人工或其他共享批次正在运行，当天自动批次就记录为`skipped_busy`并视为已处理：不等待、不排队到现有批次结束后补跑，也不停止或改写正在运行的批次，次日09:00再按计划尝试；ERP重启时，持久断点里尚未完成但还没重新登记到内存的旧自动批次也按正在运行处理新触发。没有批次冲突时，真正取得采集权后才读取全部活跃真正竞品和所有已接入店铺当前自有PLID，先真正竞品、再自有链接并按PLID去重；ERP离线或重启时仍会从持久触发与已经开始的未完成断点恢复。运行中每完成25条及收尾前重新读取目标，Seller Offers刷新后出现的新真正竞品或六店新PLID会按发现顺序追加到队尾，不会加入已经结束的历史批次。管理员能在竞品雷达看到与手动批次相同的进度、当前PLID、后台阶段、成功和待重试明细；普通运营不加载这套技术进度，只使用自己的个人监控池和新增链接。常规队列耗尽后如果仍有待重试，09:00服务端批次不会直接把它们搁置成已结束：同一`batch_id`会持久进入10分钟安全等待，按原冻结顺序对失败和未执行项各重试一次，最多执行3轮延时重试；等待、倒计时和自动继续不依赖页面，ERP重启后也会恢复。达到3轮上限仍未解决时才投影为可继续断点，管理员按钮显示“继续待重试（N）”，显式继续仍复用原批次并跳过已成功和已确认失效项，而不是只留下“开始采集”另建新批。`kxx`也可随时停止当前链接和整批；停止后同一触发日期不会被计划任务自动再启，次日09:00照常，但服务端会继续保存原批次编号、冻结目标顺序、成功/失败/终态和逐链接明细。管理员批次控制会显示“继续 09:00 自动批次”，由`kxx`显式继续时按原索引从最早失败项和首个未执行项续爬，不重新读取清单创建新批，也不重采本批已成功或已确认失效链接；ERP重启后该可续状态和最终统计仍从服务端断点恢复。旧的00:30 `track-own-store-followers`隐藏并行计划任务会在安装时移除；该CLI仅保留人工兼容，不再作为正式每日通道。自有链接成功、部分成功或失败仍记录`own_store_follower_tracking`，尚无公开快照的商品继续显示“等待首次检查”。

平台当前会拒绝原来的普通 HTTP 公开接口请求，因此竞品商品、变体和评论改由 Playwright 启动本机 Chrome/Edge 导航公开 JSON 地址；库存仍在另一个隔离匿名购物车会话中探测。命令行批量采集会复用同一个公开数据浏览器会话；ERP 也会在服务器单任务和单链接租约内串行复用隐藏的公开数据浏览器，最多连续处理25条后主动回收，遇到网络失败、浏览器异常、请求取消或服务退出时立即关闭并在下一条重建。可见的匿名库存浏览器仍保持每条链接独立启动、独立购物车和完整关闭，不会跨商品共享库存会话。

竞品中心使用 MySQL 持久化的“监控链接清单”，不再把临时多行文本框当作任务来源。具备竞品采集权限的普通运营可新增链接，链接按PLID去重并自动加入提交账号的个人监控池；只有管理员可修改或删除全局链接、手动插队、查看审计和处理失效复核，后端接口也执行同一角色限制。修改不允许偷偷改变PLID，删除只停用后续监控，不删除商品、评论、变体或历史快照。顶部提交按钮明确为“加入监控队列和我的监控池”：全新或重新激活的真正竞品同时进入两者；识别为自有商品时不重复进入真正竞品清单，但会加入个人池并沿用每日全量巡检；重复链接已在个人池时直接定位，尚未加入个人池时先幂等加入再定位。自有命中路径只更新当前个人池卡片并定位，不再触发整页自有商品投影重载。定位只发生在顶部独立个人池商品区，不再清除下方筛选或跳到“竞品最新状态”；系统自动切换个人池分页、滚动并聚焦对应卡片，以橙色描边、暖色背景、短时脉冲和“已定位到此商品”标签高亮4.5秒。尚未首次采集的链接也保留PLID和“等待首次采集”卡片，不会因没有历史而无法定位。管理员的监控清单默认只显示总数、已有历史和待首次采集三个汇总数，明细默认不创建；点击“打开管理”后使用固定视口弹层，可按名称、PLID或完整链接搜索，并可选择每页20、50或100条，页面只创建当前页链接节点；搜索或切换每页数量后自动回到第1页。粘贴Takealot完整链接时自动提取PLID匹配，不再以内联展开推动下方数百条竞品雷达长列表整体重排。若已有批次正在运行，新加入的真正竞品链接会按新增先后追加到当前待执行队尾，不打断当前商品，也不改变已冻结断点中的原任务顺序；没有活动批次时进入下一次完整采集，需要提前检查时管理员仍可人工点击“插队”。每次全局新增、修改、删除都在同一数据库事务中记录操作用户、北京时间、PLID及修改前后链接。管理员页面的“链接操作记录”也使用固定视口弹层，首次打开才按开始/结束日期请求记录，后端每页最多返回20条，避免操作记录增长后拖慢页面布局。当前最小闭环会：

个人监控池顶部现在把“商品链接、店铺链接、类目链接”分成三个明确入口。商品链接继续要求显式PLID并沿用上述单链接闭环；店铺入口接受`/seller/...?...sellers=<店铺编号>`，类目入口接受末段带数字类目ID的Takealot SEO路径（例如`/camping-outdoor/family-tents-27895`），并兼容`/all?custom=<类目标识>`。SEO类目链接会保留原始类目路径，只叠加受支持的排序和价格筛选；后台继续捕获该页面实际发出的产品列表请求，不猜造类目API参数。店铺/类目不会在粘贴或预览时写库：运营先填写可选最低/最高价格、勾选一种或多种Takealot当前排序并读取公开列表预览。最低价、最高价和最终数量会兼容浏览器返回的数字或文本值再统一校验，空白最高价继续表示不限。默认勾选“评分最高”和“最新上架”；粘贴链接自带的受支持`sort`只会补入当前多选，不会把默认双选覆盖成单项。“价格：从高到低”和“价格：从低到高”都保留，但两者互斥：勾选任一方向会自动取消另一个方向，绕过页面同时提交也会在访问Takealot前被后端拒绝。评分与最新同时选择时，系统先让同时出现在两张榜单候选中的PLID靠前，再比较两边较差名次和名次和，因此“两边都靠前”优先于“只在一边特别靠前”。相关度、价格等额外排序继续参与后续决胜；最终按PLID去重，“加入数量”始终表示最终唯一商品总数，不会按排序数量相乘。预览会显示各入选商品在所选榜单中的实际名次；这是Takealot返回的相对排序证据，不是系统猜出的精确评分或上架日期。价格筛选实际使用Takealot前台`filter=Price:<min>-<max>`，游标翻页复用平台返回的`after`，不会猜造页码。第一次预览会一次性扫描并冻结按平衡名次融合、PLID去重后的候选队列，单次最多保留1000个，同时签发绑定当前账号、约20分钟有效的确认令牌；预览之后修改“最终加入数量”只从这份冻结队列重新截取并确认，不再请求Takealot或重扫候选。筛选总数不超过20时必须纳入冻结队列中的全部商品，即使输入了更小数量也不会截断；超过20时必须在当前候选容量内人工填写1至1000的最终数量。批量确认还必须显式选择一个由当前账号创建的个人类型库，系统不会用默认库代替。确认后在一个数据库事务中再次按PLID区分已有真正竞品、自有店铺商品和全新目标：本次全部入选PLID都会加入当前账号个人池并归入所选库；已有项不重复建立或入队，自有项继续全店巡检但不进入真正竞品队列，只有全新或重新激活的真正竞品写入全局目标审计并在活动批次存在时追加到队尾。后续每个新入队PLID仍走原有商品链接采集，读取全部公开变体、主购买区和`other_offers`跟卖报价。

管理员在店铺和类目入口下各有独立的折叠“链接操作记录”。只有点击“确认加入”才生成记录，预览和冻结候选队列都不会留痕；操作头默认每页10条，展开某次确认后才按每页20条读取本次最终有序商品。操作头保存本次强制选择的个人类型库ID与名称快照；明细保留完整商品链接、PLID、标题、各排序名次，以及新增目标、重新启用、已有目标或自有商品的处理结果，并标明本次是否新加个人监控池。记录和目标变更处于同一数据库事务，升级前没有可靠来源或类型库证据的旧操作不会回填。店铺/类目链接仍只是人工来源扫描条件，不是持续定时来源；需要按最新商品集合重扫时才在对应入口重新预览，单纯调整本次确认数量不需要重扫。

每次采集还会检查全部公开变体的主报价与`other_offers`。PLID代表商品线，同一商品的多个卖家报价通常共享PLID，因此监控清单和爬取队列按PLID去重：该PLID只抓取一次，返回的全部报价保存在同一快照中并优先按公开`offer_id`或`other-buying-option-<SKU>`购买卡片标识区分，均缺失时使用卖家、SKU、变体和商品条件组成的保守稳定键。只有报价明确指向不同Takealot URL/PLID时才会自动增加另一个监控目标；已有活跃目标不会重复新增或重复入队。无法识别报价身份时不会猜造链接，用户提交的原始链接始终保留。启用库存探测后，同一商品的隔离匿名会话会逐个清空购物车并探测变体主报价和可购买跟卖报价：跟卖加购前核对购买卡片ID/SKU与卖家名，购物车内再核对PLID与卖家名，取得的精确或至少数量只写入该报价；供应商调货或明确不可加购记0，校验失败则保持缺失并进入库存复探，不会复制主报价库存。管理弹层按“原始商品链接 + 全部卖家报价”折叠成组，组内内容只有展开时才创建，并显示Offer ID、卖家、价格、报价级涨跌及各报价自己的库存状态/变化；不同PLID目标的自动发现或重新激活使用独立`auto_discover`审计。

Takealot新版页面已不再渲染`other-buying-option-<SKU>`节点ID，跟卖报价区还可能默认收起或延迟加载。库存探测会主动展开报价区，以卖家ID、精确卖家名、SKU和价格定位其唯一`buying-choice-list-item`报价行及行内`buying-choice-atc`按钮。已打开的条款对话框只在对话框内关闭，不会误点页面上的`T&Cs Apply`入口；随机出现的Braze遮罩会在精确报价按钮点击前再次清理。上文“购物车卖家名核对”适用于仍显示卖家的页面；当前新购物车已隐藏卖家名，因此只在前述报价行身份已完整核验，且隔离购物车的PLID和精确价格均一致时继续取量；若购物车实际显示其他卖家，即使价格相同也会拒绝。

区间重算同时给真正竞品和自有商品计算“周期内销售额”观察值：先按卖家、SKU、变体和条件库存范围分组，再按每组相邻精确库存点逐段计算；库存下降量乘以后一个有效点价格后累加，中间补货不会抵消已经观察到的下降段，补货量和补货货值另行累计。缺失点、非精确库存点以及不足两个精确点的单点范围全部跳过；同一范围跨过这些点后按前后净变化连接，不同范围各自计算且不跨范围相减。过滤后只要至少一组仍有两个精确点，就汇总所有可比较范围的售出和补货；整个区间没有任何可比点对时才保持数据不足。周期销售件数大于0的商品进入“库存减少”经营信号，并按该件数（页面显示为“区间内售出件数”）排序，所以区间末库存即使因补货高于区间初库存，已经观察到的售出件数也不会被排除或抵消；周期补货量大于0的商品进入“补货”经营信号，期间后续售出也不会把已经观察到的上升段抵消。只有周期销售件数和周期补货量都完整、两项都为0且库存可比时才进入“库存数量不变”；任一项大于0或区间动作数据不完整都不得归为不变。“补货”和“库存减少且评论增加”按周期销售额排序；“库存变化大”按“周期销售额 + 周期补货货值”的同币种库存周转金额排序，并在卡片中同时披露下降件数、补货件数和补货货值。详情中的当前卖家/报价使用同一分组过滤口径。发生库存变化但后点价格缺失时仍可保留件数，金额保持缺失。上述数值只是公开库存/Seller API库存的观察金额，跨跳过点只能表示前后净变化，可能受购物车占用、取消、调拨和补货影响，不是Takealot真实已付款订单收入。

竞品雷达主列表的筛选区只保留商品/店铺、库存、跟卖、个人池、经营信号、排序、观察区间和重算控件；筛选区与商品列表之间不再展示整段计算方法说明。计算口径继续由详情指标提示、代码、测试和本项目文档维护，页面精简不改变区间重算、筛选、排序或权限逻辑。

竞品雷达中所有商品级展示区都附带对应商品快照主图；变体库存则从每个非默认变体自己的公开详情 gallery 保存独立图片。详情中的当前变体表和每个区间历史快照都会按快照 ID 展开当时全部变体的可读名称、库存、限购标记和专属同源 192 像素缩略图，不会把 API 返回的字典/JSON 字符串直接显示为名称。自有Seller API Offer也带出各自TSIN和图片，同一PLID跨店重复Offer按TSIN归为同一实际变体。用户在卖家连续对比台切换任一自有或竞品变体/报价时，详情左上主图同步切换到所选项图片；只有所选项缺图时才回退商品主图。默认款没有独立变体图时使用所属商品快照主图；颜色、尺寸等非默认旧变体缺图时才显示“暂无图片”，不会拿统一主图冒充；任何图片加载失败也不会留下破图图标。

库存不是 Takealot 全平台物理总库存，而是采集时每个变体在当前匿名会话、当前卖家和当前 SKU 下的平台仓购物车可售上限。同一PLID下的各卖家报价先分别保存公开库存状态；匿名购物车探测到的精确或至少数量只绑定给实际测试且变体键、SKU、卖家一致的变体主报价，不会复制给其他跟卖报价。其他跟卖报价若公开数据没有可核验数量，页面只显示“有货/没货/未知”状态，数量保持缺失，绝不补成0。尺寸、颜色等选择器会被组合枚举，页面“各变体库存”逐行展示；当前不可加入购物车的变体直接显示“没货”。无论提示出现在快捷数量还是自定义数量校验中，只要页面出现 `current stock = N` 明确警告，程序就立即把 `N` 保存为精确平台仓库存并停止该变体的所有后续数量尝试。若出现 `Limited to N per customer`，程序会实际验证限购数量 `N`：该数量可以加入时只保存“至少 N”，并标记“每位客户限购 N 件”，不会把促销限购当成精确库存；只有限购数量仍无法加入时才继续在其下方校验库存。确认 9 件可加入后会先验证 10 件；平台提示 `We currently do not have 10 in stock.` 或明确拒绝 10 件时记录为精确 9 件，程序也会在输入框未出现时继续读取页面弹窗。若只是 `10+` 输入框打不开/无法完成输入，且没有明确缺少 10 件的提示，则仍保守显示“至少 9 件”。只有 10 件明确被接受才继续超量测试和二分校验。首次打开数量菜单时会等待动画并最多重开3次；仍读不到数字选项就刷新购物车一次、重新核对同一 PLID 后再试，避免页面慢加载造成偶发“未探测”。数量控件显示更新成功后会留出短暂提示结算窗口，避免平台警告稍晚出现时被误判为已接受。只有999件仍被接受或后续页面拒绝继续验证时才显示保守下限。探测会等待异步加购落库、重试数量菜单动画和临时购物车更新错误，并只把 `aria-hidden` 未启用的数量输入框视为可编辑控件；Braze 营销遮罩只在阻挡目标控件时被清理。本次最终仍未探测成功时，当前库存继续为空；页面只在 SKU、卖家和变体集合一致时显示“上次成功库存 + 时间”的过期参考，该值不会回填当前库存，也不参与库存净流出和销量计算。公开接口标记为 `is_leadtime` 的供应商调货/长时效到货变体不计入有效平台仓库存，统一显示“没货”，也不参与库存净流出销量推断。评论属于 PLID 商品维度，所有变体共用同一份评论，不重复抓取或计数。竞品页面不展示基于评论率反推的累计销量估算；库存变化和观察期评论信号也不是官方销量，补货、购物车占用、取消和评论延迟都可能影响判断。

竞品详情顶部使用“卖家连续对比台”，左侧在同一位置切换卖家，右侧直接比较当前卖家的区间历史，不再要求每切换一次卖家就重新滚动到快照区。卖家默认按所选区间首尾可比的精确库存净流出排序，也可切换为价格、当前精确库存或原始顺序，并支持“上一个/下一个”连续查看；库存净流出只是一种观察信号，不等于实际出货或订单，补货也会改变排序。基础历史视图是共用时间轴的价格、精确库存和PLID共用评论数三组折线；自有链接选中精确Seller API自有报价时追加“近30天浏览量”第四组，四组保持相同的横轴范围、左右边界和纵轴版式，各自保留独立量纲。第四组直接读取与价格/库存同一条逐次Seller Offer观察，只接纳时间戳完全相同的节点；历史无法从明确日报运行或完全相同旧快照恢复的点保持缺口，不再做最近节点吸附。流量场景下卖家导航位于图表上方，四联图使用整行宽度。四联图在桌面短视口使用392单位的紧凑绘图区，并在窗口高度不超过900像素时同步压缩该详情弹窗的页头、固定详情和页脚间距，使约855像素高的常用桌面窗口可同时看到固定详情框与四组折线；普通竞品三联图使用346单位布局，窄屏或更低窗口仍保留弹窗滚动作为兜底。各指标区使用浅色背景，并在相邻指标之间绘制清晰实线分隔，避免把不同量纲误读成一张连续图。曲线和图框均不添加阴影。图表上方固定显示当前报价的区间售出观察件数与共用时间点详情，默认详情为最新报价时间点；鼠标在图中横向移动或使用左右方向键时，只切换具体北京时间、价格、库存状态/证据、评论数及同次真实流量记录，详情框本身不会跟随指针移动，也不会在移出图表后消失。区间件数会跨补货段累计库存下降；缺失和非精确点会跳过，卖家、SKU、变体或条件不同的库存范围分开累计，任何不足两个精确点的范围不参与。过滤后若没有任何同范围精确点对才显示数据不足。库存不是精确值时图上仍保留断点，不把“至少”或未知数量连成精确库存折线，每条曲线仍只使用当前卖家的兼容报价，不回退到主报价或其他卖家。

竞品详情的“公开评论”支持把好评/中评/差评与起止日期组合筛选，并可按最新评论、最早评论、评分从高到低或评分从低到高排序；页面会显示筛选后的评论数和该商品评论总数。没有评论日期的记录在未设置时间范围时保留，设置时间范围后不纳入结果。

库存探测严格以输入链接中的 PLID 为目标：程序只点击该商品页右侧主购买区的 `Add to Cart`，不会点击“You Might Also Like”“What’s Hot”等推荐商品。跳转购物车后还会再次核对目标 PLID；找不到目标商品就让本条库存探测失败并清空购物车，不会拿其他商品的库存冒充竞品库存。

大量链接首次建档时，可在页面关闭库存探测，先快速采集公开商品与评论；后续再分时补充库存。单个链接失败不会中断整批。

勾选库存探测时，如果商品与评论已经成功但一个或多个可购买变体最终仍为“未探测”，系统会保存已取得的快照，同时把该链接保留在“待重试”，不会误记为完整成功，也不会把它计作断网熔断。每个失败变体会按变体名称、SKU、失败阶段和技术原因持久化说明，例如“打开购物车失败：连接在页面加载时被关闭（ERR_CONNECTION_CLOSED）”；同一原因也会进入当前运行提示和逐链接结果日志，不再只显示笼统的“1/1 个未探测”。第一次自动复探前至少先执行1条其他待执行链接，第二次自动复探前至少先执行2条；总计初次探测加2次自动复探。若当轮剩余任务不足以满足间隔，不会退化为队尾立即复探，而是继续保留待重试，供人工插队或以后继续。复探安排和运行中新增链接都属于普通进度提示，不会再被写入批次停止原因或导致当前商品结束后误暂停。主动关闭库存探测、供应商调货和明确不可加购不属于失败。

竞品最新状态卡片列表顶部提供组合筛选器：关键词可匹配商品名称、PLID、完整Takealot链接以及卡内全部卖家、Offer ID、SKU或变体；粘贴完整链接时自动提取PLID，再叠加“有货 / 没货 / 未探测”库存状态和固定十二类经营信号。真正竞品分区另有“竞品店铺”搜索选择器，可输入数字`sellers`、公开报价偶见的`M`前缀ID或店铺名，也可从当前全部对比报价汇总的自动完成选项中选择。系统以去除`M`前缀后的`sellers` ID作为稳定身份键，同一ID跨商品只显示一次并标出唯一PLID数量；店铺名可能改名或重名，只用于显示和模糊搜索，同名不同ID不会合并，报价未返回ID时才回退为名称匹配。经营信号只保留“降价、涨价、价格不变、补货、库存减少、库存数量不变、库存变化大、评论增加、好评增加、差评增加、库存减少且评论增加、新增跟卖卖家”。区间重算得到的周期补货量大于0即归为“补货”，周期销售件数大于0即归为“库存减少”；只有旧数据缺少对应周期字段时，才分别回退到“检测到补货”/报价库存增加或恢复有货，以及商品总库存净流出/报价库存减少或转为没货。周期销售件数和周期补货量都完整时，只有两项均为0且库存可比才归为“库存数量不变”；只要发生补货或库存下降，即使期初与期末库存相等或某个报价自身未变，也不得再把商品归为不变。旧数据只有在两项周期动作字段都缺失且不存在补货/减少信号时，才允许按首尾精确库存为0或报价精确数量不变回退。同一观察区间PLID评论总数、4–5星好评数或1–2星差评数增加时分别进入对应评论类别，同时发生库存减少和评论总数增加时再进入组合类别；系统首次观察到某卖家的日期落入所选区间时进入“新增跟卖卖家”。评论信号属于PLID商品，不能归属到某个卖家。待建立基线、价格/报价/库存不可比、库存状态不变和旧技术趋势名称不再作为经营信号选项或醒目标签，但原始字段、区间数值、判断说明和详情证据继续保留。列表不再另设一套排序指标选择器；选中经营信号后，真正竞品与自有链接两个分区只用旁边的升序/降序控件，自动按该信号对应的价格变化、区间内售出件数、周期销售额、库存周转金额、库存净变化、评论增量、好差评增量或新增跟卖卖家数排列。选择“全部”时保持原顺序并禁用方向，缺失变化值始终排在有值记录之后。页面实时显示筛选结果数与商品总数，支持一键清除；本次库存未探测、仅显示上次成功过期参考的商品归入“未探测”。明细支持上一页/下一页，并可选择每页20、50或100条；页面只创建当前页商品卡片，筛选、排序或切换每页数量后自动回到第1页。这些筛选、排序和分页只处理当前已经读取的列表，不会重新采集平台或写入数据库。

共享搜索会把缺失、空值和数字字段统一转换为安全字符串后再匹配；自有商品记录没有真正竞品专属字段时也可继续粘贴完整Takealot链接搜索，不会再因读取`undefined.toLocaleLowerCase()`进入整页错误状态。监控链接管理使用同一空值安全规则。

加入个人监控池时，服务端会按当前账号最新店铺授权重新核对自有商品归属，而不是只依赖页面隐藏。直接加入个人池、真正竞品或共享库卡片加入、单商品链接新增、店铺/类目批量确认都使用同一硬边界：若PLID只属于当前账号无权查看的已接入店铺，接口返回403并提示调整选择或联系管理员授权；错误不会显示无权店铺名称或私有详情，也不会写个人关系、类型库归类、全局目标、操作记录、审计或活动批次。若同一PLID同时存在于有权和无权店铺，只要至少有一个所属店铺可见就允许加入，但响应只显示有权限的店铺。店铺/类目整批中只要命中一个禁止项就整批拒绝，原冻结候选仍可直接减少最终数量后再次确认，无需重扫Takealot。该校验只阻止新增，不会自动删除既有个人关系，也不改变全局采集和历史。

竞品雷达把当前账号的个人监控池固定为所有角色标题后的第一块独立商品区，不再使用“查看我的个人监控池”按钮跳到下方自有店铺/真正竞品列表。区域直接按账号关系分页展示真正竞品和自有商品卡片，并提供与完整商品工作区一致的“真正竞品 / 自有商品跟卖”来源标签，以及商品名/PLID/完整链接/卖家搜索、竞品店铺、库存状态、互斥的“现在被跟卖 / 曾经被跟卖 / 未发现跟卖”跟卖状态、个人类型库、经营信号、信号升降序、每页20/50/100条和北京时间观察区间选择；竞品店铺只对真正竞品来源生效，自有商品缺少竞品专属字段时也能安全筛选。所有选择器只重排当前已读取的个人关系卡片，不采集上游、不写库；“按区间重算”则会把所选北京时间范围重新提交给后端，同时刷新真正竞品和自有商品的周期销售额、补货量及经营信号，不能只改页面日期文案。整页刷新时，页面会与完整1200余条雷达投影并行，优先按当前账号个人池和可访问共享库中的PLID读取小投影；小投影始终读取当前账号全部可访问、启用且已接入的店铺，不受顶栏当前查看店铺影响，也不能因提速绕过私有店铺权限。从个人监控池或其中的共享类型库卡片打开商品详情时，详情对象、卖家连续对比、报价历史、自有销量及近30天浏览量继续使用同一账号全店授权范围，切换顶栏当前店铺不会把其他获授权店铺从弹层中剔除；从下方普通自有商品工作区打开详情时则继续遵循顶栏当前店铺、全部店铺或我的运营店铺范围。小投影返回前只显示“正在恢复”，不能把已采集商品误报为首次采集；返回后，共享自有商品若与账号全部授权店铺没有交集，会明确显示“无权查看店铺详情”并隐藏店铺名称、图片、商品名、价格、库存和Seller API私有详情；账号有权但当前Offer没有返回详情时显示“店铺详情暂不可用”；无法确认来源的共享PLID显示“商品详情暂不可用”。这三种情况都不会误报“等待首次采集”或要求重新粘贴链接，只有确定为真正竞品且确实没有成功快照时才显示等待首次采集。新增后定位会自动切到卡片所属来源、清除冲突筛选、翻页并高亮。已有快照显示图片、商品、价格、库存、周期销售额和最近采集；卡片可打开商品详情、从个人池移除，管理员还可进入原有监控队列操作。共享类型库中只由个人池小投影返回、尚未出现在当前主列表分区的自有商品也直接使用该小投影对象打开详情；只有详情对象实际存在并能渲染弹层时才锁定页面滚动，数据变化使详情对象暂不可用时必须立即解除滚动锁。每个账号可创建、命名、重命名或删除自己的纯白类型库，一张卡可同时进入多个库；个人池顶部明确分为“我的监控池 / 我的类型库 / 共享给我”，空库也保留入口。创建者可从全部系统用户中逐人授予“只读”或“可编辑”：只读只能查看；可编辑可把自己的个人池卡片加入共享库并移除库内卡片，还可把该共享库设为自己的新增链接默认归类，但不能改库名、删除库或管理分享。共享库只传递库信息和PLID，不会自动把商品加入接收者个人池；卡片价格、库存及Seller API私有详情仍按接收者原有店铺权限读取，无权数据不会因分享暴露。普通单商品新增可选择自己创建的库、共享给自己且可编辑的库，或明确选“不自动加入任何类型库”；只读共享库不能作为默认，分享被撤销、权限降为只读或库被删除后，引用该库的默认设置立即失效并要求重新选择。店铺/类目批量确认仍必须逐次显式选择一个自己创建的库，不能直接走默认。新增、归类、个人删除或共享库移除成功后会重新读取响应式库数据，角标即时更新，最后一张卡移除后直接显示0而无需手工刷新。输入框和按钮继续保留全局监控含义，按钮文案为“加入监控队列和我的监控池”；新增或重复成功后自动翻到对应页并高亮定位。管理员的共享链接与批次、全局指标、链接失效复核紧随个人池，仍排在商品经营区之前；普通运营不渲染或轮询这些管理员模块。个人池归属始终私有，管理员也不能读取未显式分享给自己的类型库。个人删除、库内移除、撤销分享或删除库都不停止全局每日采集、不移除活动批次、不改变自有全量巡检，也不删除历史。

竞品最新状态对真正竞品和自有商品都按PLID每个商品只创建一张紧凑父卡片，不会把同一PLID的多个卖家报价或跨店重复Offer拆成多个商品；不同PLID即使标题相近也保持独立，避免错误合并。自有卡片按TSIN优先统计真实变体数。自有商品分区不再提供含糊的“有被跟卖”，改为互斥的“现在被跟卖 / 曾经被跟卖 / 未发现跟卖”选择器；“现在”只认所选区间末次快照仍存在的跟卖报价，“曾经”只认区间内出现过但末次快照已消失的跟卖。详情弹窗的“卖家连续对比台”按规范化卖家名称去重，同一卖家的不同SKU、变体和报价放在同一个卖家组内，再在组内切换具体报价；“上一个/下一个”按卖家组移动，不会把同一卖家的不同变体伪装成多个卖家。自有Seller API Offer与公开跟卖使用同一套价格、库存、变化、变体图片和历史展示，但继续标明数据来源；精确库存只显示在Seller API明确返回或真正匹配购物车探测身份的报价上，非精确值标为“至少”，其他报价若公开数据没有数量则明确显示“数量未返回”且继续保留有货/没货/未知状态，不补0。旧快照没有可区分报价时保留原始链接并明确不猜卖家、Offer ID或库存数量。窄屏下对比台改为单列，卖家导航、组内变体和悬浮明细按可用宽度重排，不产生整页横向滚动。

每张竞品最新状态商品卡都支持直接点击或键盘回车/空格打开完整详情弹窗，无需滚动到页面底部；个人监控池、个人/共享类型库、真正竞品和自有商品跟卖的小卡也复用该弹窗。标题区显示最近一次已保存的Takealot公开面包屑完整类目路径，并在上游提供时显示末级类目ID；打开详情只读本机MySQL，不会现场访问Takealot。升级前历史快照没有该字段时会明确提示后续成功公开商品采集自动补齐，不用标题、来源店铺、类目扫描链接或商品URL猜测。弹窗顶部的卖家连续对比台把卖家切换、区间排序和历史折线放在同一视口；选中某个卖家后，卖家专属的价格、库存、涨跌信号和折线随选择切换。折线只包含真正匹配当前卖家兼容报价的时间点，不为没有该卖家的日期创建“未识别”占位，也不会回退到PLID主报价或其他卖家数据。Offer ID继续采集和保留为最强身份依据，但页面不强依赖它；界面以卖家、SKU、变体、价格和库存为主，Offer ID仅在有值时使用更小、更浅的辅助文字展示，未返回时不重复创建提示。Offer ID缺失或变化时，只有卖家ID/名称一致且SKU、变体和条件不冲突、同一快照候选唯一时才连接。只按卖家名称无法唯一识别报价，同卖家多SKU或候选歧义时保持不匹配。平台对变体主报价没有返回Offer ID和卖家时，系统只在同一PLID、同一变体主报价且已保存唯一变体明细的范围内，用“变体键 + SKU”建立匿名报价身份，并把该变体已经核验的价格和库存投影到报价历史；SKU变化或出现明确卖家后仍视为另一条报价，不跨卖家连接，普通跟卖也不使用这一回退。评论与商品变体表按同一PLID商品共用：Takealot评论没有卖家或Offer ID归属，因此主报价与跟卖共用同一份商品评论，不伪装为卖家专属评价。监控队列继续按PLID去重，切换报价不会重复加入队列。弹窗完整提供评论分类、起止日期组合筛选、日期或评分排序和评论全文。对比台之后的“监控队列操作”卡允许修改、删除、活动批次插队或重新加入PLID链接。商品详情和卖家报价都不再重复铺在最新状态卡片列表下方，长内容只在弹窗内部滚动，顶部商品标题和底部“打开当前卖家报价页 / 关闭”操作保持可见。“任务爬取详情”内的成功任务和待重试任务也都可以点击或用键盘打开同一套监控队列操作页；待重试入口会明确显示“人工重试并插队”。

梯子或代理短时不稳定时，公开数据浏览器启动会自动重试；无论预热失败、请求取消还是页面超时，程序都会强制关闭页面上下文、Chrome 和 Playwright 驱动，不允许遗留后台浏览器进程。只有真实导航失败、429 或 Takealot 5xx 才归入连接类错误；页面内容暂时无法判定会单独保留重试，不会累计断网次数。404疑似失效、409页面不确定、单条浏览器连接失败和5xx等普通可恢复失败使用按任务数计算的指数退避：三次自动重试前分别至少执行1、2、4条其他待执行链接。若当轮剩余任务不足以满足间隔，不会为了凑次数把失败项直接塞到队尾立即重试：人工批次继续保留在“待重试”，供人工插队或以后继续；09:00服务端批次则在常规队列耗尽后进入上文10分钟延时轮次。库存未探测仍使用上文总计3次探测、间隔1条和2条任务的规则。明确失败的链接不会因为同一PLID曾经成功或插队成功过而从续爬队列消失，后续任一次成功会立即清除旧失败状态。批量页面连续两条出现真实连接或 Takealot 临时服务错误时会暂停剩余链接，保留此前已成功写入的数据和当前进度，避免断网期间继续空跑全部链接。恢复网络后可重新提交失败链接。

首次遇到商品公开数据 404 或链接仍处于“疑似失效”时，不会删除链接，也不会直接当成永久失效。系统会在同一个 Playwright 浏览器中同时检查目标商品页和最近成功采集的已知正常商品：Takealot 的 `404, Page Not found` 标题或正文会被明确识别为不存在页面，不能因为404页自身也有标题就误认成商品；正常商品则使用商品标题和页面商品内容识别，不依赖单个可见标题在固定8秒内出现。如果对照或目标内容暂时无法稳定判定，本次单独标记“页面复核结果不确定”并保留重试，不计入连接失败；只有目标明确为404页且正常对照可打开，才记录一次有效的“疑似失效”。至少间隔10分钟累计3次有效复核后才首次转为“确认失效”。已经长期确认失效的链接在后续批次只需复核一次：公开商品数据再次返回404时立即维持“确认失效”并作为本批终态，不再重复三次页面和对照检查；403、导航失败、429、5xx等连接异常不算完成复核，仍会保留重试。任意一次后续采集成功都会把状态重置为正常。竞品雷达的“链接复核状态”默认只显示疑似/确认数量并保持收起，需要核对时再展开复核次数、对照 PLID 和最近检查时间，避免平时占用页面空间和创建整张复核表；疑似或确认失效行本身可以点击，即使没有成功快照，也能直接打开对应 PLID 的监控队列操作页，执行修改、删除、活动批次插队或重新加入。

每次点击“开始采集”都会以当时重新读取的真正竞品和自有PLID建立一个独立人工批次，并把链接顺序、已检查位置、待重试位置、已确认失效位置、成功 PLID、运行状态和当前链接请求编号保存到当前浏览器的本地断点。采集中整页刷新或前端重新加载时，ERP 会自动回到竞品雷达并从当前链接恢复，不需要再次点击“继续”；前端会用本地批次编号识别这是刷新前由当前页面启动的同一批次，并用保存在当前标签页的客户端编号重新接回。服务进程仍在时，恢复队列会把服务端仍在执行的当前链接放到最前面，并复用同一请求编号等待原后台探测任务完成，然后才回到最早待重试项，避免刷新后旧请求与待重试队列同时争用 Playwright 浏览器；运行期间其他用户新增的监控链接由服务端按新增顺序保存为待执行队尾项，持有页面每2秒同步并追加写入同一浏览器断点，原任务顺序不变。09:00自动批次不依赖任何浏览器断点，服务端持久保存冻结顺序、当前项、结果、错误、重试队列、延时轮次和下次自动继续时间；ERP退出时当前项仍视为未完成，重启后先恢复该项，处于延时等待时则继续原倒计时。人工停止的手动批次不会自动继续；`kxx`停止自动批次后同一触发日期也不会自动重启，但可在管理员批次控制中显式继续同一服务端断点。自动批次完成3轮延时重试后仍有失败项，也会投影为同一种可继续服务端断点。继续时复用原`batch_id`，按冻结索引重建失败/未执行队列，已成功和已确认失效项保持跳过；“开始采集”入口在存在该可续自动断点时不会另建人工批次覆盖操作语义。手动“继续失败/未完成”仍按本批已经冻结并保存的链接顺序恢复，不受此后监控清单增删改影响：此前成功的商品即使穿插在待重试项后面也会直接跳过，只重试疑似失效、其他临时失败项和尚未执行项；已确认失效链接在本批后续续爬中自动跳过。这里的跳过仅依据当前批次成功/确认失效记录，不会因为数据库中存在昨天的快照而跳过今天的新采集。历史已确认失效链接会进入新批次，但只要公开商品数据再次返回404就立即作为确认失效终态，不会重新排队累计三次复核。

刷新或切换店铺时，竞品页会优先沿用当前未完成断点的客户端编号，并在页面退出前主动释放同源页面通道。为避免旧页面尚未完全卸载造成误判，只有同一实例连续响应两轮探测才认定为真实的“本账号另一页面”；只响应首轮的刷新瞬时重叠不会换发客户端编号。真正复制或另开的标签页仍会取得独立编号，并继续由服务端单批次租约阻止并发采集。

如果`kxx`在人工批次运行中退出登录、会话过期或切换到另一个账号，竞品页会在会话被替换前立即安全脱离：只取消旧页面对当前请求的等待，不停止服务端已开始的当前商品，也不再由旧页面请求剩余链接；401/403不会被误记为剩余商品失败。断点继续保留当前索引和请求编号，原账号`kxx`重新登录后可以复用同一请求恢复，其他账号仍不能继续或停止该批次；旧会话迟到的401也不会把随后登录的新账号踢出。该行为不是把人工批次变成完全后台运行：当前商品完成后，剩余队列等待`kxx`恢复；需要完全不依赖浏览器的整批运行时使用09:00自动批次，或在独立Chrome个人资料中保留`kxx`会话。

如果梯子、网络或 Takealot 临时服务异常造成连续2条真实连接失败，手动与09:00自动批次都会暂停剩余链接并立即保存各自断点，同时显示距离下次自动尝试的10分钟倒计时。暂停原因逐条记录造成熔断的两个PLID、浏览器连接失败或HTTP状态和接口返回原因；新增链接、插队和库存轮后复探提示不参与计数。Takealot公开API或商品页持续403也按临时连接异常处理。倒计时结束后自动从失败/未完成链接继续；如果VPN仍异常则再次暂停。手动批次把重试时间写入浏览器断点，页面刷新后继续倒计时；自动批次把暂停时间写入服务端断点，页面是否打开或ERP重启都不丢，并在暂停期间持续发布共享状态，让`kxx`仍可停止。人工停止、链接校验错误、权限不足、链接确认失效和零待重试的正常完成均不会触发自动重启；09:00批次的尾部延时重试属于原批次内部续爬，不是新一轮每日启动。手动批次还可在倒计时期间点击“继续失败/未完成”提前重试。

服务端把每个批次的开始、手动/自动恢复、暂停、人工停止、完成，以及每条链接的开始、后台数据浏览器、商品与变体、全部评论、库存浏览器、快照保存、结果、请求复用和异常阶段写入 `logs\competitor-collection.log`。库存未探测结果包含失败变体、SKU、失败阶段和精简技术原因；连接类暂停包含连续两条失败的 PLID、状态和原因。同一阶段同时发布到共享批次状态，管理员页面每2秒能看到当前链接正在后台读取数据、复用后台浏览器、启动库存浏览器还是保存快照，普通运营不轮询这套技术状态。从第二条链接起，服务端会在每次公开数据浏览器租约前统一随机冷却5至10秒，即使刷新页面、使用旧前端或上一条网络失败后重建浏览器也不能绕过；前端仍只保留1秒界面交接，不作为真实限速边界。公开浏览器首次预热成功后再随机等待4至7秒，每次变体请求前等待3至6秒，每个额外评论页等待2至5秒；403、429、超时和5xx的原有退避重试保持不变。日志按大小轮转，方便以后区分是页面刷新、人工操作、随机节流、网络暂停还是具体 PLID 异常；日志不记录账号密码和会话密钥。

新增或修改监控链接时，前端会先检查 URL 格式、Takealot 域名和 PLID，服务端再执行同样的强制校验；其他平台链接不会写入清单或送入采集。已有链接修改时必须保持原 PLID，不同商品应先删除旧链接再新增，避免历史身份被改写。

管理员启动人工竞品采集后可以切换到其他 ERP 页面；竞品雷达页面会保持采集实例，返回后继续显示原输入、完成数量、进度条、成功结果和失败说明，不会因为导航切换而清空。

竞品批量采集同一时间只允许一个服务器级批次运行：人工批次由一个账号和浏览器标签页持有，09:00自动批次由正式ERP服务端驱动，但二者共用同一串行租约，不能并发开启第二个Playwright配置。当前来源、操作者、已检查/总数、成功、待重试、确认失效、待续爬、正在处理的PLID和当前采集阶段统一保存在服务端；管理员竞品页的“任务爬取详情”按“成功任务”和“待重试任务”展示同一服务端明细，普通运营页面不加载这套技术进度。服务端对当前请求编号持有单链接租约：页面刷新可以用相同请求编号接回，但另一条链接会被拒绝；自动批次也通过同一个单链接执行入口和协调器，不存在隐藏的第二进程。临时403、网络或服务异常只进入“待重试”，对应链接后续成功后会从该计数移除；“确认失效”取持久化链接复核状态并合并本批刚确认的链接，不会被其他链接成功清零。批次占用期间运营新增项仍按新增顺序追加到当前批次队尾；全局修改、删除和插队只允许管理员，且修改和删除只影响后续新批次，不篡改已经冻结的运行队列。“开始采集”和“继续失败/未完成”在其他批次占用时会显示醒目的橙色提示卡；09:00批次明确标注“每日09:00自动任务”。只有`kxx`可停止活动批次，即使当前页面没有本地断点也会使用共享批次编号提交服务端取消；当前库存探测会跳过慢速清理并关闭库存浏览器和复用公开浏览器。手动批次保留当前索引供恢复，自动批次则持久化未完成当前项供ERP重启续跑。

活动批次运行期间，新保存的监控链接由服务端按保存先后追加到待执行队列末尾，不打断当前正在探测的商品，也不重排断点中已经冻结的任务；连续新增多个链接按先增先执行，刷新或断点恢复后仍保持队尾顺序。管理员若需要提前检查，可在监控链接明细中人工点击“插队”：服务端会在当前正在执行商品之后额外增加一次优先探测，当前浏览器探测不会被强行中断；该链接在原队列中的位置不会被删除，队列走到原位置时仍须按原顺序再探测一次。服务端会在本批保留已接受的手动插队记录；按钮请求成功后立即变为禁用的“已插队”，同一PLID尚未消费的重复请求按幂等成功处理，不会安排多个优先副本。从管理员“待重试任务”点击进入时，按钮会显示“人工重试并插队”，请求使用独立`manual_retry`来源并记录操作人、北京时间、PLID和URL；上一条人工重试已经开始执行后允许再次发起，仍在待执行队列中时重复点击不会增加副本。尚未消费的队尾追加项和手动插队指令同时写入`logs/competitor-batch-queue.json`，ERP重启后同一批次恢复时继续执行；目标真正开始后才从待执行指令中移除，批次完整结束后自动清理文件。

竞品批次的开始、自动/手动继续和停止只认用户名 `kxx`，不按管理员、运营或选品模板放权；其他任何账号即使使用管理员模板，也不能通过页面或接口启停批次。具备竞品采集权限的管理员可新增、修改、删除全局链接、手动插队并查看审计/失效复核；非管理员只可新增链接并管理自己的个人监控池。后端会强制执行这些边界，不能靠修改前端按钮绕过。

`kxx` 可在人工批次或09:00自动批次运行中随时开启或关闭“显示检测浏览器”；即使自动批次显示由“每日09:00自动任务”持有，任何已登录的 `kxx` 页面仍可修改。设置由服务端批次统一保存，当前执行链接保持启动时的原设置，从下一条任务链接开始生效；人工批次同时保存到浏览器断点，自动批次保存到服务端运行断点，ERP重启后继续沿用。其他管理员只能查看共享设置，不能修改；普通运营不显示这项管理员控制。若原始人工采集标签页仍在运行，同账号新页面可点击“接管并继续待重试”；服务端会等待当前商品及其浏览器清理结束后才转移客户端租约，旧页面的下一条请求会被拒绝，因此不会产生两个库存浏览器并发。ERP 重启后服务端人工批次已释放时，新页面也可显式接回同源 `localStorage` 中的既有断点，只继续失败和未完成项，不重跑本批已经成功或确认失效的链接。

共享批次中的失败集合统一标为“未解决”，表示这些链接尚未完整成功；库存复探或普通自动重试执行期间该数字可以暂时不变，只有某条链接成功后才减少。当前卡片会另外显示库存复探/普通重试的次数和实际后端阶段，不再让固定的未解决数字冒充重试执行进度。

活动批次期间，管理员页面的进度条以及成功、待重试、确认失效、已检查、待续爬和逐链接明细统一读取服务端共享批次状态；普通运营不渲染或轮询该管理员模块。非批次持有的管理员页面不得把自己的旧浏览器断点统计混入当前批次。09:00自动批次结束或被停止后继续在管理员模块展示该批次的最终共享统计与明细，避免回退成某个页面的旧本地结果；普通人工批次没有活动状态时，页面才用本地断点数字提示可恢复任务。

当前交付是最小模块。原独立工具中的关键词/类目排名、持续卖家上新监测、Buy Box 历史占有率和六工作表 Excel 尚未迁入；店铺/类目人工来源扫描不等于这些历史信号，这些信号不会在当前页面中伪装成已支持。

### 保留的运营日报后端周期版本

统一 Vue 前端已不再提供运营日报模块；本节只说明仍保留的后端、CLI、MySQL、计划任务与 Excel 兼容流程。运营日报不会让后一次采集覆盖前一次值。核对周期固定为北京时间当日 10:00（含）至次日 10:00（不含），周期内全部定时采集和手动完整刷新都归入同一个日报业务日并逐次保存。例如 7 月 25 日 10:00 至 7 月 26 日 09:59 的所有版本都归入 7 月 24 日日报。四个计划阶段分别运行：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli daily-report-run --slot morning
.\.venv\Scripts\python.exe -m takealot_ops.cli daily-report-run --slot evening
.\.venv\Scripts\python.exe -m takealot_ops.cli daily-report-run --slot pre_close
.\.venv\Scripts\python.exe -m takealot_ops.cli daily-report-deadline
```

- 早间任务计划在每天 10:05 触发；当天 10:05 后时间最早的一次完整成功平台仓可售库存，会按实际北京时间日期和实际成功时间冻结到独立的 `daily_inventory_snapshots`。如果内部重试或 Windows 任务重启后才成功，运行记录、版本标签和导出会显示例如“实际 10:20”，不会仍写成 10:05。业务日 D 的日报统一使用“D 日整日销量 + D+1 日库存”：通常由早间任务取得；若早间库存漏爬或不完整，则采用 D+1 当天随后最早的完整手动或定时拉取，一旦完整即固定，18:00晚间及其他更晚采集不得覆盖。
- 早间、晚间、次日09:00周期末和周期内全部手动版本继续分别保存同一业务日订单与近30天浏览量，但版本核对只比较当天订单数（销量）。周期末任务位于10:00周期结束前一小时，用来补取平台临近周期末才入账的订单；09:00 库存只保留采集留痕。10:05 后的晚间或手动库存只在此前尚无完整库存时用于恢复；首次完整恢复形成后不再被更晚版本覆盖。任意两个成功版本的非空销量不同就进入待办；销量一致时不推送版本待办，库存变化和浏览量变化都不参与版本冲突。
- 右上角“刷新全部数据”只允许`kxx`点击；一次操作固定依次刷新`.env`全部已配置店铺（当前6店），每家完整成功后各增加一个不可覆盖的手动刷新版本。同一周期允许存在多个手动版本；其他账号无论角色和权限均不能启动该任务。
- 普通 HTML、Excel、PNG 日报也使用该前一业务日作为文件日期和数据截止日期；每次成功 Sales 都会重拉截至执行日的最近30个 SAST 自然日，以补回平台延迟订单并修订已变化的历史销售额。
- 每次早间、晚间和周期末任务都有分层保护：单个 HTTP 请求会重试网络超时、429和5xx；整批采集失败后依次使用新会话重试和忽略异常系统代理的直连备用；Windows任务仍失败时每5分钟重启，最多3次。Offers 失败不会再阻断本批 Sales 的独立重拉和历史销售额修订，但只有 Offers 与 Sales 都完整返回才允许冻结日报；只完成 Sales 时该批完整采集仍保持失败，禁止把旧缓存或单侧成功伪装成周期末成功。Returns在同轮按最近365个SAST自然日附加刷新，失败会保存独立状态并沿用最近成功明细，但不改变Offers/Sales决定的日报冻结结果。
- 每次整批尝试的序号、策略、开始/结束时间、阶段状态、脱敏失败分类和最终根因会同时写入 `logs/takealot-ops.log` 与日报运行记录。所有路径耗尽后才标记漏爬，并明确区分鉴权拒绝、限流、网络/DNS/TLS/代理、接口异常响应和本地流程异常。
- `/api/erp/daily-report/events` 与日报读写接口继续保留给兼容客户端，并继续执行登录、店铺与日报权限校验；当前统一 Vue 前端不再订阅事件、不再读取这些接口，也不显示矩阵、待办或全局提醒。
- 商品只有在本周期最终采用值的当天订单数或平台库存为空时才标记“漏爬”；近30天浏览量为空不算漏爬，某次采集失败或商品缺席但订单与库存已由其他成功版本补齐时也不打商品漏爬标识。漏爬不算冲突、不要求人工确认，也不阻止导出。所有定时/手动采集失败、商品缺席和字段空值的脱敏原因仍持久化到运行日志，并进入 Excel“漏爬说明”供追查。
- 近30天浏览量保留全部采集版本、底层存储和 Excel 展示，但不参与冲突判断。同一10:00核对周期只比较各成功版本的当天订单数；任意非空销量不同就形成`capture_difference`待办，销量一致时自动采用最新非空销量。业务日D的库存采用D+1日10:05后的首次完整实采，早间漏爬或不完整时由当天随后最早的完整恢复值补齐并锁定。
- 库存连续性只在相邻两个日报日都取得稳定正确值后计算；某一方仍有未确认的同周期版本差异时暂缓跨日公式。版本确认后立即重算，仍不相符才形成`stock_continuity`待办；新版本恢复公式时临时库存待办自动解除。
- 人工候选、确认、撤销及备注增删改继续由后端保存不可删除的审计。确认合并只确定正确销量或人工值，不能顺带豁免库存连续性；库存差异确认只关闭待办，Excel中的库存异常事实仍保留。前一日报日确认发生变化时会立即向后一日报日传播重算。
- 18:30仍未合并的数据会形成持久待办快照，次日采集照常进行。库存连续性按“上一日报日的D日早间库存 − 当前日报日的D日整日销量 = 当前日报日的D+1日早间库存”核对。
- 只要截止日期及之前存在未处理的销量版本差异或库存连续性异常，运营日报 Excel 就拒绝导出并返回具体日期和 SKU；漏爬不会阻断。最后一项待办确认完成时会自动导出到 `exports\operations-daily\YYYY-MM-DD\`。

如果只需用当前数据库做演练、不访问平台，可运行：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli daily-report-capture --slot morning --date 2026-07-24
```

## 7. 安装 Windows 自动任务

安装脚本本身不会自动运行；只有运营人员明确执行后才会创建计划任务。默认建立六个互不覆盖的任务：`10:05`早间采集、`18:00`晚间复核、次日`09:00`周期末更新同一业务日、`18:30`未合并快照/自动导出、每天`09:00`竞品雷达共享采集，以及当前Windows用户登录后自动确保ERP运行。错过触发时间后会尽快补跑，并忽略并发重复实例：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\install_scheduled_task.ps1 `
  -ProjectPath 'D:\南非店铺数据抓取' `
  -MorningAt '10:05' `
  -EveningAt '18:00' `
  -PreCloseAt '09:00' `
  -DeadlineAt '18:30' `
  -CompetitorCollectionAt '09:00'
```

计划任务使用项目自己的`.venv`和绝对项目路径，不会改变ERP的局域网监听地址。登录自启动任务以当前交互式用户、有限权限运行，延迟30秒等待Windows服务；它只在健康检查失败时调用正式重启链，失败后每分钟最多重试12次。竞品任务动作只登记当日持久触发并通知本机8501，爬取留在正式ERP共享批次中；该任务失败时每5分钟最多重试3次，ERP离线时触发文件仍由登录自启动任务或下次正式启动恢复。安装脚本同时移除旧的“Takealot 自有商品跟卖自动追踪”00:30隐藏并行任务。

周期末任务自北京时间 2026-07-30 起启用；更早日报明确显示“尚未启用”，不会被倒标成漏采。固定09:00而不是09:50，是为了在10:00周期边界前补取一次临近结束的数据，同时为分层重试和Windows任务补跑留出时间。

## 8. 备份与恢复

本项目只制作本机备份，不上传云端或异地。每次 `daily-run` 会先执行 MySQL 表完整性检查，再通过 `mysqldump --single-transaction` 生成一致性转储；成功后压缩为 `backups\takealot-时间.sql.gz`，并生成同名 `.json` 清单和 `.sha256` 校验文件。程序会重新读取整个压缩包，核对 SHA-256、压缩前后大小、MySQL 转储头和完成标记；任何一步失败都会删除本次不完整文件并让任务失败。

需要立即手动生成一份经过校验的本地备份时运行：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli backup-local
```

需要复核已有备份时运行：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli backup-verify `
  .\backups\takealot-YYYYMMDD-HHMMSS-ffffff.sql.gz
```

新格式备份按 UTC 时间分层保留：最近14天保留每一次，15至90天每天保留最新1份，91至365天每周保留最新1份，366天至7年每月保留最新1份，超过7年自动删除。升级前已有的明文 `.sql` 不会被新规则自动删除。

恢复步骤：

1. 停止正在运行的看板和每日任务。
2. 对选定的 `.sql.gz` 先运行 `backup-verify`，确认清单、SHA-256 和压缩内容全部通过。
3. 用 7-Zip 等本机工具解压出 `.sql`；在 MySQL Workbench 中先导入独立的空恢复库并抽查表和行数，禁止直接覆盖正在运行的正式库。
4. 确认恢复副本可用后，再在维护窗口备份或重建目标 `takealot_ops`，使用 Workbench 的 Data Import 导入同一 `.sql`。
5. 运行 `.\.venv\Scripts\python.exe -m takealot_ops.cli verify`，通过后再启动看板和每日任务。

本机备份可以防止误删、错误发布和数据库逻辑损坏，但无法防止整台电脑、同一块物理硬盘或勒索软件同时破坏数据库与 `backups\`。如果以后接入另一块本地物理硬盘，应把备份目录整体定期复制过去；当前方案按用户要求不做异地备份。

### 8.1 D盘 binlog 连续归档

所有备份产物统一保存在 `D:\南非店铺数据抓取\backups\`：完整备份位于根目录，binlog 原始归档、状态文件、校验文件和归档进程日志位于 `backups\binlog\`。MySQL 在 C 盘数据目录中的活动 binlog 是数据库运行源文件，不属于备份副本；程序通过本机 TCP 持续读取并把独立副本写到 D 盘，不会在 C 盘另外创建备份文件。

首次配置需要在服务器电脑上运行一次：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\configure_binlog_backup.ps1
```

脚本会隐藏询问 MySQL 管理员密码，创建 `takealot_backup@localhost` 专用账号，随机生成独立密码并只写入 Git 忽略的 `.env`。该账号只获得读取业务库、取得完整备份坐标和连续读取 binlog 所需的权限；密码不进入命令行、日志或代码。随后优先安装两个 Windows 任务：

- `Takealot MySQL Binlog Local Archive`：开机后持续运行 `mysqlbinlog --raw --stop-never`，断开后每分钟自动重启，从 D 盘已有的最新同名文件继续追赶；
- `Takealot MySQL Binlog Local Archive Maintenance`：每天02:30校验已经关闭的 binlog，生成 SHA-256，并删除超过35天的归档。当前正在写入的文件不会被校验任务删除。

如果当前 Windows 账号没有“任务计划程序”注册权限，安装脚本会自动降级为当前用户的登录启动项，并立即启动两个带互斥保护的隐藏守护循环：归档断开后每分钟重启，维护每天02:30执行。该模式不需要管理员权限，但电脑重启后必须至少登录一次 Windows，binlog 归档才会继续。

检查状态：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli binlog-archive-status
```

归档目标是覆盖最近30天；实际保留35天，为完整备份轮换、任务短暂停止和恢复操作预留5天重叠。启用专用账号后，新生成的 `.sql.gz.json` 清单会同时记录一致性快照对应的 binlog 文件名和位置。时间点恢复顺序为：校验并导入最近完整备份到隔离恢复库 → 从清单记录的位置开始重放 D 盘 binlog → 在误操作前的目标时间停止 → 核对表数、行数和关键业务数据。只有完成隔离库导入与重放演练后，才能称为时间点恢复已经验证。

## 9. 流量指标口径

`page_views_30_days` 只能称为“近30天浏览量”；不得将其或每日快照差值标注为精确日流量或访客数。

店铺级趋势不是 Seller API 直接返回的店铺总数，而是每天次日09:00周期末版本中已返回该字段的商品求和。页面必须同时展示覆盖商品数与缺失商品数；缺失商品不按0计入，整批失败日不连接折线。

“近30天日均浏览量”只是滚动窗口值除以 30；“30天浏览量窗口净变化”只是相邻快照的窗口差值。缺失值保持为空，不补零。

## 10. MySQL 运行边界

- 正式运行只使用本机 MySQL 8.0、`mysql+pymysql` 同步驱动和 `utf8mb4` 字符集。
- ERP 查询连接执行数据库级只读事务；采集、指标重建和竞品刷新使用单独的可写连接。
- 应用账号只授予 `takealot_ops` 数据库所需权限，不使用 root 启动 ERP。
- 每日运行执行 MySQL `CHECK TABLE`，并生成经过 gzip、SHA-256 和完整内容校验的 `mysqldump` 本地备份。
- `data\takealot.db` 仅保留为迁移完成前的数据留档，不再是运行数据源，也不会自动回退。

## 11. NFT102 访客表兼容流程

统一 ERP 前端不再提供 NFT102 上传续写模块。后台实现、既有输出目录和命令行方式仍保留；需要继续使用时，可在中国时间 10:05 后双击项目根目录的 `更新NFT102日报.bat`。该方式会自动寻找本机最新模板，生成新 Excel 与核对报告，并继续遵守不覆盖源文件的规则。

既有基准目录 `data\nft102-baselines\` 和结果目录 `outputs\nft102-daily\YYYY-MM-DD\` 保持不变。连续处理时，输出文件名仍会替换旧的 `_NFT102_日期` 后缀，不会每天叠加日期。

看板固定使用中文界面：导航、按钮、上传提示、字段名、商品状态、异常说明以及图表和表格工具控件均不显示英文。平台返回的商品原始名称、店铺代码、商品编码和南非货币符号属于真实业务数据，保持平台原值，不做猜测性翻译。网页上传上限为100兆字节。

填写口径：

- 表格日期使用当天日期；“当天订单数”使用前一天完整的 Sales quantity。
- “访客总数”填写 `page_views_30_days`，含义是近30天滚动浏览量。
- 接口不提供精确“当天访客数”，因此续写旧模板时该行留空；保留的运营日报导出表不再展示该字段。
- “平台库存数量”填写 Takealot 各地区 `quantity_available` 合计；收货中和在途库存不计入可售库存。
- 仅按表头中的完整 13 位 SKU 自动匹配；无法识别、无法匹配和重复旧列会留空并写入核对报告。

每次会同时生成 `.核对报告.txt`（供运营查看）和 `.核对报告.json`（供程序审计）。
