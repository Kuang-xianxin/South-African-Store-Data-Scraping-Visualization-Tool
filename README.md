# Takealot 店铺运营数据工具

这是一个在 Windows 本机运行的小型运营 ERP：通过只读 Seller API 采集自有店铺 Offer、Sales 与 Shipment 数据，通过长睿 W8 客户接口读取仓配数据，并通过公开商品接口和隔离匿名购物车观察竞品。统一的 Vue 3 + TypeScript 前端包含经营总览、商品中心、关键词流量、搜索定位、经营坐标、物流管理、约平台仓、竞品雷达、运营日报和用户权限；自有店铺和竞品历史统一保存在本机 MySQL 8.0。NFT102 与风险/质量的后台能力仍保留，但不再作为 ERP 前端模块展示。

## 1. 安装

在 PowerShell 中进入项目目录：

```powershell
Set-Location -LiteralPath 'D:\南非店铺数据抓取'
uv venv --python 3.11 .venv
uv pip install --python .\.venv\Scripts\python.exe -e ".[dev]"
.\.venv\Scripts\python.exe -m playwright install chromium
```

检查命令是否已安装：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli --help
```

## 2. 配置 API Key 与 MySQL

复制模板，生成项目根目录下的 `.env` 文件：

```powershell
Copy-Item .env.example .env
notepad .env
```

单店可继续只填写 `TAKEALOT_API_KEY`。多店铺使用非敏感注册表把店铺代码、显示名称和密钥环境变量对应起来；真实密钥仍各自单独保存，并把 MySQL 密码替换为本机应用账号密码：

```env
TAKEALOT_API_KEY=在这里粘贴真实Key
TAKEALOT_STORE_02_API_KEY=在这里粘贴第2家店真实Key
TAKEALOT_STORES=current|官方店铺显示名A|TAKEALOT_API_KEY;store-02|官方店铺显示名B|TAKEALOT_STORE_02_API_KEY
TAKEALOT_DATABASE_URL=mysql+pymysql://takealot_app:密码@127.0.0.1:3306/takealot_ops?charset=utf8mb4
```

密码中的 `+`、`@`、`:` 等特殊字符必须使用 URL 百分号编码。程序会自动读取 `D:\南非店铺数据抓取\.env`，已经存在的系统环境变量优先于 `.env`。不要把真实 Key 或数据库密码写进 `.env.example`，也不要把 `.env` 发给他人或提交到 GitHub。

物流管理还需要在同一个被 Git 忽略的 `.env` 中配置长睿提供的 W8 授权码。当前正式服务商域名是 `crgyl.w8soft.net`，测试域名与正式域名不是同一租户；不要把正式授权码写进测试地址。

```env
W8_API_TOKEN=在这里粘贴长睿提供的授权码
W8_BASE_URL=https://crgyl.w8soft.net/prod-api/w8
```

“搜索定位”默认使用火山方舟豆包Seed 2.0 Lite，阿里云百炼千问作为跨厂商备用。真实 Key 可放在被 Git 忽略的 `.env`，也可保存为 Windows 用户级 `DASHSCOPE_API_KEY` 和 `ARK_API_KEY`；正式重启脚本只在当前进程缺少对应变量时按这两个固定名称补载，不覆盖已经显式提供的进程变量，也不输出或写入 Key 值。普通打开页面、切店、筛选和查看历史只读 MySQL，不调用模型或 Takealot。只有拥有“调用多模态模型并采集搜索定位”权限的用户点击“识别图片并定位”才产生模型请求和受控公开搜索：

```env
DASHSCOPE_API_KEY=在这里粘贴阿里云百炼Key
TAKEALOT_SEARCH_QWEN_MODEL=qwen3.7-plus
ARK_API_KEY=在这里粘贴火山方舟Key
TAKEALOT_SEARCH_DOUBAO_MODEL=doubao-seed-2-0-lite-260215
TAKEALOT_SEARCH_MAX_PAGES=5
TAKEALOT_SEARCH_MAX_KEYWORDS=4
TAKEALOT_SEARCH_OFFER_MAX_AGE_HOURS=36
TAKEALOT_SEARCH_IMAGE_MAX_DIMENSION=640
```

相同主图、实际已配置且顺序一致的模型链和提示版本会复用已保存的结构化识别，本轮模型 Token 与估算费用均为0；增删供应商Key会改变模型链签名，但签名不含Key值。模型成功后会先保存原始识别与真实usage，再执行Offer重验和公开搜索；后续搜索失败时重试仍可复用这次已付费识别，不会重复付图片Token。同一轮因身份冲突或异常切换供应商时，所有已返回的可计量usage都会合计到本轮总Token与费用；HTTP 200但结构校验失败的响应只要返回usage也照实记账，但不能缓存复用。两家都发生身份冲突时只缓存原始图片profile，本轮因当前标题冲突而降低的置信度不会污染缓存，标题纠正后可零Token重新核对。主标题改变只重做识别后的本地交叉核对，明显异类冲突会零Token停止，正常一致时仍重新采集公开排名以保留当时位置。主图先使用既有安全图片缓存缩到最长边640像素，再以Data URL送入模型。默认单商品最多4个候选词、每词5页，低置信识别不发起平台搜索，豆包临时失败先有限重试再切换千问。按2026-08-07可配置标准单价与常见输出长度估算，首次识别约1000–1600输入Token、300–700输出Token，千问约人民币0.0044–0.0088元/商品；100个新商品约0.44–0.88元。实际账单以供应商返回Token及当时价格为准，页面按每次真实usage显示估算费用。Key不会进入页面、数据库、日志或错误响应。

旧 SQLite 数据只作为迁移源和回退留档，不再被 ERP、采集或日报读取。首次切换时，MySQL 目标库必须为空，然后执行：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli migrate-to-mysql
```

迁移器会复制全部业务表并逐表核对行数；目标库已有数据时会拒绝执行，避免覆盖或重复导入。

## 3. 首次采集与检查

采集当前 Offer 和最近七个南非标准时间（SAST）自然日的 Sales：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli collect
```

也可以指定销售日期范围：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli collect --start 2026-07-01 --end 2026-07-21
```

检查数据库完整性和当天数据质量：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli verify
```

如果出现未知销售状态，命令会返回非零状态。先在 `config/sale_status_rules.yaml` 中确认该状态应计入还是排除，再重新计算。
平台状态 `Cancelled by Takealot - DC Stock Inquiry` 属于取消单，和 `Returned` 一样计入订单记录总量但从有效销量中排除，不再触发未知状态质量失败。

## 4. 本地看板

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli dashboard
```

首次启动后，管理员必须先在服务器电脑上打开 `http://127.0.0.1:8501`，创建首个管理员账号；这个初始化入口会拒绝其他局域网电脑，避免同事抢先注册管理员。密码至少8个字符，只以带随机盐的 scrypt 哈希保存到本机 MySQL。

初始化完成后，同事可打开 `http://服务器局域网IP:8501` 登录。服务器 IP 可在 PowerShell 执行 `ipconfig` 查看 IPv4 地址。正式 ERP 监听 `0.0.0.0:8501`，但 MySQL 仍只连接本机 `127.0.0.1`，数据库端口不会提供给局域网。当前方案适用于同一受信任局域网，不应把 `8501` 直接映射到公网；如需跨网络或公网访问，应增加 HTTPS 反向代理和网络访问控制。

完成并验证项目修复后，使用 `.\scripts\restart_erp.ps1` 自动停止当前项目 ERP、隐藏启动新进程并等待 `/api/health` 通过。脚本只会停止命令行明确包含 `takealot_ops.erp.web:app` 的8501监听进程；端口被其他程序占用时会拒绝操作。人工重启与登录自启动共用同一个跨进程互斥，避免同时停止或拉起两个实例。启动前会对白名单内的千问、豆包用户级 Key 做缺失补载，值不写入脚本或日志；启动输出写入 `logs\erp.stdout.log` 和 `logs\erp.stderr.log`。

Windows计划任务`Takealot ERP 登录后自动启动`会在当前Windows账号登录后延迟30秒运行`ensure_erp_started.ps1`。它先等待自动启动的`MySQL80`并检查`/api/health`：ERP已经健康时直接退出，不重启、不打断活动任务；ERP未运行时才调用上述正式`restart_erp.ps1`启动链。任务使用当前交互式用户而不是SYSTEM，确保用户级模型Key、Windows凭据管理器和需要可见浏览器的人工操作仍属于同一账号；因此电脑开机后仍需正常登录Windows，但进入桌面后无需再手动启动ERP。启动检查使用跨进程互斥避免重复拉起，结果写入`logs\erp-startup.log`，失败时每分钟最多重试12次，并允许使用电池时启动。

“物流管理”把长睿正式环境的仓库、渠道、产品数、库存、入库、出库、退货与状态分布，同 Takealot Shipment、PO、目的仓、发货/卸货状态和 SKU 收货数量放在一页。打开或切回物流页面只读取当前店铺在 MySQL 中的最近成功快照，不会因为页面访问、切店或等待缓存过期自动调用长睿或 Takealot。两边上游只在人工点击“手动同步两边接口”，或既有10:05早间、18:00晚间、次日09:00周期末及右上角手动店铺采集完整成功后同步；人工重复同步仍保留最短间隔保护。Takealot读取和最近成功快照按当前店铺隔离，并发工作线程显式继承所选店铺上下文，不会复用其他店铺的Key或PO。W8是六店共用服务商，同一轮全店定时采集只读取一次长睿结果，再在每个店铺上下文分别保存快照。每次成功读取的完整脱敏物流数据会覆盖保存到本机 MySQL，任一上游接口暂时失败时自动展示该服务商最近一次成功快照，并标明本地同步时间。页面不创建、取消、打印或修改任何上游物流单据，也不展示长睿收件人地址。

两边只有在头程号、箱唛或长睿单号明确出现在 Takealot Reference、Tracking Info 或 PO 字段时才列为“明确编号直连”。候选关系分为三级：完整卖家 SKU 与各 SKU 发送数量完全一致、双方唯一且建单日期相差不超过30天为高置信；完整 SKU 集合一致但数量不同、日期相差不超过60天为中置信；至少一半 SKU 精确重合但整单 SKU 范围不同、日期相差不超过60天为低置信。页面逐条展示双方数量、差额、日期差和一对多歧义；只有2至3个 Takealot Shipment 的逐SKU数量合计精确等于一个长睿入库单时才额外提示可能拆批组合。所有档位都不会自动当成已确认关系；拥有“确认物流关联”权限的运营或管理员人工核对后才写入永久关联与审计记录，撤销时必须填写原因。仅日期接近、数量相同或文本相似均不会单独形成候选。W8 当前查询结果没有逐站扫描轨迹；退货接口返回条数与 `total` 不一致时会明确告警，并按实际返回条目展示。

“约平台仓”按顶栏当前店铺复用`OfferCurrent`，支持用SKU、TSIN、名称或Offer ID定位商品并分别填写CPT、JHB、DBN数量。页面只有“直接创建发货单草稿”入口：点击后先验证当前店铺的内存会话，有效则立即执行Takealot服务端预审并创建平台草稿；没有有效会话时由服务器读取该店铺预配置凭据发起登录，只有Takealot登录响应明确要求2FA才弹出验证码，验证后自动续接同一个幂等请求。另一个页签同时展示本模块创建的真实平台Shipment和物流模块最近成功保存的Takealot Shipment只读快照。真实写适配器直连Seller Portal当前使用的固定BFF主机`https://seller-api.takealot.com`，不经过星凯、不使用星凯JWT或签名，也不改动原本严格GET-only的公开Marketplace API客户端。由于这是Takealot未公开的Portal内部契约，功能同时受默认关闭的`TAKEALOT_PORTAL_BFF_ENABLED`总开关和默认空的`TAKEALOT_PORTAL_ENABLED_STORES`店铺代码允许列表约束；只有两个条件同时满足的当前店铺才能登录、验证OTP、预审、创建或执行后续平台动作，端点升级时必须重新核验。

每店铺邮箱和密码必须由服务器管理员从本机控制台写入运行ERP的Windows账号所拥有的凭据管理器；交互式方式为运行`.\.venv\Scripts\python.exe -m takealot_ops.cli portal-credential-set --store 店铺代码 --email 邮箱`，再在隐藏输入提示中填写密码。本机用户级环境变量可以作为管理员一次性导入来源，但ERP运行时不直接依赖这些变量，且不得把密码复制到项目`.env`。页面和API没有接收密码的入口，密码不进入MySQL、日志、审计或页面响应。可用`portal-credential-status --store 店铺代码`查看脱敏状态，或用`portal-credential-delete --store 店铺代码 --confirm-store 店铺代码`删除。OTP和Bearer只在当前Python进程内存按店铺隔离，OTP固定`remember_device=false`，重启或退出即清空。2FA由Takealot的`/v1/login`响应触发，不是ERP定时强制；平台没有要求时不会弹窗。

单次点击内部固定执行“校验会话 → 必要时登录/2FA → Takealot服务端`shipments_review`分仓 → 逐Offer/区域数量完全一致校验 → 单次提交Task 22”。本地记录仅用于幂等和审计，不再作为用户可操作的冻结步骤；浏览器端旧冻结、预审、二次创建接口已移除。`UNALLOCATED`、未知仓库、数量变化或部分分配都拒绝建单。POST/PUT从不自动重试；网络超时会标记“结果未知”，必须先去Seller Portal人工核对，避免重复Shipment。确认PO使用平台预览和Task 21后再输入Shipment ID；归档使用平台当前归档端点。当前Portal构建产物中的“确认已发货”路径存在`vi/`疑似拼写异常，因此实现采用推定的`/v1/`路径但继续由`TAKEALOT_PORTAL_SHIPPED_WRITE_ENABLED=false`独立关闭，必须在授权人工抓包确认后才能开放。所有流程都服从Takealot服务端分仓和补货限制，绝不实现“不可约”绕过。

权限页面提供四个快速模板：

- 查看（`viewer`）：查看店铺、竞品、运营日报和已有报表，不执行采集、刷新或人工处理；
- 运营（`operator`）：承担日常运营工作，可调用搜索定位、管理物流关联与平台仓；真实平台仓创建只允许在服务器本机点击直接创建，平台要求2FA时再人工填写验证码，此外可采集、刷新、处理日报待办并生成报表；
- 选品（`selection`）：可查看和采集竞品雷达，也可查看运营日报，但不能处理日报待办；
- 管理员（`admin`）：默认拥有全部业务能力，并可管理账号和权限。

四个模板都只是新建账号或快速套用的起点，不是固定角色边界。管理员可在“用户权限”页面对每个现有账号逐项开启或关闭店铺查看、搜索定位运行、物流关联确认、竞品采集、日报查看、日报待办处理、日报 Excel、刷新和用户管理权限；套用模板会替换该账号当前的自定义权限，逐项调整后账号需重新登录生效。系统始终保留至少一个启用的用户权限管理账号，避免管理员把自己锁在系统外。

“用户权限”页面同时提供无数量上限的店铺权限目录和账号—店铺多对多分配。普通运营账号选择“仅访问勾选店铺”后，可以分配任意数量的店铺；当前常见的一人两店只是运营规则，不是程序上限。管理员、老板等跨店账号可开启“全部店铺（含未来新增）”，以后增加第7、第8个店铺时会自动进入其可见范围，不需要逐个账号补勾选。该开关独立于查看、运营、选品、管理员四个权限模板，因此“老板”不需要新增一套写死的角色；只要给对应账号选择合适功能权限并开启全部店铺即可。

升级时，既有账号会无损保留为“全部店铺”，避免上线后突然失去数据；管理员再按实际分工把普通运营改为限定店铺。正式业务表现已使用`store_code`区分店铺，原有历史自动归入`current`，新采集按所选店铺写入。2026-08-04 已接入`current`至`store-06`六家店；以后仍可先预留新店，只有凭据进入`TAKEALOT_STORES`并完成首次采集后才标记为已接入。

登录后，页面顶栏的“当前查看店铺”会列出该账号可访问的店铺。选择任一已接入店铺时，请求会携带店铺代码，后端先校验账号范围，再只读取该店铺的商品、销售、指标、异常、物流快照、刷新状态和运营日报；切店会重新加载页面数据。待接入店铺仍只显示安全说明，不会复用其他店铺数据。不同运营人员通过各自账号登录取得店铺和功能范围，管理员页面不提供无留痕的账号冒充切换。

店铺范围与公共模块权限彼此独立。竞品雷达只要账号已开启对应功能权限，即使没有分配任何店铺也可以进入和操作；登录时会自动落到第一个可用公共模块。竞品雷达会只读复用当前单店 Seller API Offer 的PLID和完整刷新历史来识别自有链接，但这不改变它的公共模块权限边界。经营总览、商品中心、关键词流量、搜索定位、经营坐标、运营日报、全量刷新和既有店铺报表仍属于店铺数据范围，必须同时具备对应功能权限和已接入店铺授权；保留的风险后台接口继续执行同一店铺授权校验。共用商品缩略图接口接受店铺、竞品或日报任一查看权限，但仍要求登录并执行官方图片来源安全校验。

“经营总览”的顶栏店铺下拉框在账号至少可见两家已接入店铺时增加“全部 N 个店铺”选项；正式全店账号当前显示“全部 6 个店铺”。选择全部时只读取并展示当前账号可见店铺的老板盘面和逐店卡片，切回具体店铺时只读取该店的完整趋势、健康度和商品明细；这个全部范围不会作为虚构店铺代码进入商品、物流、日报等单店模块。受限账号只汇总其获授权、已启用且已完成数据接入的店铺，不会泄露其他店铺或把数量写死。每张卡片显示该店自身最新可用指标日的下单件数/金额、近7日下单、在售商品、转化率、缺货、最近周期末商品近30天浏览量，以及平台可售、平台在途和平台收货中库存；点击“进入该店明细”会切回真实店铺上下文。

老板盘面的健康状态不使用黑箱分数，而是按“需关注、数据待补、当前口径正常”排列，并直接列出缺货商品、流量和库存字段缺口。数据异常/异常商品指标暂不在经营总览展示，也不参与店铺健康判断或排序；ERP 前端暂不展示这些异常，底层判定、接口和报表继续保留。各店“负责运营”动态取该店获授权、启用且拥有店铺查看权限的非管理员账号，管理员不进入名单；姓名只随当前账号可见店铺返回。顶部库存物流区从本地最近成功快照把共享 W8 海外仓只计一次，同时按可见店铺最新 Offer 汇总平台可售、平台在途与平台收货中，并显示商品字段覆盖。海外仓锁定、已分配出库、海外仓在途和平台不同阶段分开展示，不相加成可能重复的“总库存”。跨店销售合计继续标注实际返回家数，不把缺失店铺补0，也不假设各店指标日完全相同；转化率中位数不跨店平均。打开页面、切换全部店铺或进入某店明细只读本地 MySQL，不触发 W8 或 Takealot 上游同步。

全部现有前端模块会保留在侧边导航中，账号没有对应查看权限时以“未开放”标识展示；点击锁定模块或页面内未授权的刷新、竞品采集、日报处理/导出等操作时，统一显示“当前账号该功能权限未开放”，不得静默无响应。后端仍会再次校验每个接口，前端提示不能替代真实授权。

前端发布新权限模型而正式后端尚未重启时，页面会按旧账号的查看、运营或管理员模板临时补齐权限，避免登录后空白；后端重启后自动改用账号级真实权限。登录信息无法识别、接口连接失败或页面脚本异常时，页面必须显示明确错误说明和重新连接/重新加载入口，不允许只留下空白页。

权限由后端接口强制执行，不只是隐藏前端按钮。会话保存在可撤销的 HttpOnly Cookie 和 MySQL 会话记录中：登录后有效7天，只要在到期前继续使用，系统就把到期时间自动顺延到最近一次有效使用后的7天；为避免页面高频轮询反复写库，同一会话每1天最多续期一次，并同步刷新浏览器 Cookie。连续7天没有任何有效使用才需要重新登录；主动退出，或管理员修改该账号的权限、模板、密码、启用状态时，旧会话仍会立即失效。写操作需要 CSRF 校验，连续登录失败会被短时限流。浏览、筛选和切换页面时使用 MySQL 只读事务，不调用平台 API，因此查看已有历史数据不需要 API Key。

侧边栏会显示“最近采集”和“最新指标”，用于判断当前看到的数据是否已经更新。“最近采集”以及竞品历史快照的时间固定按北京时间（Asia/Shanghai）显示，不跟随浏览器或南非平台时区；“最新指标”仍是既定的 SAST 业务日期。拥有“刷新全部数据”权限的账号可调用项目根目录 `.env` 中的 API Key，完成带分层重试的只读采集、指标重建、日报导出、完整性检查和备份，并把这次结果冻结为当前 10:00 核对周期的独立“手动刷新”版本。所有非管理员模板账号共享全局1小时冷却：任何账号成功刷新后，其他非管理员模板账号都会同步显示刷新人和剩余倒计时；管理员模板账号在保留刷新权限时可以越过冷却，但不能和一场正在执行的刷新并发。冷却记录保存在 MySQL，服务重启后仍有效；失败刷新不开始冷却。失败时可查看 `logs\takealot-ops.log`，失败原因也会进入日报运行记录，页面不会显示或记录 API Key。

“商品中心”直接在每条商品栏中展示平台商品缩略图；图片缺失或加载失败时显示“暂无图片”，不会保留破图图标。点击商品栏或用键盘回车/空格激活后，商品身份、当前售价、最新日/近7日下单、库存、近30天浏览量、转化率以及每日销售件数快照会集中显示在当前视口的详情弹窗中；历史区不再展示流量快照，销售柱图纵轴按整数件数显示数字刻度。详情不再重复铺在商品列表下方，避免在窄屏中滚动到页面底部查找。弹窗支持遮罩、顶部和底部关闭入口及 Escape 关闭，打开时锁定背景滚动，关闭后焦点回到原商品栏。

“关键词流量”完全复用每天完整 Offers 快照：`page_views_30_days`形成按日近30天浏览量趋势，官方 `title` 形成“商品标题关键词”档案。Seller Offers 当前没有独立 `keyword`、`search_term` 或 `tags` 字段，因此系统不会伪造平台搜索词；`product_label`是数字商品标签，也不作为关键词。每个商品的首个有效标题快照就是基线；以后标题词新增、移除、词序或写法发生变化时，系统生成南非业务日变化节点和对应标签，并以高对比竖线固定在流量图上。页面没有人工建档、补录或修改入口，查看已有历史也不会调用平台接口或写入数据库。

每个变更节点都提供两项并列结论。第一项比较“变更前窗口最后一个有效近30天浏览量”与“变更后窗口最新有效值”，明确显示上升、下降、持平、净变化和百分比；第二项分别对变更前后有效日按真实日期计算线性趋势斜率，显示上升/下降趋势以及趋势速度是增强、减弱还是反转。页面可选择前后3、7、14或30天，变更当天因采集先后不确定而排除；变更后窗口未结束时明确显示仍在积累。缺失流量保持缺失，断点不连线、不补0。所有结论只是关键词变更节点附近的观察对比，不能单独证明流量变化由关键词造成；价格、库存、促销和季节等同期因素仍需运营结合判断。

“搜索定位”与上面的“关键词流量”是两套不同口径。列表先以当前店铺授权 Seller Offers 的 `OfferCurrent` 作为自有身份凭据；完整刷新会删除上游已不存在的Offer。只有状态严格等于`buyable`、平台与卖家可售库存合计为正、快照不超过36小时、数字PLID/主标题/Takealot官方`covers_images`主图齐全的链接才显示。点击运行时在任何模型调用前再次执行同一闸门；模型识别完成、平台搜索开始前再核对一次，状态或资料变化即停止。库存为正但状态被卖家或平台禁用仍不算在售，普通查看也不会为了更新状态自动访问上游。

通过自有在售闸门后，第一阶段多模态请求只接收缩小后的商品主图，绝不接收主标题或SKU，因此页面“图片独立识别”不会再直接复述主标题。识别完成后，服务器才把窄商品形态、可见区别属性和搜索候选与当前官方主标题做本地交叉核对，并记录哪些短语得到标题支持。豆包Seed 2.0 Lite默认主用，千问`qwen3.7-plus`作跨厂商备用；千问把候选返回成字符串数组时由供应商适配层补成统一结构，业务字段仍由Pydantic严格校验。新识别出现图片身份与标题明显冲突时尝试备用，两家都冲突则把置信度降到搜索门槛以下；缓存复用后若当前标题与旧图片识别明显异类，也会以零Token低置信停止，两种情况都不继续消耗Takealot搜索请求。模型链签名只包含当前实际启用且按调用顺序排列的提供商与模型，不含Key；相同主图、同模型链和提示版本可复用付费识别。模型阶段一成功就先持久化usage，即使后续搜索失败也可供重试复用；页面主结果继续保留最后一次完整成功分析，并另行提示最近失败尝试。

模型会分别给出精准长尾查询、普通买家可能先输入的短词根，以及可竞争相邻需求的词根；这些都只是候选。系统读取Takealot公开`search_suggestions`，把真实补全文案、输入词根和补全第几项写入证据，再对每个最终候选检查默认`Relevance`的完整第一页（最多36个自然商品）。只有至少60%标题命中模型第一条窄物理形态词才列为核心词。相邻需求候选必须来自真实补全，并在实际扫描中找到本商品、自然位进入前72位，同时按模型窄物理形态词核算、首页扣除本商品后标题词元命中的直接同类不超过2个，才标记为相邻需求蓝海；这是保守的标题词证据门槛，并不等同于平台已证明没有同义词竞品。任一条件缺失都不生成该打法标题。通过后沿Takealot`after`游标最多扫描配置页数，记录目标PLID第几页、第几行、第几列及跨页自然序位。排名不是靠视觉猜测广告：解析器只读取`sections.products.results`中的`product_views`且排除显式`sponsored/promoted`标记，其他数据区和结果类型不进入序列。补全顺序是平台直接意图代理但不是公开搜索量；平台返回商品数只是供给规模，也不是访客量、热度或销量证明。

结果卡把“第X页、第X行、第X列”作为主定位；“跨页自然排名 #N”紧随其后解释为“自然商品序列中的第N个”。第几页来自Takealot的`after`游标页，每个游标页最多纳入36个自然商品，页内按桌面端从左到右每行四项映射坐标；跨页自然排名只按实际纳入的自然商品连续累计。若平台页内有被排除的赞助或非商品记录，下一游标页不承诺机械地从`页码 × 36 + 1`开始。页面可能额外插入其他内容，因此视觉位置仍可能与接口自然序列坐标不同。

标题建议固定拆成三种彼此独立的打法，并始终分成三个区域展示：第一种“完整连续词组版”只把首个通过验证的完整核心短语前置；第二种“类目热词覆盖版”只合并真实Takealot补全且已通过核心相关性、同时得到当前标题支持的类目表达，用更积极的前部覆盖测试多个查询；第三种“相邻需求蓝海版”只在上述可搜到本商品、前72位和按窄形态标题词核算的直接同类不超过2个同时成立时，把相关需求词前置。第二种所称“热词”仍只是平台补全支持的搜索意图词，不代表公开搜索量；第三种未达门槛时保留区域并明确显示暂无方案，不硬编标题。三种标题均只使用可支持事实：蓝海补全新增词必须来自原始相邻需求词根，未获当前标题支持的数字/规格单位、材质、颜色、受众、品牌兼容、功效及模型区别属性会被阻断；App、Smart、USB等高风险属性也不会写入建议。系统不自动修改 Seller Portal 标题，也不保证一定前移；后续完整Offer刷新检测到标题确实等于某一建议后，只把该打法的证据词作为主验证目标并强制同词复采。任何基线词本轮缺失或未找到时都只报告证据不足，不能把剩余词的前移包装成整体前移；其他查询只能作为次要观察。该前后对比仍是观察证据，排名会受时间、地区、个性化、库存、价格和平台策略影响，不能单独证明标题造成变化。

建议标题还会经过服务器端固定整理：最终只保留字母、数字和单个空格，不含任何标点；相关核心词在前，当前标题已有卖点和参数在后，单复数重复词会合并。标题区的基线固定显示“本次分析时标题”；若最新Offer标题已经变化，页面会另外提示当前标题与建议基线不一致，要求重新分析，避免把运营同事后续改题误当成旧建议的输入。旧缓存结果在读取时也执行同一规则，因此格式升级不需要重新调用模型或额外消耗Token。这里的“已验证”只代表当前搜索页同类型结构和自然位置，不代表平台提供了搜索量或承诺改名后排名前移。

Vue ERP 的现有商品图片入口统一使用登录态同源缩略图：商品中心、经营坐标、竞品雷达、运营日报及其弹窗、历史卡片不再直接下载和解码平台高清原图。列表、表格、卡片和小型头图使用最长边 192 像素 JPEG，商品中心详情大图使用最长边 640 像素 JPEG；后端只接受 Takealot 官方 S3 与媒体域名的 `covers_images` 路径，并限制来源、原图大小、像素和可选缩略尺寸。结果按尺寸缓存在 `data\runtime-cache\product-thumbnails-*`，属于可删除、按需重建的运行产物。同一图片的并发首次请求仍只转换一次；进程内缓存键锁按正在使用人数计数，成功、失败或异常退出后由最后一个使用者立即移除，不会随历史图片数量长期滞留。图片声明固有尺寸并异步解码，长列表继续懒加载和跳过离屏绘制，避免页面交互时反复布局或解码大量图片。

浏览器中的原生图片标签不能附加普通 API 使用的 `X-Store-Code` 请求头，因此缩略图同源 URL 会显式携带当前选中的真实 `store_code`；后端也只对缩略图路由兼容没有店铺参数的旧页面，在账号不存在 `current` 授权时使用其任一已授权店铺完成门禁。登录、功能权限和官方图片来源校验保持不变。其他运营电脑通过局域网打开 ERP 后，请求的仍是 ERP 服务器上的同源缩略图接口，由服务器访问、转换并缓存 Takealot 原图，客户端不会直接下载平台高清原图；无痕窗口只需重新登录，加载链路不变。

“经营坐标”使用商品最新的近30天浏览量和截至最新指标日的近30个自然日下单件数，只展示一个二维坐标散点图，不再划分明星、潜力、待优化、转化问题四象限，也不再提供分位选择、分类筛选卡或十字分界。横轴固定为“近30天浏览量相对排名”，纵轴固定为直立竖排的“近30日下单件数相对排名”；两个方向的0、25、50、75、100关键排名刻度放在图框外的独立白色数字标记中，避免被散点遮挡，图内只保留轻量参考网格。散点统一使用高对比蓝色。鼠标移到商品点上会立即出现 ERP 样式的信息卡，优先展示平台商品缩略图，并显示商品名称、平台 SKU、库存、近30天浏览量、近30日下单、首次上架/最早记录、最近补货时间和数据截止日期；图片缺失或加载失败时显示“暂无图片”，不保留破图图标。信息卡会按点位自动向上或向下展开，不会被图框裁切。点击小点会直接复制平台 SKU 并显示结果反馈。只有同时具备两个真实指标的商品进入坐标图；缺失数据不会按0处理，仍完整保留在“全部商品”区域。全部商品改为自适应卡片，商品名称和全部字段完整换行展示，不需要左右滑动；每张卡片均包含商品图片、平台 SKU、浏览量、下单、平台库存、首次上架/最早记录、最近补货及数据截止日期，并可通过“排序方式”选择器按近30天浏览量、近30日下单、平台库存或商品名称排列。SKU 搜索框支持忽略大小写的完整或部分平台 SKU 即时匹配，持续显示当前结果数与商品总数，无匹配时给出明确空态；清空搜索后恢复全部商品。浏览器复用未变化的卡片虚拟节点，避免悬停或复制 SKU 时重新构建全部商品内容。单品分析和店铺总览的每日下单件数图只显示真实整数件数，不再绘制可能产生小数的移动平均线。

Offers 接口提供 `created_at` 时，“首次上架”使用该平台时间；旧历史没有该字段时明确标为“本库最早记录”，不会伪装成平台真实上架时间。系统逐条比较同一商品的有效平台库存快照：后一条库存高于前一条时，后一条快照的实际采集时间就是“最近补货时间”，同时显示较前次增加数量；该时间按北京时间展示，不属于估算。没有观察到库存增加时显示暂无记录。Offers 接口只明确返回近30天滚动浏览量，没有独立的近7日流量字段，因此经营坐标和悬浮卡不再推算或展示近7日流量，只展示平台原值“近30天浏览量”。

Seller API 也没有独立的店铺总浏览量字段。经营总览的“店铺商品近30天浏览量汇总趋势”复用每天次日09:00周期末成功冻结的商品版本：每个点按周期末实际采集的北京日期减一天归档，例如8月6日09:00采集显示为8月5日，不直接复用运营日报的 `business_date`。同一归档日取最新成功 `pre_close` 版本，汇总接口已返回的各商品 `page_views_30_days`，并显示覆盖商品数和缺失商品数。缺失值不补0；某日整次周期末刷新失败时，正式周期末值继续保持失败和断点，同时查找该北京时间自然日最近一次非周期末成功采集作为橙色虚线参考，并明确展示实际采集时间、来源时段、覆盖数和缺失数。没有同日成功采集时仍保持完整断点；参考值不得冒充09:00正式周期末数据。同一天因Windows重试形成多个周期末版本时只取最新成功版本，不重复相加。折线默认展示截止所选日期的最近30个自然日，反映每天观察到的滚动30天窗口汇总，不代表精确当天流量或访客数。

统一 ERP 前端已移除“报表工作台”、NFT102 上传续写页面和“风险与质量”模块；侧边栏独立的“运营日报”模块及其核对、合并和 Excel 流程保持不变。既有 NFT102 后台能力以及风险接口、异常计算、数据库记录与报表口径仍保留，供命令行及兼容流程使用。

异常口径默认以“最新指标日”为准：后台风险投影、Excel 总览和 HTML 总览都统计该日出现异常的去重商品数；异常明细保留同一商品在当天触发的每一种异常，因此明细记录条数可能大于异常商品数。历史异常继续保存在数据库并可由后台接口读取；Excel、HTML 和 PNG 日报默认只输出最新指标日异常，不混入历史日期。经营总览和现有 ERP 前端不展示或使用这项异常统计。

销量趋势改用同一指标日截止的自然日均值比较：近3天下单件数日均值低于近15日均值时判为“销量下降”，高于时判为“销量上升”，两者相等时不产生销量趋势异常。两个窗口都包含当前指标日；只有系统已覆盖完整15日窗口时才判断，窗口内已覆盖但没有订单的自然日按0件参与平均，历史不足不补零、不判趋势。不再使用“当日销量对比此前7日均值”以及最低销量、涨跌百分比门槛。

风险后台能力继续保留完整异常证据：销量趋势保存异常发生日截止的15天逐日销量及近3日/近15日日均，流量转化保存实际浏览量、转化率、销量窗口与必要阈值，疑似断货、停止更新和未知销售状态保留各自触发上下文。历史异常证据不得用当前指标替代，不足30天的销量窗口不得伪装完整覆盖；这些数据继续供接口和报表使用，但当前 ERP 前端不再提供风险卡片、筛选或详情弹窗。

### 4.1 竞品观察

真正竞品列表增加独立的“可跟卖机会”统计和选择器，可筛选“全部报价售罄”与“暂无卖家报价”，命中商品会在卡片上显示标签。这不是经营信号，也不作用于自有商品分区：只使用所选观察区间最新一次成功公开商品快照的完整报价数组；数组为空才算暂无卖家报价，数组非空且每条报价都有明确没货证据才算全部售罄。任一报价有货或库存未知、旧快照缺少完整报价数组、采集失败或库存探测失败都不会被误判。查看、筛选和统计只读本机MySQL，后续成功采集会按最新证据自动更新，不额外访问平台或写库。

“竞品雷达”是统一 Vue ERP 的一个正式模块，与经营总览等页面共用 `8501` 地址和同一份 MySQL，不再通过 Streamlit 嵌入或单独启动第二个端口。

竞品雷达会从六个已接入店铺 Seller API 当前 Offer 的 `productline_id` 自动汇总自有商品链接，先在每店内去重、再跨店按PLID去重，并与人工维护的“真正竞品”分区。页面使用“真正竞品”和“自有商品跟卖”两个来源标签页，默认只显示真正竞品；自有商品默认严格跟随顶栏“当前查看店铺”，只展示该店自己的去重PLID、Seller API最新刷新和跟卖结果。进入竞品雷达时，同一个顶栏店铺下拉框会增加“全部店铺”选项，用于汇总账号可访问的已接入店铺并跨店去重，共享PLID会保留各真实店铺名称；其他单店业务模块不使用该跨店选项。每次点击“开始采集”都会重新读取当时最新的全部真正竞品和账号可访问的全部已接入店铺自有PLID，先放真正竞品、再放全部自有链接，按PLID去重后复用同一个页面批次、断点和串行浏览器；顶栏当前店铺只改变页面查看范围，不会缩小手动采集范围。真正竞品和任一自有PLID都可插队，插队副本在当前商品之后执行，原队列位置和断点不被改写。每天09:00自动批次会读取全部活跃真正竞品和所有已接入店铺的当前自有PLID，范围不受某个登录账号或页面店铺选择缩小。自有PLID不会写入人工监控清单，也不需要逐条新增、修改或删除；页面始终同时显示后台全量跨店去重数和店铺内合计数，便于核对是否覆盖所有店铺。

2026-08-04以前由旧页面生成的混合批次可能把当前店私有链接、其他店私有链接和真正竞品一起保存在浏览器断点中，例如旧的647条“待爬取”。断点格式现已升级为版本9；新页面首次加载会删除所有旧版断点，不再恢复错误混合清单。新建手动批次会按当前规则重新读取真正竞品和自有PLID；09:00自动批次使用独立的服务端持久断点，不会混用某个浏览器的旧本地断点。新增链接时，真正竞品会正常写入人工清单；若PLID实际属于任一已接入店铺，接口直接返回真实店铺名并提示已经处于每日统一采集范围，不再出现“后台说已存在、页面却看不到”的冲突。

自有商品的Seller API数据来自“刷新全部数据”的完整 Offers 拉取：`store_offer_baselines`继续按北京自然日、店铺和Offer ID只保留当日最早一次完整拉取，供每日基准口径使用；新增`store_offer_observations`把每次手动或定时完整刷新都保存为不可变历史点。竞品页当前值和折线读取刷新观察点，因此同一天后续拉取也会更新价格、总库存、Takealot可售库存、卖家可售库存和区间变化；Seller API时间点没有同步公开评论时，评论折线保持断点。自有PLID进入统一共享批次后读取全部公开变体及报价，以所有已接入店铺当前Seller API的Offer ID和SKU精确排除自有Offer，剩余卖家才算跟卖；因此竞争卖家即使抢到某个变体的主报价也继续保留和探测。商品变体本身不等于跟卖，公开变体只在PLID共用变体区展示，只有排除自有身份后仍属于其他卖家的具体报价才进入跟卖列表。自有分区提供独立的六店日期区间表单，从不可变公开快照回溯区间内任一天出现过的跟卖卖家并列出具体发现日期；即使该卖家在区间末已经消失也不会漏掉。“新增跟卖卖家”表示系统全历史首次观察日期落入所选区间，不代表卖家实际开始跟卖的绝对时间。PLID商品共用评论在首次检查或公开评论数变化时单独读取，评论数不变时复用已保存正文；无论是否发现跟卖，详情都展示已有评论、评分、好中差评结构和公开变体。Takealot评论仍属于整个PLID，无法归属到某个跟卖卖家。

“六店自有链接跟卖发现记录”默认收起，只保留标题、北京时间口径和“展开记录”按钮；展开后才创建日期查询表单、说明与结果列表。再次收起不会清空已经选择的日期或已查询结果，也不会触发新的平台访问或数据库写入。

Takealot同一变体的主购买区可能同时显示多个单选报价，例如页面上方的“Fastest Delivery”和“Best Price”。采集会保存该区域全部报价，而不是只取当前勾选项：每个变体自己的选中主报价只属于该变体，不直接触发跟卖；同一变体内其他未选报价以及下方红色`other_offers`才是跟卖候选。主购买区响应名为`sku`的值当前实际对应Offer ID，因此自有链接会用它同时交叉核对六店Seller API Offer ID和SKU。平台只返回绿色报价卖家ID、不返回名称时，页面显示稳定卖家ID和“平台未返回名称”，不会猜造卖家名。自有商品和真正竞品两个分区都提供“有被跟卖/未发现跟卖”筛选，旧快照仍按红色`other_offers`保守兼容。

竞品每日采集不再依赖运营保持竞品页面打开。Windows 计划任务默认每天北京时间09:00运行 `trigger-competitor-collection`；该命令只按北京自然日幂等写入一个持久触发文件并唤醒本机ERP，实际爬取仍由正式ERP启动与手动按钮相同的共享单批次。批次真正取得采集权时才读取全部活跃真正竞品和所有已接入店铺当前自有PLID，先真正竞品、再自有链接并按PLID去重；人工批次正在运行时自动请求保持待开始，ERP离线或重启时也会从持久触发与未完成断点恢复，不会静默漏掉当日请求。运行中每完成25条及收尾前重新读取目标，Seller Offers刷新后出现的新真正竞品或六店新PLID会按发现顺序追加到队尾，不会加入已经结束的历史批次。管理员能在竞品雷达看到与手动批次相同的进度、当前PLID、后台阶段、成功和待重试明细；普通运营不加载这套技术进度，只使用自己的个人监控池和新增链接。`kxx`可随时停止当前链接和整批，停止后当日不会再次自动启动，次日09:00照常。旧的00:30 `track-own-store-followers`隐藏并行计划任务会在安装时移除；该CLI仅保留人工兼容，不再作为正式每日通道。自有链接成功、部分成功或失败仍记录`own_store_follower_tracking`，尚无公开快照的商品继续显示“等待首次检查”。

平台当前会拒绝原来的普通 HTTP 公开接口请求，因此竞品商品、变体和评论改由 Playwright 启动本机 Chrome/Edge 导航公开 JSON 地址；库存仍在另一个隔离匿名购物车会话中探测。命令行批量采集会复用同一个公开数据浏览器会话；ERP 也会在服务器单任务和单链接租约内串行复用隐藏的公开数据浏览器，最多连续处理25条后主动回收，遇到网络失败、浏览器异常、请求取消或服务退出时立即关闭并在下一条重建。可见的匿名库存浏览器仍保持每条链接独立启动、独立购物车和完整关闭，不会跨商品共享库存会话。

竞品中心使用 MySQL 持久化的“监控链接清单”，不再把临时多行文本框当作任务来源。具备竞品采集权限的普通运营可新增链接，链接按PLID去重并自动加入提交账号的个人监控池；只有管理员可修改或删除全局链接、手动插队、查看审计和处理失效复核，后端接口也执行同一角色限制。修改不允许偷偷改变PLID，删除只停用后续监控，不删除商品、评论、变体或历史快照。顶部提交按钮明确为“加入监控队列和我的监控池”：全新或重新激活的真正竞品同时进入两者；重复链接已在个人池时直接定位，尚未加入个人池时先幂等加入再定位。定位只发生在顶部独立个人池商品区，不再清除下方筛选或跳到“竞品最新状态”；系统自动切换个人池分页、滚动并聚焦对应卡片，以橙色描边、暖色背景、短时脉冲和“已定位到此商品”标签高亮4.5秒。尚未首次采集的链接也保留PLID和“等待首次采集”卡片，不会因没有历史而无法定位。管理员的监控清单默认只显示总数、已有历史和待首次采集三个汇总数，明细默认不创建；点击“打开管理”后使用固定视口弹层，可按名称、PLID或完整链接搜索，并可选择每页20、50或100条，页面只创建当前页链接节点；搜索或切换每页数量后自动回到第1页。粘贴Takealot完整链接时自动提取PLID匹配，不再以内联展开推动下方数百条竞品雷达长列表整体重排。若已有批次正在运行，新加入的链接会按新增先后追加到当前待执行队尾，不打断当前商品，也不改变已冻结断点中的原任务顺序；没有活动批次时进入下一次完整采集，需要提前检查时管理员仍可人工点击“插队”。每次新增、修改、删除都在同一数据库事务中记录操作用户、北京时间、PLID及修改前后链接。管理员页面的“链接操作记录”也使用固定视口弹层，首次打开才按开始/结束日期请求记录，后端每页最多返回20条，避免操作记录增长后拖慢页面布局。当前最小闭环会：

每次采集还会检查全部公开变体的主报价与`other_offers`。PLID代表商品线，同一商品的多个卖家报价通常共享PLID，因此监控清单和爬取队列按PLID去重：该PLID只抓取一次，返回的全部报价保存在同一快照中并优先按公开`offer_id`或`other-buying-option-<SKU>`购买卡片标识区分，均缺失时使用卖家、SKU、变体和商品条件组成的保守稳定键。只有报价明确指向不同Takealot URL/PLID时才会自动增加另一个监控目标；已有活跃目标不会重复新增或重复入队。无法识别报价身份时不会猜造链接，用户提交的原始链接始终保留。启用库存探测后，同一商品的隔离匿名会话会逐个清空购物车并探测变体主报价和可购买跟卖报价：跟卖加购前核对购买卡片ID/SKU与卖家名，购物车内再核对PLID与卖家名，取得的精确或至少数量只写入该报价；供应商调货或明确不可加购记0，校验失败则保持缺失并进入库存复探，不会复制主报价库存。管理弹层按“原始商品链接 + 全部卖家报价”折叠成组，组内内容只有展开时才创建，并显示Offer ID、卖家、价格、报价级涨跌及各报价自己的库存状态/变化；不同PLID目标的自动发现或重新激活使用独立`auto_discover`审计。

竞品雷达中所有商品级展示区都附带对应商品快照主图；变体库存则从每个非默认变体自己的公开详情 gallery 保存独立图片。详情中的当前变体表和每个区间历史快照都会按快照 ID 展开当时全部变体的可读名称、库存、限购标记和专属同源 192 像素缩略图，不会把 API 返回的字典/JSON 字符串直接显示为名称。默认款没有独立变体图时使用所属商品快照主图；颜色、尺寸等非默认旧变体缺图时才显示“暂无图片”，不会拿统一主图冒充；任何图片加载失败也不会留下破图图标。

库存不是 Takealot 全平台物理总库存，而是采集时每个变体在当前匿名会话、当前卖家和当前 SKU 下的平台仓购物车可售上限。同一PLID下的各卖家报价先分别保存公开库存状态；匿名购物车探测到的精确或至少数量只绑定给实际测试且变体键、SKU、卖家一致的变体主报价，不会复制给其他跟卖报价。其他跟卖报价若公开数据没有可核验数量，页面只显示“有货/没货/未知”状态，数量保持缺失，绝不补成0。尺寸、颜色等选择器会被组合枚举，页面“各变体库存”逐行展示；当前不可加入购物车的变体直接显示“没货”。无论提示出现在快捷数量还是自定义数量校验中，只要页面出现 `current stock = N` 明确警告，程序就立即把 `N` 保存为精确平台仓库存并停止该变体的所有后续数量尝试。若出现 `Limited to N per customer`，程序会实际验证限购数量 `N`：该数量可以加入时只保存“至少 N”，并标记“每位客户限购 N 件”，不会把促销限购当成精确库存；只有限购数量仍无法加入时才继续在其下方校验库存。确认 9 件可加入后会先验证 10 件；平台提示 `We currently do not have 10 in stock.` 或明确拒绝 10 件时记录为精确 9 件，程序也会在输入框未出现时继续读取页面弹窗。若只是 `10+` 输入框打不开/无法完成输入，且没有明确缺少 10 件的提示，则仍保守显示“至少 9 件”。只有 10 件明确被接受才继续超量测试和二分校验。首次打开数量菜单时会等待动画并最多重开3次；仍读不到数字选项就刷新购物车一次、重新核对同一 PLID 后再试，避免页面慢加载造成偶发“未探测”。数量控件显示更新成功后会留出短暂提示结算窗口，避免平台警告稍晚出现时被误判为已接受。只有999件仍被接受或后续页面拒绝继续验证时才显示保守下限。探测会等待异步加购落库、重试数量菜单动画和临时购物车更新错误，并只把 `aria-hidden` 未启用的数量输入框视为可编辑控件；Braze 营销遮罩只在阻挡目标控件时被清理。本次最终仍未探测成功时，当前库存继续为空；页面只在 SKU、卖家和变体集合一致时显示“上次成功库存 + 时间”的过期参考，该值不会回填当前库存，也不参与库存净流出和销量计算。公开接口标记为 `is_leadtime` 的供应商调货/长时效到货变体不计入有效平台仓库存，统一显示“没货”，也不参与库存净流出销量推断。评论属于 PLID 商品维度，所有变体共用同一份评论，不重复抓取或计数。竞品页面不展示基于评论率反推的累计销量估算；库存变化和观察期评论信号也不是官方销量，补货、购物车占用、取消和评论延迟都可能影响判断。

竞品详情顶部使用“卖家连续对比台”，左侧在同一位置切换卖家，右侧直接比较当前卖家的区间历史，不再要求每切换一次卖家就重新滚动到快照区。卖家默认按所选区间首尾可比的精确库存净流出排序，也可切换为价格、当前精确库存或原始顺序，并支持“上一个/下一个”连续查看；库存净流出只是一种观察信号，不等于实际出货或订单，补货也会改变排序。历史快照改为共用时间轴的价格、精确库存和PLID共用评论数三组折线；三个指标区使用各自的浅色背景，并在相邻指标之间绘制清晰实线分隔，避免把不同量纲误读成一张连续图。鼠标悬浮或键盘左右移动会显示具体北京时间、价格、库存状态/证据和评论数。库存不是精确值时保留断点，不把“至少”或未知数量连成精确库存折线；每条曲线仍只使用当前卖家的兼容报价，不回退到主报价或其他卖家。

竞品详情的“公开评论”支持把好评/中评/差评与起止日期组合筛选，并可按最新评论、最早评论、评分从高到低或评分从低到高排序；页面会显示筛选后的评论数和该商品评论总数。没有评论日期的记录在未设置时间范围时保留，设置时间范围后不纳入结果。

库存探测严格以输入链接中的 PLID 为目标：程序只点击该商品页右侧主购买区的 `Add to Cart`，不会点击“You Might Also Like”“What’s Hot”等推荐商品。跳转购物车后还会再次核对目标 PLID；找不到目标商品就让本条库存探测失败并清空购物车，不会拿其他商品的库存冒充竞品库存。

大量链接首次建档时，可在页面关闭库存探测，先快速采集公开商品与评论；后续再分时补充库存。单个链接失败不会中断整批。

勾选库存探测时，如果商品与评论已经成功但一个或多个可购买变体最终仍为“未探测”，系统会保存已取得的快照，同时把该链接保留在“待重试”，不会误记为完整成功，也不会把它计作断网熔断。每个失败变体会按变体名称、SKU、失败阶段和技术原因持久化说明，例如“打开购物车失败：连接在页面加载时被关闭（ERR_CONNECTION_CLOSED）”；同一原因也会进入当前运行提示和逐链接结果日志，不再只显示笼统的“1/1 个未探测”。第一次自动复探前至少先执行1条其他待执行链接，第二次自动复探前至少先执行2条；总计初次探测加2次自动复探。若当轮剩余任务不足以满足间隔，不会退化为队尾立即复探，而是继续保留待重试，供人工插队或以后继续。复探安排和运行中新增链接都属于普通进度提示，不会再被写入批次停止原因或导致当前商品结束后误暂停。主动关闭库存探测、供应商调货和明确不可加购不属于失败。

竞品最新状态卡片列表顶部提供组合筛选器：关键词可匹配商品名称、PLID、完整Takealot链接以及卡内全部卖家、Offer ID、SKU或变体；粘贴完整链接时自动提取PLID，再叠加“有货 / 没货 / 未探测”库存状态和固定十一类经营信号。经营信号只保留“降价、涨价、价格不变、补货、库存减少、库存数量不变、评论增加、好评增加、差评增加、库存减少且评论增加、新增跟卖卖家”。“检测到补货、库存增加、恢复有货”统一归为“补货”；商品总库存净流出大于0或任一报价库存减少/转为没货归为“库存减少”；同一观察区间PLID评论总数、4–5星好评数或1–2星差评数增加时分别进入对应评论类别，同时发生库存减少和评论总数增加时再进入组合类别；系统首次观察到某卖家的日期落入所选区间时进入“新增跟卖卖家”。评论信号属于PLID商品，不能归属到某个卖家。待建立基线、价格/报价/库存不可比、库存状态不变和旧技术趋势名称不再作为经营信号选项或醒目标签，但原始字段、区间数值、判断说明和详情证据继续保留。列表不再另设一套排序指标选择器；选中经营信号后，真正竞品与自有链接两个分区只用旁边的升序/降序控件，自动按该信号对应的价格变化、库存净变化或净流出、评论增量、好差评增量或新增跟卖卖家数排列。选择“全部”时保持原顺序并禁用方向，缺失变化值始终排在有值记录之后。页面实时显示筛选结果数与商品总数，支持一键清除；本次库存未探测、仅显示上次成功过期参考的商品归入“未探测”。明细支持上一页/下一页，并可选择每页20、50或100条；页面只创建当前页商品卡片，筛选、排序或切换每页数量后自动回到第1页。这些筛选、排序和分页只处理当前已经读取的列表，不会重新采集平台或写入数据库。

共享搜索会把缺失、空值和数字字段统一转换为安全字符串后再匹配；自有商品记录没有真正竞品专属字段时也可继续粘贴完整Takealot链接搜索，不会再因读取`undefined.toLocaleLowerCase()`进入整页错误状态。监控链接管理使用同一空值安全规则。

竞品雷达把当前账号的个人监控池固定为所有角色标题后的第一块独立商品区，不再使用“查看我的个人监控池”按钮跳到下方自有店铺/真正竞品列表。区域直接按账号关系分页展示卡片：已有快照显示图片、商品、价格、库存和最近采集，待首次采集仍显示PLID与等待状态；卡片可打开商品详情、从个人池移除，管理员还可进入原有监控队列操作。输入框和按钮继续保留全局监控含义，按钮文案为“加入监控队列和我的监控池”；新增或重复成功后自动翻到对应页并高亮定位。管理员的共享链接与批次、全局指标、链接失效复核紧随个人池，仍排在商品经营区之前；普通运营不渲染或轮询这些管理员模块。真正竞品列表继续提供“全部竞品 / 只看我的监控池”筛选和“我的监控池”卡片标识，详情顶部继续提供醒目的加入/删除个人池按钮。每个账号只读取自己的个人归类，管理员也不会通过该工作区看到其他账号的个人池。后端继续限制非管理员只能新增全局目标，不能绕过页面调用全局修改、删除、插队、审计或复核接口。个人删除不停止全局每日采集、不移除活动批次，也不删除历史；自有店铺PLID不会进入该池。升级不会按旧操作审计猜测历史归属，既有真正竞品可重新粘贴或从详情按钮加入。

竞品最新状态按 PLID 每个商品只创建一张紧凑父卡片，不会把共享 PLID 的多个卖家报价拆成多个商品。自有商品分区新增“有被跟卖/未发现跟卖”选择器。详情弹窗的“卖家连续对比台”按规范化卖家名称去重，同一卖家的不同SKU、变体和报价放在同一个卖家组内，再在组内切换具体报价；“上一个/下一个”按卖家组移动，不会把同一卖家的不同变体伪装成多个卖家。自有Seller API Offer与公开跟卖使用同一套价格、库存、变化和历史展示，但继续标明数据来源；精确库存只显示在Seller API明确返回或真正匹配购物车探测身份的报价上，非精确值标为“至少”，其他报价若公开数据没有数量则明确显示“数量未返回”且继续保留有货/没货/未知状态，不补0。旧快照没有可区分报价时保留原始链接并明确不猜卖家、Offer ID或库存数量。窄屏下对比台改为单列，卖家导航、组内变体和悬浮明细按可用宽度重排，不产生整页横向滚动。

每张竞品最新状态商品卡都支持直接点击或键盘回车/空格打开完整详情弹窗，无需滚动到页面底部。弹窗顶部的卖家连续对比台把卖家切换、区间排序和历史折线放在同一视口；选中某个卖家后，卖家专属的价格、库存、涨跌信号和折线随选择切换。折线只包含真正匹配当前卖家兼容报价的时间点，不为没有该卖家的日期创建“未识别”占位，也不会回退到PLID主报价或其他卖家数据。Offer ID继续采集和保留为最强身份依据，但页面不强依赖它；界面以卖家、SKU、变体、价格和库存为主，Offer ID仅在有值时使用更小、更浅的辅助文字展示，未返回时不重复创建提示。Offer ID缺失或变化时，只有卖家ID/名称一致且SKU、变体和条件不冲突、同一快照候选唯一时才连接。只按卖家名称无法唯一识别报价，同卖家多SKU或候选歧义时保持不匹配。平台对变体主报价没有返回Offer ID和卖家时，系统只在同一PLID、同一变体主报价且已保存唯一变体明细的范围内，用“变体键 + SKU”建立匿名报价身份，并把该变体已经核验的价格和库存投影到报价历史；SKU变化或出现明确卖家后仍视为另一条报价，不跨卖家连接，普通跟卖也不使用这一回退。评论与商品变体表按同一PLID商品共用：Takealot评论没有卖家或Offer ID归属，因此主报价与跟卖共用同一份商品评论，不伪装为卖家专属评价。监控队列继续按PLID去重，切换报价不会重复加入队列。弹窗完整提供评论分类、起止日期组合筛选、日期或评分排序和评论全文。对比台之后的“监控队列操作”卡允许修改、删除、活动批次插队或重新加入PLID链接。商品详情和卖家报价都不再重复铺在最新状态卡片列表下方，长内容只在弹窗内部滚动，顶部商品标题和底部“打开当前卖家报价页 / 关闭”操作保持可见。“任务爬取详情”内的成功任务和待重试任务也都可以点击或用键盘打开同一套监控队列操作页；待重试入口会明确显示“人工重试并插队”。

梯子或代理短时不稳定时，公开数据浏览器启动会自动重试；无论预热失败、请求取消还是页面超时，程序都会强制关闭页面上下文、Chrome 和 Playwright 驱动，不允许遗留后台浏览器进程。只有真实导航失败、429 或 Takealot 5xx 才归入连接类错误；页面内容暂时无法判定会单独保留重试，不会累计断网次数。404疑似失效、409页面不确定、单条浏览器连接失败和5xx等普通可恢复失败使用按任务数计算的指数退避：三次自动重试前分别至少执行1、2、4条其他待执行链接。若当轮剩余任务不足以满足间隔，不会为了凑次数把失败项直接塞到队尾立即重试，而是继续保留在“待重试”，供人工插队或以后继续；库存未探测仍使用上文总计3次探测、间隔1条和2条任务的规则。明确失败的链接不会因为同一PLID曾经成功或插队成功过而从续爬队列消失，后续任一次成功会立即清除旧失败状态。批量页面连续两条出现真实连接或 Takealot 临时服务错误时会暂停剩余链接，保留此前已成功写入的数据和当前进度，避免断网期间继续空跑全部链接。恢复网络后可重新提交失败链接。

首次遇到商品公开数据 404 或链接仍处于“疑似失效”时，不会删除链接，也不会直接当成永久失效。系统会在同一个 Playwright 浏览器中同时检查目标商品页和最近成功采集的已知正常商品：Takealot 的 `404, Page Not found` 标题或正文会被明确识别为不存在页面，不能因为404页自身也有标题就误认成商品；正常商品则使用商品标题和页面商品内容识别，不依赖单个可见标题在固定8秒内出现。如果对照或目标内容暂时无法稳定判定，本次单独标记“页面复核结果不确定”并保留重试，不计入连接失败；只有目标明确为404页且正常对照可打开，才记录一次有效的“疑似失效”。至少间隔10分钟累计3次有效复核后才首次转为“确认失效”。已经长期确认失效的链接在后续批次只需复核一次：公开商品数据再次返回404时立即维持“确认失效”并作为本批终态，不再重复三次页面和对照检查；403、导航失败、429、5xx等连接异常不算完成复核，仍会保留重试。任意一次后续采集成功都会把状态重置为正常。竞品雷达的“链接复核状态”默认只显示疑似/确认数量并保持收起，需要核对时再展开复核次数、对照 PLID 和最近检查时间，避免平时占用页面空间和创建整张复核表；疑似或确认失效行本身可以点击，即使没有成功快照，也能直接打开对应 PLID 的监控队列操作页，执行修改、删除、活动批次插队或重新加入。

每次点击“开始采集”都会以当时重新读取的真正竞品和自有PLID建立一个独立人工批次，并把链接顺序、已检查位置、待重试位置、已确认失效位置、成功 PLID、运行状态和当前链接请求编号保存到当前浏览器的本地断点。采集中整页刷新或前端重新加载时，ERP 会自动回到竞品雷达并从当前链接恢复，不需要再次点击“继续”；前端会用本地批次编号识别这是刷新前由当前页面启动的同一批次，并用保存在当前标签页的客户端编号重新接回。服务进程仍在时，恢复队列会把服务端仍在执行的当前链接放到最前面，并复用同一请求编号等待原后台探测任务完成，然后才回到最早待重试项，避免刷新后旧请求与待重试队列同时争用 Playwright 浏览器；运行期间其他用户新增的监控链接由服务端按新增顺序保存为待执行队尾项，持有页面每2秒同步并追加写入同一浏览器断点，原任务顺序不变。09:00自动批次不依赖任何浏览器断点，服务端持久保存冻结顺序、当前项、结果、错误和重试队列；ERP退出时当前项仍视为未完成，重启后先恢复该项。人工停止的手动批次不会自动继续；`kxx`停止自动批次后同一触发日期也不会重启。手动“继续失败/未完成”仍按本批已经冻结并保存的链接顺序恢复，不受此后监控清单增删改影响：此前成功的商品即使穿插在待重试项后面也会直接跳过，只重试疑似失效、其他临时失败项和尚未执行项；已确认失效链接在本批后续续爬中自动跳过。这里的跳过仅依据当前批次成功/确认失效记录，不会因为数据库中存在昨天的快照而跳过今天的新采集。历史已确认失效链接会进入新批次，但只要公开商品数据再次返回404就立即作为确认失效终态，不会重新排队累计三次复核。

刷新或切换店铺时，竞品页会优先沿用当前未完成断点的客户端编号，并在页面退出前主动释放同源页面通道。为避免旧页面尚未完全卸载造成误判，只有同一实例连续响应两轮探测才认定为真实的“本账号另一页面”；只响应首轮的刷新瞬时重叠不会换发客户端编号。真正复制或另开的标签页仍会取得独立编号，并继续由服务端单批次租约阻止并发采集。

如果`kxx`在人工批次运行中退出登录、会话过期或切换到另一个账号，竞品页会在会话被替换前立即安全脱离：只取消旧页面对当前请求的等待，不停止服务端已开始的当前商品，也不再由旧页面请求剩余链接；401/403不会被误记为剩余商品失败。断点继续保留当前索引和请求编号，原账号`kxx`重新登录后可以复用同一请求恢复，其他账号仍不能继续或停止该批次；旧会话迟到的401也不会把随后登录的新账号踢出。该行为不是把人工批次变成完全后台运行：当前商品完成后，剩余队列等待`kxx`恢复；需要完全不依赖浏览器的整批运行时使用09:00自动批次，或在独立Chrome个人资料中保留`kxx`会话。

如果梯子、网络或 Takealot 临时服务异常造成连续2条真实连接失败，手动与09:00自动批次都会暂停剩余链接并立即保存各自断点，同时显示距离下次自动尝试的10分钟倒计时。暂停原因逐条记录造成熔断的两个PLID、浏览器连接失败或HTTP状态和接口返回原因；新增链接、插队和库存轮后复探提示不参与计数。Takealot公开API或商品页持续403也按临时连接异常处理。倒计时结束后自动从失败/未完成链接继续；如果VPN仍异常则再次暂停。手动批次把重试时间写入浏览器断点，页面刷新后继续倒计时；自动批次把暂停时间写入服务端断点，页面是否打开或ERP重启都不丢，并在暂停期间持续发布共享状态，让`kxx`仍可停止。人工停止、链接校验错误、权限不足、链接确认失效和正常完成均不会触发自动重启；手动批次还可在倒计时期间点击“继续失败/未完成”提前重试。

服务端把每个批次的开始、手动/自动恢复、暂停、人工停止、完成，以及每条链接的开始、后台数据浏览器、商品与变体、全部评论、库存浏览器、快照保存、结果、请求复用和异常阶段写入 `logs\competitor-collection.log`。库存未探测结果包含失败变体、SKU、失败阶段和精简技术原因；连接类暂停包含连续两条失败的 PLID、状态和原因。同一阶段同时发布到共享批次状态，管理员页面每2秒能看到当前链接正在后台读取数据、复用后台浏览器、启动库存浏览器还是保存快照，普通运营不轮询这套技术状态。从第二条链接起，服务端会在每次公开数据浏览器租约前统一随机冷却5至10秒，即使刷新页面、使用旧前端或上一条网络失败后重建浏览器也不能绕过；前端仍只保留1秒界面交接，不作为真实限速边界。公开浏览器首次预热成功后再随机等待4至7秒，每次变体请求前等待3至6秒，每个额外评论页等待2至5秒；403、429、超时和5xx的原有退避重试保持不变。日志按大小轮转，方便以后区分是页面刷新、人工操作、随机节流、网络暂停还是具体 PLID 异常；日志不记录账号密码和会话密钥。

新增或修改监控链接时，前端会先检查 URL 格式、Takealot 域名和 PLID，服务端再执行同样的强制校验；其他平台链接不会写入清单或送入采集。已有链接修改时必须保持原 PLID，不同商品应先删除旧链接再新增，避免历史身份被改写。

管理员启动人工竞品采集后可以切换到其他 ERP 页面；竞品雷达页面会保持采集实例，返回后继续显示原输入、完成数量、进度条、成功结果和失败说明，不会因为导航切换而清空。

竞品批量采集同一时间只允许一个服务器级批次运行：人工批次由一个账号和浏览器标签页持有，09:00自动批次由正式ERP服务端驱动，但二者共用同一串行租约，不能并发开启第二个Playwright配置。当前来源、操作者、已检查/总数、成功、待重试、确认失效、待续爬、正在处理的PLID和当前采集阶段统一保存在服务端；管理员竞品页的“任务爬取详情”按“成功任务”和“待重试任务”展示同一服务端明细，普通运营页面不加载这套技术进度。服务端对当前请求编号持有单链接租约：页面刷新可以用相同请求编号接回，但另一条链接会被拒绝；自动批次也通过同一个单链接执行入口和协调器，不存在隐藏的第二进程。临时403、网络或服务异常只进入“待重试”，对应链接后续成功后会从该计数移除；“确认失效”取持久化链接复核状态并合并本批刚确认的链接，不会被其他链接成功清零。批次占用期间运营新增项仍按新增顺序追加到当前批次队尾；全局修改、删除和插队只允许管理员，且修改和删除只影响后续新批次，不篡改已经冻结的运行队列。“开始采集”和“继续失败/未完成”在其他批次占用时会显示醒目的橙色提示卡；09:00批次明确标注“每日09:00自动任务”。只有`kxx`可停止活动批次，即使当前页面没有本地断点也会使用共享批次编号提交服务端取消；当前库存探测会跳过慢速清理并关闭库存浏览器和复用公开浏览器。手动批次保留当前索引供恢复，自动批次则持久化未完成当前项供ERP重启续跑。

活动批次运行期间，新保存的监控链接由服务端按保存先后追加到待执行队列末尾，不打断当前正在探测的商品，也不重排断点中已经冻结的任务；连续新增多个链接按先增先执行，刷新或断点恢复后仍保持队尾顺序。管理员若需要提前检查，可在监控链接明细中人工点击“插队”：服务端会在当前正在执行商品之后额外增加一次优先探测，当前浏览器探测不会被强行中断；该链接在原队列中的位置不会被删除，队列走到原位置时仍须按原顺序再探测一次。服务端会在本批保留已接受的手动插队记录；按钮请求成功后立即变为禁用的“已插队”，同一PLID尚未消费的重复请求按幂等成功处理，不会安排多个优先副本。从管理员“待重试任务”点击进入时，按钮会显示“人工重试并插队”，请求使用独立`manual_retry`来源并记录操作人、北京时间、PLID和URL；上一条人工重试已经开始执行后允许再次发起，仍在待执行队列中时重复点击不会增加副本。尚未消费的队尾追加项和手动插队指令同时写入`logs/competitor-batch-queue.json`，ERP重启后同一批次恢复时继续执行；目标真正开始后才从待执行指令中移除，批次完整结束后自动清理文件。

竞品批次的开始、自动/手动继续和停止只认用户名 `kxx`，不按管理员、运营或选品模板放权；其他任何账号即使使用管理员模板，也不能通过页面或接口启停批次。具备竞品采集权限的管理员可新增、修改、删除全局链接、手动插队并查看审计/失效复核；非管理员只可新增链接并管理自己的个人监控池。后端会强制执行这些边界，不能靠修改前端按钮绕过。

`kxx` 可在人工批次或09:00自动批次运行中随时开启或关闭“显示检测浏览器”；即使自动批次显示由“每日09:00自动任务”持有，任何已登录的 `kxx` 页面仍可修改。设置由服务端批次统一保存，当前执行链接保持启动时的原设置，从下一条任务链接开始生效；人工批次同时保存到浏览器断点，自动批次保存到服务端运行断点，ERP重启后继续沿用。其他管理员只能查看共享设置，不能修改；普通运营不显示这项管理员控制。若原始人工采集标签页仍在运行，同账号新页面可点击“接管并继续待重试”；服务端会等待当前商品及其浏览器清理结束后才转移客户端租约，旧页面的下一条请求会被拒绝，因此不会产生两个库存浏览器并发。ERP 重启后服务端人工批次已释放时，新页面也可显式接回同源 `localStorage` 中的既有断点，只继续失败和未完成项，不重跑本批已经成功或确认失效的链接。

共享批次中的失败集合统一标为“未解决”，表示这些链接尚未完整成功；库存复探或普通自动重试执行期间该数字可以暂时不变，只有某条链接成功后才减少。当前卡片会另外显示库存复探/普通重试的次数和实际后端阶段，不再让固定的未解决数字冒充重试执行进度。

活动批次期间，管理员页面的进度条以及成功、待重试、确认失效、已检查、待续爬和逐链接明细统一读取服务端共享批次状态；普通运营不渲染或轮询该管理员模块。非批次持有的管理员页面不得把自己的旧浏览器断点统计混入当前批次。09:00自动批次结束或被停止后继续在管理员模块展示该批次的最终共享统计与明细，避免回退成某个页面的旧本地结果；普通人工批次没有活动状态时，页面才用本地断点数字提示可恢复任务。

当前交付是最小模块。原独立工具中的关键词/类目排名、卖家上新、Buy Box 历史占有率和六工作表 Excel 尚未迁入；这些信号不会在当前页面中伪装成已支持。

## 6. 每日完整运行

```powershell

```

执行顺序为：完整分页采集 → 七个 SAST 自然日指标重建 → 数据质量检查 → 报表导出 → MySQL 表完整性检查 → `mysqldump` 一致性备份、压缩和校验。任何分页失败都不会发布不完整快照或报表。日志写入 `logs\takealot-ops.log`，不会记录 API Key 或数据库密码。

### 运营日报的周期版本

运营日报不会让后一次采集覆盖前一次值。核对周期固定为北京时间当日 10:00（含）至次日 10:00（不含），周期内全部定时采集和右上角手动刷新都归入同一个日报业务日并逐次保存。例如 7 月 25 日 10:00 至 7 月 26 日 09:59 的所有版本都归入 7 月 24 日日报。四个计划阶段分别运行：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli daily-report-run --slot morning
.\.venv\Scripts\python.exe -m takealot_ops.cli daily-report-run --slot evening
.\.venv\Scripts\python.exe -m takealot_ops.cli daily-report-run --slot pre_close
.\.venv\Scripts\python.exe -m takealot_ops.cli daily-report-deadline
```

- 早间任务计划在每天 10:05 触发；当天 10:05 后时间最早的一次完整成功平台仓可售库存，会按实际北京时间日期和实际成功时间冻结到独立的 `daily_inventory_snapshots`。如果内部重试或 Windows 任务重启后才成功，页面、版本标签和导出会显示例如“实际 10:20”，不会仍写成 10:05。业务日 D 的日报统一使用“D 日整日销量 + D+1 日库存”：通常由早间任务取得；若早间库存漏爬或不完整，则采用 D+1 当天随后最早的完整手动或定时拉取，一旦完整即固定，18:00晚间及其他更晚采集不得覆盖。
- 早间、晚间、次日09:00周期末和周期内全部手动版本继续分别保存同一业务日订单与近30天浏览量，但版本核对只比较当天订单数（销量）。周期末任务位于10:00周期结束前一小时，用来补取平台临近周期末才入账的订单；09:00 库存只保留采集留痕。10:05 后的晚间或手动库存只在此前尚无完整库存时用于恢复；首次完整恢复形成后不再被更晚版本覆盖。任意两个成功版本的非空销量不同就进入待办；销量一致时不推送版本待办，库存变化和浏览量变化都不参与版本冲突。
- 每次成功点击右上角“刷新全部数据”都会在完成完整采集后增加一个不可覆盖的手动刷新版本；同一周期允许存在多个手动版本，但普通运营账号受全局1小时冷却限制，管理员可按需越过冷却。
- 普通 HTML、Excel、PNG 日报也使用该前一业务日作为文件日期和数据截止日期；采集仍会重拉截至执行日的最近7个 SAST 自然日，以补回平台延迟订单。
- 每次早间、晚间和周期末任务都有分层保护：单个 HTTP 请求会重试网络超时、429和5xx；整批采集失败后依次使用新会话重试和忽略异常系统代理的直连备用；Windows任务仍失败时每5分钟重启，最多3次。只有 Offers 与 Sales 都完整返回才允许冻结日报，禁止把旧缓存伪装成当次成功数据。
- 每次整批尝试的序号、策略、开始/结束时间、阶段状态、脱敏失败分类和最终根因会同时写入 `logs/takealot-ops.log` 与日报运行记录；页面“采集保护与重试记录”可直接查看。所有路径耗尽后才标记漏爬，并明确区分鉴权拒绝、限流、网络/DNS/TLS/代理、接口异常响应和本地流程异常。
- 已登录页面会订阅运营日报服务端事件。定时/手动拉取、人工处理、撤销或备注落库后，待办列表、日报矩阵和全局未处理提醒会自动重新获取；服务重启或网络短暂中断后会在重连时补刷新。人工编辑弹窗打开期间延后刷新，避免覆盖尚未提交的输入。
- 商品只有在本周期最终采用值的当天订单数或平台库存为空时才标记“漏爬”；近30天浏览量为空不算漏爬，某次采集失败或商品缺席但订单与库存已由其他成功版本补齐时也不打商品漏爬标识。漏爬不算冲突、不要求人工确认，也不阻止导出。所有定时/手动采集失败、商品缺席和字段空值的脱敏原因仍持久化到运行日志，并进入 Excel“漏爬说明”供追查。页面“数据完整性说明”的每条定时或手动采集说明都显示对应数据日期，默认只读取当前日报日及前2天；运营可用开始、结束日期选择器查询任意历史范围，所选范围内的说明全部在固定高度滚动区展示，不再只截取前8条。
- 近30天浏览量保留全部采集版本、底层存储和页面/Excel 展示，但不参与冲突判断；顶部原“暂缺近30天浏览量”汇总卡改为“同周期销量版本差异”且不显示单位，数量统计截至当前日报日仍未处理、带`capture_difference`问题的历史待办；“库存不平”同样统计截至当前日报日仍未处理、带`stock_continuity`问题的历史待办，“已确认”仍只统计当前日报日。浏览量缺失继续保持缺失并在矩阵中显示。同一 10:00 核对周期内，只比较各成功版本的当天订单数；任意非空销量不同就进入“同周期销量版本差异”待办，即使最后一次又恢复为较早数值，中间差异也不会被覆盖。销量一致的商品不推送版本待办，自动采用最新非空销量；业务日 D 的库存采用 D+1 日10:05后的首次完整实采，早间漏爬/不完整时由当天随后最早的完整恢复值补齐并锁定。拥有“处理运营日报待办”权限的账号可选择本周期最新拉取值、早间采集值、晚间采集值或人工候选值确认有差异的销量版本。确认合并必须填写备注；人工修改只需选择修改原因，不要求操作备注。人工候选值可以反复修改，第二次打开会回填上次候选值和原因；每次保存都追加修改前后值的审计，不覆盖历史。若版本差异待办保存的人工订单和库存已经满足相邻日报日库存公式，系统会立即采用该人工值、生成可撤销的确认留痕并关闭整条待办，不再转成库存待办或要求再点击一次“消除差异”；公式仍不相符或暂时无法计算时才继续保留待处理状态。
- 早间首次完整成功后，只要前一日报日正确库存和本日报日订单/库存都已具备，库存连续性公式不平就立即持久化为待办并通过登录态事件流推送，不再出现页面已有红标但数据库仍为“等待晚间”的情况。晚间、周期末或手动版本若随后带来销量差异，销量版本待办按优先级接管；若新版本使库存公式恢复相符，临时库存待办自动解除。
- 库存连续性只在相邻两个日报日都已经取得稳定正确值后计算：某一方仍有未确认的同周期版本差异时，只保留该日期的版本差异待办，跨日公式暂缓。版本确认后系统立即用确认值重算；仍不相符才继续推送独立的“前后日报日库存连续性”待办。若库存待办存在期间又出现新版本差异，则先切回版本差异待办；已经有人工确认基线时，只对比“上次人工确认值”和确认后的新拉取/人工候选，旧的已处理版本只保留审计、不再混入本次证据。重新确认后再用新的确认值计算库存连续性。
- 库存连续性待办只展示前一日报日正确库存、当前日报日正确订单/库存和跨日公式；同周期版本待办只展示本次待确认的版本值。人工修改后，系统会立即用候选订单和库存重算公式：公式已经相符时页面只提供“消除差异”，采用该人工值并关闭红标；公式仍不相符时只提供“确认库存差异”，关闭待办但日报矩阵、库存异常筛选、顶部异常统计和 Excel 库存单元格继续保留红标。两个接口都会在后端重新校验，不能绕过页面执行错误动作；“确认合并”只处理版本选择，不能顺带关闭库存连续性问题。
- 待办卡不会再统一显示“数据有差异”：同周期销量不一致显示“销量版本有差异”，跨日报日公式不平显示“前后日报库存不平”。如果问题由既有人工确认之后的新销量版本或连续性传播触发，标识会明确增加“确认后”或“人工确认后”，版本问题和库存问题使用不同颜色。
- “单独加备注”不会确认、关闭或改变待办。拥有“处理运营日报待办”权限的账号可以新增、修改、删除备注，并按通用备注、同周期版本差异或库存连续性关联展示；新增、修改、删除都会追加审计，保留创建人、修改人、中国时间和修改前后内容。修改通用备注只填写修改后的正文，不另填原因；删除通用备注可直接确认，无需填写删除原因，留痕仍保存被删除内容、操作人和时间。删除版本/库存问题备注仍必须填写原因。删除只从当前有效备注中移除，不会删除审计历史。确认合并时填写的确认备注会自动显示为“（确认：备注内容）”；如果确认合并后库存公式仍不平并继续确认差异，差异备注同时显示为“（库存差异已确认：备注内容）”。两条备注并列写入页面与 Excel 的同一备注单元格。撤销相应确认后只移除对应的当前有效备注，历史仍保留在审计中。
- 人工确认合并后会立即重新计算下一日报日的库存连续性。如果确认前公式成立、确认后的前一日库存却让下一日报日出现新冲突，下一日报日会自动重新进入待办；运营继续确认该待办时，系统再向后一日报日检查，形成可连续传播的核对链。待办卡明确标注“由前一日人工确认合并触发”，并展示触发日期、确认来源、操作人、北京时间、备注、确认前后公式、当前实际库存以及所有相关采集版本的订单和库存。
- 已确认商品可从日期备注行的“备注与确认记录”撤销本次确认。撤销必须填写原因，系统不会删除原确认，而是追加“撤销确认”审计、清空当前最终值并恢复为“已撤销确认待重核”；同日需要重新选择正确版本。若撤销影响下一日报日的库存连续性，下一日报日同时保留“撤销确认后库存待重算”待办，展示原确认值、撤销人/时间/原因、当前订单、实际库存和撤销前公式；前一日重新确认后立即按新正确值重算，仍不平则转成真实库存连续性待办，恢复正确则自动解除。
- 日报下方的“待办处理留痕”集中列出最近100次人工操作，包括人工候选、备注新增/修改/删除、确认合并、消除库存差异、确认库存差异及两类撤销。每一步都独立展示商品、平台SKU、日报日、操作人和北京时间。人工候选允许无操作备注；确认合并和确认库存差异继续展示必填备注，撤销操作继续展示必填撤销原因；通用备注修改/删除只记录新正文或被删除内容。确认记录另展示采用来源或库存公式，备注修改/删除展示修改前后内容或被删除内容。可按北京时间“处理日期”和日报“数据日期”独立或组合筛选，并随时清除筛选恢复全部记录。当前仍有效的确认记录可从这里直接撤销：“消除差异”按确认值撤销，“确认库存差异”按库存差异确认撤销；撤销也独立成一条留痕，原处理记录不删除并标明撤销人、时间和备注。即使商品后来不在当前商品表中，留痕也会从当时的采集快照恢复商品名和平台SKU，并优先恢复可用商品图。
- 点击任一人工核对待办卡或待办处理留痕卡的非操作区域，会把平台 SKU 自动填入上方搜索框、筛出对应商品，并把日报矩阵纵向滚动到该记录自己的数据日期；目标日期的起始行会突出显示。人工修改、确认、备注和撤销等卡片按钮不会触发定位；如果该日期已经不在当前读取的日报表范围内，页面会明确提示。待办卡、留痕卡及其操作/备注弹窗的商品身份区显示平台商品图，缺失或加载失败显示“暂无图片”；日报横向数据表保持原布局，不加入图片。
- 18:30 仍未合并的数据会形成持久待办快照。次日仍正常采集；库存连续性按“上一日报日的 D 日早间库存 − 当前日报日的 D 日整日销量 = 当前日报日的 D+1 日早间库存”核对，历史待办会在 ERP 全局持续提醒。顶部提醒明确标注历史数量不含当前日报日，并同时列出当前日报日数量和下方待办合计，避免把“历史1个 + 当前1个”误读为漏算。
- 页面不再提供“日报业务日期”选择器，固定按北京时间 10:00 边界自动读取当前核对周期对应的日报日。页面和 Excel 主表保留原工作表的商品横向布局；页面加载最近30个有数据业务日，每个日期固定显示“近30天浏览量、当天订单数、平台库存数量（次日实采）、备注”四行，表格内部可上下滚动且一次最多完整显示4日，打开时自动定位最新日期。筛选后的全部商品一次完整放在同一张横向矩阵中，不再拆成24列一组，也不再显示“上一组/下一组”；运营直接使用矩阵底部横向滚动条一直查看到最后一个商品。鼠标指针位于该横向滚动条命中区时，普通滚轮会转换为左右滚动且不再带动矩阵或外层页面上下移动；离开滚动条后仍保持正常纵向滚动。页面日期列会在“当天订单数”和“平台库存数量”对应单元格中显示该日报日全部商品的订单合计与次日实采库存合计，合计只显示数字，不附加“单”或“件”，且不随 SKU 搜索、状态筛选或横向滚动位置变化；任一商品的对应值缺失时显示“—”和缺失商品数，不把不完整数据伪装成总数。早间库存漏爬被后续完整拉取补齐后，不再生成大量商品级占位；库存与日期总格以及 Excel 同一位置统一备注“漏爬已解决”、库存来源和精确到秒的实际北京时间，Excel“漏爬说明”仍保留原失败原因。商品列标题下方只显示 SKU 值，不添加“平台 SKU”前缀；商品名称与 SKU 表头在矩阵内部纵向滑动时持续吸顶，滚动边界不会把手势串到外层页面，避免查看较早日期时失去商品列身份。备注行按“（通用/版本/库存：备注内容）”显示在对应商品列，可点击管理该商品当天的全部备注。“当天访客数”字段已完全移除，不能用30天滚动窗口差值伪造。
- 只要截止日期及之前存在未处理的销量版本差异或库存连续性异常，运营日报 Excel 就拒绝导出并返回具体日期和 SKU；漏爬不会阻断。最后一项待办确认完成时会自动导出到 `exports\operations-daily\YYYY-MM-DD\`。

## 7. 安装 Windows 自动任务

安装脚本本身不会自动运行；只有运营人员明确执行后才会创建计划任务。默认建立六个互不覆盖的任务：`10:05`早间采集、`18:00`晚间复核、次日`09:00`周期末更新同一业务日、`18:30`未合并快照/自动导出、每天`09:00`竞品雷达共享采集，以及当前Windows用户登录后自动确保ERP运行。错过触发时间后会尽快补跑，并忽略并发重复实例：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\install_scheduled_task.ps1 `
  -ProjectPath 'D:\南非店铺数据抓取' `
  -MorningAt '10:05' `
  -EveningAt '18:00' `
  -PreCloseAt '09:00' `
  -DeadlineAt '18:30' `
  -CompetitorCollectionAt '09:00'
```

计划任务使用项目自己的`.venv`和绝对项目路径，不会改变ERP的局域网监听地址。登录自启动任务以当前交互式用户、有限权限运行，延迟30秒等待Windows服务；它只在健康检查失败时调用正式重启链，失败后每分钟最多重试12次。竞品任务动作只登记当日持久触发并通知本机8501，爬取留在正式ERP共享批次中；该任务失败时每5分钟最多重试3次，ERP离线时触发文件仍由登录自启动任务或下次正式启动恢复。安装脚本同时移除旧的“Takealot 自有商品跟卖自动追踪”00:30隐藏并行任务。

周期末任务自北京时间 2026-07-30 起启用；更早日报明确显示“尚未启用”，不会被倒标成漏采。固定09:00而不是09:50，是为了在10:00周期边界前补取一次临近结束的数据，同时为分层重试和Windows任务补跑留出时间。

## 8. 备份与恢复

本项目只制作本机备份，不上传云端或异地。每次 `daily-run` 会先执行 MySQL 表完整性检查，再通过 `mysqldump --single-transaction` 生成一致性转储；成功后压缩为 `backups\takealot-时间.sql.gz`，并生成同名 `.json` 清单和 `.sha256` 校验文件。程序会重新读取整个压缩包，核对 SHA-256、压缩前后大小、MySQL 转储头和完成标记；任何一步失败都会删除本次不完整文件并让任务失败。

需要立即手动生成一份经过校验的本地备份时运行：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli backup-local
```

需要复核已有备份时运行：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli backup-verify `
  .\backups\takealot-YYYYMMDD-HHMMSS-ffffff.sql.gz
```

新格式备份按 UTC 时间分层保留：最近14天保留每一次，15至90天每天保留最新1份，91至365天每周保留最新1份，366天至7年每月保留最新1份，超过7年自动删除。升级前已有的明文 `.sql` 不会被新规则自动删除。

恢复步骤：

1. 停止正在运行的看板和每日任务。
2. 对选定的 `.sql.gz` 先运行 `backup-verify`，确认清单、SHA-256 和压缩内容全部通过。
3. 用 7-Zip 等本机工具解压出 `.sql`；在 MySQL Workbench 中先导入独立的空恢复库并抽查表和行数，禁止直接覆盖正在运行的正式库。
4. 确认恢复副本可用后，再在维护窗口备份或重建目标 `takealot_ops`，使用 Workbench 的 Data Import 导入同一 `.sql`。
5. 运行 `.\.venv\Scripts\python.exe -m takealot_ops.cli verify`，通过后再启动看板和每日任务。

本机备份可以防止误删、错误发布和数据库逻辑损坏，但无法防止整台电脑、同一块物理硬盘或勒索软件同时破坏数据库与 `backups\`。如果以后接入另一块本地物理硬盘，应把备份目录整体定期复制过去；当前方案按用户要求不做异地备份。

### 8.1 D盘 binlog 连续归档

所有备份产物统一保存在 `D:\南非店铺数据抓取\backups\`：完整备份位于根目录，binlog 原始归档、状态文件、校验文件和归档进程日志位于 `backups\binlog\`。MySQL 在 C 盘数据目录中的活动 binlog 是数据库运行源文件，不属于备份副本；程序通过本机 TCP 持续读取并把独立副本写到 D 盘，不会在 C 盘另外创建备份文件。

首次配置需要在服务器电脑上运行一次：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\configure_binlog_backup.ps1
```

脚本会隐藏询问 MySQL 管理员密码，创建 `takealot_backup@localhost` 专用账号，随机生成独立密码并只写入 Git 忽略的 `.env`。该账号只获得读取业务库、取得完整备份坐标和连续读取 binlog 所需的权限；密码不进入命令行、日志或代码。随后优先安装两个 Windows 任务：

- `Takealot MySQL Binlog Local Archive`：开机后持续运行 `mysqlbinlog --raw --stop-never`，断开后每分钟自动重启，从 D 盘已有的最新同名文件继续追赶；
- `Takealot MySQL Binlog Local Archive Maintenance`：每天02:30校验已经关闭的 binlog，生成 SHA-256，并删除超过35天的归档。当前正在写入的文件不会被校验任务删除。

如果当前 Windows 账号没有“任务计划程序”注册权限，安装脚本会自动降级为当前用户的登录启动项，并立即启动两个带互斥保护的隐藏守护循环：归档断开后每分钟重启，维护每天02:30执行。该模式不需要管理员权限，但电脑重启后必须至少登录一次 Windows，binlog 归档才会继续。

检查状态：

```powershell
.\.venv\Scripts\python.exe -m takealot_ops.cli binlog-archive-status
```

归档目标是覆盖最近30天；实际保留35天，为完整备份轮换、任务短暂停止和恢复操作预留5天重叠。启用专用账号后，新生成的 `.sql.gz.json` 清单会同时记录一致性快照对应的 binlog 文件名和位置。时间点恢复顺序为：校验并导入最近完整备份到隔离恢复库 → 从清单记录的位置开始重放 D 盘 binlog → 在误操作前的目标时间停止 → 核对表数、行数和关键业务数据。只有完成隔离库导入与重放演练后，才能称为时间点恢复已经验证。

## 9. 流量指标口径

`page_views_30_days` 只能称为“近30天浏览量”；不得将其或每日快照差值标注为精确日流量或访客数。

店铺级趋势不是 Seller API 直接返回的店铺总数，而是每天次日09:00周期末版本中已返回该字段的商品求和。页面必须同时展示覆盖商品数与缺失商品数；缺失商品不按0计入，整批失败日不连接折线。

“近30天日均浏览量”只是滚动窗口值除以 30；“30天浏览量窗口净变化”只是相邻快照的窗口差值。缺失值保持为空，不补零。

## 10. MySQL 运行边界

- 正式运行只使用本机 MySQL 8.0、`mysql+pymysql` 同步驱动和 `utf8mb4` 字符集。
- ERP 查询连接执行数据库级只读事务；采集、指标重建和竞品刷新使用单独的可写连接。
- 应用账号只授予 `takealot_ops` 数据库所需权限，不使用 root 启动 ERP。
- 每日运行执行 MySQL `CHECK TABLE`，并生成经过 gzip、SHA-256 和完整内容校验的 `mysqldump` 本地备份。
- `data\takealot.db` 仅保留为迁移完成前的数据留档，不再是运行数据源，也不会自动回退。

## 11. NFT102 访客表兼容流程

统一 ERP 前端不再提供 NFT102 上传续写模块。后台实现、既有输出目录和命令行方式仍保留；需要继续使用时，可在中国时间 10:05 后双击项目根目录的 `更新NFT102日报.bat`。该方式会自动寻找本机最新模板，生成新 Excel 与核对报告，并继续遵守不覆盖源文件的规则。

既有基准目录 `data\nft102-baselines\` 和结果目录 `outputs\nft102-daily\YYYY-MM-DD\` 保持不变。连续处理时，输出文件名仍会替换旧的 `_NFT102_日期` 后缀，不会每天叠加日期。

看板固定使用中文界面：导航、按钮、上传提示、字段名、商品状态、异常说明以及图表和表格工具控件均不显示英文。平台返回的商品原始名称、店铺代码、商品编码和南非货币符号属于真实业务数据，保持平台原值，不做猜测性翻译。网页上传上限为100兆字节。

填写口径：

- 表格日期使用当天日期；“当天订单数”使用前一天完整的 Sales quantity。
- “访客总数”填写 `page_views_30_days`，含义是近30天滚动浏览量。
- 接口不提供精确“当天访客数”，因此续写旧模板时该行留空；运营日报页面和导出表不再展示该字段。
- “平台库存数量”填写 Takealot 各地区 `quantity_available` 合计；收货中和在途库存不计入可售库存。
- 仅按表头中的完整 13 位 SKU 自动匹配；无法识别、无法匹配和重复旧列会留空并写入核对报告。

每次会同时生成 `.核对报告.txt`（供运营查看）和 `.核对报告.json`（供程序审计）。
